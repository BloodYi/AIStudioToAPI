# 新旧调度模式的管理界面适配方案

## 1. 背景与目标

项目同时保留旧版单活跃账号调度和新版模型感知多账号调度。当前部分管理界面仍使用旧模式的字段和文案，导致新模式下出现“当前活跃账号 #−1”“使用次数 0 / 40”等无实际意义的信息，浏览器池上限和重试信息也可能来自错误的配置。

本阶段修复管理界面的模式判断、数据来源和操作展示，保留旧调度模式。请求日志保留信息统一移入“设置 → 日志”，继续只读展示。

本文为实施方案，编写本文不代表相关代码已经完成。

## 2. 改造范围

### 2.1 本阶段实施

- 后端基础状态接口明确返回实际调度模式，以及展示所需的模式专属配置。
- 首页按模式展示账号状态、浏览器池上限和重试信息。
- 新调度详情仅在新模式下显示。
- 账号页按模式展示“当前账号”标记和手动切换操作。
- 将请求明细保留与清理状态移入设置页的日志模块，统计页保留摘要和入口。
- 更新中文、英文文案，验证两种模式及加载异常场景。

### 2.2 本阶段不实施

- 环境变量配置的热修改、统一配置持久化及配置优先级重构。
- 浏览器池或执行槽动态扩缩容。
- 调度模式在线切换。
- 调度算法、账号轮换、重试、冷却和日志清理行为变更。
- 删除旧模式代码，或合并新旧模式配置项。
- 公开看板的功能改造。

## 3. 已确认的现状

| 位置 | 当前行为 | 问题 |
| --- | --- | --- |
| `StatusRoutes._getStatusData()` | 返回旧模式的当前账号、使用计数、失败计数、`maxContexts` 和 `maxRetries` | 缺少明确模式字段，新模式界面仍读取旧配置 |
| `/api/dashboard/realtime` | 新模式返回调度器汇总；旧模式返回 `scheduler: { enabled: false }` | 不能仅凭对象存在判断新模式 |
| `SchedulerStatus.vue` | 根节点按 `data` 是否存在显示 | 旧模式的禁用对象也是真值，可能显示空调度卡片 |
| `StatusPage.vue` | 浏览器池上限读取 `MAX_CONTEXTS`，重试信息读取 `MAX_RETRIES` | 新模式应分别使用 `MAX_BROWSER_WORKERS` 和 `MAX_RETRIES_PER_REQUEST` |
| `AccountsPage.vue` | 使用 `currentAuthIndex` 展示当前账号与切换按钮 | 新模式没有唯一活跃账号，不应提供旧模式切换操作 |
| 请求明细保留卡片 | 位于统计页，展示保留天数、清理间隔及状态 | 配置说明与设置页分离 |

现状以编写本文时的工作区源码为准，实施前应核对代码是否已有相关修复。

## 4. 调度模式与接口约定

### 4.1 模式字段

在 `/api/status/core` 的 `status` 对象中新增：

```json
{
  "schedulingMode": "model-aware",
  "schedulerMaxBrowserWorkers": 12,
  "schedulerMaxRetriesPerRequest": 2
}
```

约定如下：

- `schedulingMode` 取值为 `legacy` 或 `model-aware`。
- 以服务实际创建的调度器为准；存在新调度器时返回 `model-aware`，否则返回 `legacy`。
- 新模式的两个配置字段从实际调度器配置读取；旧模式返回 `null`。
- 保留原有 `maxContexts`、`maxRetries`、`currentAuthIndex`、`usageCount`、`failureCount` 等字段及其含义，不覆盖成新模式数据。
- 不将账号切换中的暂停、无请求、无可用账号或数据获取失败解释为模式切换。

明确模式放在基础状态接口中，确保首页、账号页和设置页都能获取，不依赖仅在首页请求的调度详情接口。无需新增设置接口或改变启动流程。

### 4.2 前端加载与异常处理

- 用一个共享的模式状态或计算属性处理条件展示，各页面不重复推测模式。
- 初次加载前为“未确定”，模式专属内容暂不显示；通用内容可正常展示。
- 基础状态请求成功后更新模式与对应配置。
- 请求失败或返回未知模式时，不自动回退为旧模式；已有成功状态可保留，初次加载则继续显示未确定状态。
- 同一次页面会话中，模式确认变化后更新专属内容，避免保留上一个模式的数据和操作。
- 若模式字段缺失，显示必要的加载或版本兼容提示，不用 `currentAuthIndex === -1`、对象存在、账号数量等条件推断。
- 保持现有 ETag 与轮询机制；收到 `304` 时保留有效快照，不清空状态。

管理端与服务端应作为同一版本发布。若需支持旧服务端，兼容逻辑必须能够明确识别模式；不在本阶段默认加入猜测式回退。

## 5. 首页展示规则

| 展示项 | 旧模式 | 新模式 |
| --- | --- | --- |
| 当前活跃账号 | 保留原有展示 | 隐藏 |
| 使用次数／切换阈值 | 保留原有展示 | 隐藏 |
| 连续失败次数／切换阈值 | 保留原有展示 | 隐藏 |
| 已扫描账号总数 | 保留 | 保留 |
| 去重后可用账号 | 保留现有统计口径 | 保留现有统计口径 |
| 同时登录的账号 | 保留原有数量和 `MAX_CONTEXTS` 上限 | 改为“浏览器 Context 数量”，上限使用 `MAX_BROWSER_WORKERS` |
| 错误重试信息 | 保留原有数值、说明和 `MAX_RETRIES` 提示 | 使用 `MAX_RETRIES_PER_REQUEST`，移除旧模式限制说明 |
| 新调度器详情 | 隐藏 | 显示 |
| 流式模式、强制工具、API 密钥来源等通用状态 | 保留 | 保留 |

### 5.1 账号状态卡

新模式直接隐藏前三项，让卡片自然缩短，不新增占位指标。账号和模型的运行状态继续在已有调度详情中查看。

去重后可用账号总数不等同于某模型当前可调度账号数。本阶段不改变统计公式，也不将其描述为模型实时可用数。

### 5.2 浏览器池数量

新模式的数量表示已建立的 Context，沿用基础状态接口的 `activeContextsCount`；上限改用新增的 `schedulerMaxBrowserWorkers`。

该数量不代表 READY 数，也不代表正在执行的请求数。READY、BUSY、INITIALIZING 等状态继续由上方调度详情展示，不在账号卡片重复维护第二套汇总。

旧模式保留 `MAX_CONTEXTS=0` 表示无限的展示规则。新模式不能把缺失值或 `0` 当成无限，缺少配置时显示“—”。环境变量提示也应按模式选择。

### 5.3 重试信息

新模式标签使用“最多重试次数”。例如 `MAX_RETRIES_PER_REQUEST=2` 时显示“最多重试 2 次（最多尝试 3 次）”；配置为 `0` 时显示“最多重试 0 次（最多尝试 1 次）”。

“最多”表示上限，不承诺每个失败请求一定会完成全部尝试。提示变量使用 `MAX_RETRIES_PER_REQUEST`，不再显示旧参数 `MAX_RETRIES` 的值，也不沿用“仅对假流式和非流式生效”的旧说明。

本阶段不重新定义旧模式重试计数的含义，旧模式保持现有行为和展示。

### 5.4 调度详情显隐

首页以基础状态返回的模式作为显示前提。旧模式不渲染新调度详情。

注意新模式的汇总对象目前不一定带有 `enabled: true`，不能直接把组件条件改为 `data.enabled`。可由父组件传入明确模式或启用标记，结合有效数据控制显示。

新模式详情请求失败时保留已有快照或显示加载异常；不因此展示旧模式状态。

## 6. 账号管理页

- 增加明确的模式输入，供账号页统一控制展示。
- 旧模式保留“当前账号”标记、手动切换按钮以及原有忙碌状态限制。
- 新模式隐藏“当前账号”标记及普通切换、快速切换等旧模式操作，不将其他账号误标为当前账号。
- 新模式不向账号页暴露旧模式切换回调，防止隐藏按钮之外仍存在可触发入口。
- 上传认证、导入账号、自动登录、搜索、去重、删除等通用功能继续按原有条件工作。
- 保留服务端已有的忙碌与维护检查。本阶段不放宽账号维护限制，也不以 UI 隐藏替代后端检查。

实施时应检查账号页其他依赖 `currentAuthIndex` 的展示，避免只隐藏按钮而保留错误的状态文案。

## 7. 请求日志保留信息的位置调整

### 7.1 设置页

在“设置 → 日志”中明确区分：

| 分组 | 内容 | 本阶段交互 |
| --- | --- | --- |
| 运行日志 | 日志级别、面板显示条数 | 保留现有操作 |
| 请求明细保留 | 保留天数、自动清理间隔 | 只读 |
| 请求明细清理状态 | 最近成功清理、删除条数、下次清理、已有错误状态 | 只读 |

使用现有日志存储状态接口的数据，不新增独立计算逻辑。设置页进入时加载，展示期间按现有合理刷新机制更新；离开后停止专属刷新，避免重复轮询。

保留必要说明：

- 请求明细按请求完成时间计算保留期限。
- `0` 表示永久保留，自动过期清理停用。
- 配置仍来自环境变量；修改 Compose 环境变量后需重新创建容器生效。
- 已删除明细不能通过延长保留期限恢复；每日与累计汇总长期保留。

加载中、统计功能关闭、永久保留和接口错误应分别显示，不用默认的“30 天 / 60 分钟”掩盖未获取的数据。两个调度模式使用相同的日志保留展示。

### 7.2 统计页

移除原有完整“日志保留”卡片，保留简短摘要，例如“请求明细保留 30 天，每 60 分钟清理”，并提供跳转到设置页日志模块的入口。

永久保留时显示相应摘要；数据不可用时显示明确状态。统计页和设置页使用同一数据来源。请求记录表及过期时间展示保持不变。

本阶段不新增编辑输入框、保存按钮或立即清理按钮。

## 9. 实施顺序

1. 增加基础状态接口字段，确认两种模式返回正确的数据。
2. 接入共享模式判断，处理未加载、失败和模式变化。
3. 修复首页状态卡、新调度详情及变量提示。
4. 修复账号页的标记、切换入口及回调传递。
5. 移动日志保留信息，补齐设置页的数据加载和统计页入口。
6. 更新双语文案，完成接口验证、构建和两种模式的页面验收。

## 10. 验收标准

### 10.1 模式与数据来源

- `legacy` 模式保留当前账号、使用次数、失败计数及手动切换。
- 新模式隐藏上述内容，不再出现无意义的 `#-1` 和旧阈值。
- 旧模式不显示新调度卡片，即使详情接口返回 `{ enabled: false }`。
- 专门配置 `MAX_CONTEXTS=3`、`MAX_BROWSER_WORKERS=12`：新模式显示上限 12，旧模式显示上限 3。
- 专门配置 `MAX_RETRIES=5`、`MAX_RETRIES_PER_REQUEST=2`：新模式显示最多重试 2 次、最多尝试 3 次；旧模式保留原有数值。
- 新模式重试配置为 `0` 时正确展示，不被真值判断替换成默认值。
- 页面首次加载、接口失败、未知模式及 `304` 响应均不会导致误判、空调度卡片或旧切换入口闪现。
- 模式确认变化时，页面不会沿用之前模式的配置或专属操作。

### 10.2 日志信息

- 设置页能够展示保留期限、清理间隔及实时清理状态，统计页摘要与之相符。
- 统计页入口能定位设置页的日志模块。
- 永久保留、统计关闭、加载失败等状态正确区分。
- 文案明确当前仍需修改环境变量并重新创建容器，不暗示已支持热修改。
- 运行日志现有设置正常；请求记录、过期时间和汇总统计行为保持原样。

### 10.3 验证方式

- 为后端新增的模式及字段来源补充有意义的接口回归测试。
- 执行相关现有测试及 `npm run build:ui`，确认模板和双语资源正常。
- 分别在两种启动模式下人工检查首页、账号页、日志设置及统计页。
- 检查窄屏布局及错误状态；不为单纯的显隐模板新增大量镜像实现的测试。

## 11. 后续阶段

运行配置热修改及持久化作为独立阶段评估。后续若实现日志保留热修改，可沿用本阶段的设置模块增加编辑能力；需要另外设计主服务、存储线程和清理定时器的一致更新，不能只增加前端输入框。
