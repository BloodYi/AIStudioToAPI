# AI Studio 弹窗扫描竞态修复方案

本文用于指导后续代码修复。本次交付仅新增方案文档，不修改业务代码。当前代码基线为 `f4b07e4`；关联背景见 [自动登录超时排查与修复方案](./account-login-timeout-investigation.md)。

## 1. 结论与证据边界

**现有证据足以修复“弹窗扫描结果过期，后续可见性检查却使用新页面状态”的代码缺口。** 应将人工挑战判定建立在当前弹窗的完整分类结果上，取消跨时刻的 `knownHint` 布尔值兜底。

不能承诺修复所有 Google 登录或 Studio 人工挑战失败，也不能将这次费用提示误判解释为账号身份及目标应用已验证成功。

用户提供的实际失败任务：

- 任务 ID：`b7945142-154c-4d95-a489-36c561e09354`。
- 结束时间：`2026-10-05T05:33:50.117Z`（北京时间 `2026-10-05 13:33:50.117`）。
- 阶段与错误：`aistudio_ready_wait / manual_challenge`。
- 尝试次数：1；界面显示耗时约 32 秒。
- 明确失败来源：`studio_unrecognized_dialog`。

关键诊断：

| 字段                               | 实际值                 | 含义                                                       |
| ---------------------------------- | ---------------------- | ---------------------------------------------------------- |
| `transitionScan.scanCount`         | `0`                    | 提示扫描时没有可见的 `role="dialog"`                       |
| `transitionScan.scannedDialogs`    | `[]`                   | 没有弹窗进入提示分类                                       |
| `failureSnapshot.transitionCount`  | `1`                    | 失败后快照出现一个同类候选                                 |
| `failureSnapshot.gateCount`        | `1`                    | 有一个候选属于人工挑战兜底选择器                           |
| 该候选 `role / ariaModal`          | `dialog / false`       | 费用提示为非模态弹窗                                       |
| `textMatches.title / cap / create` | 全为 `true`            | 满足现有费用提示的三个文案规则                             |
| `nonblockingRule`                  | `true`                 | 满足现有非模态与尺寸规则                                   |
| 宽高、视口                         | `241×129`、`1440×1000` | 面积占比约 `0.0216`，低于 `0.25`                           |
| `closeButtonCandidate`             | `false`                | 未发现匹配标签的关闭按钮候选，现有逻辑不要求必须关闭此提示 |

快照还有一个 `128×34` 的容器，但它的 `gateCandidate=false`，不属于当前人工挑战兜底选择器，不应仅因出现在诊断列表中就视为阻塞。

失败快照晚于判定瞬间：它不能证明触发判定的节点一定就是最终记录的费用提示，不能排除短暂出现过其他节点，也不能区分新插入、从隐藏变为可见或稍后补上 `role`。不过，扫描与后续页面状态不一致已得到真实记录支持，且临时 Firefox 合成页面实验已复现扫描后出现费用提示导致同类失败。

`operationPart=text_read` 是最后一次操作记录，并非这次错误的异常调用栈。`submitCount=0` 与 `pageStateBefore=totp_input` 是 Google 阶段留下的诊断，不能据此推断验证码未提交。

## 2. 当前触发机制

涉及 `src/accounts/AccountLoginWorker.js` 的 `validateStudio()` 和 `src/accounts/LoginPageHandlers.js` 的 `transition()`。

当前顺序：

```text
terms() 检查协议
→ transition() 扫描提示，当前没有弹窗，返回 false
→ 页面异步变化，弹窗进入可见状态
→ visible() 再次检查当前 DOM，返回 true
→ 使用旧的 accepted=false 与 knownHint=false
→ manual_challenge
```

人工挑战检查在模型升级页及编辑器就绪判断之前执行。因此，Studio 主界面已经显示，也可能被这个兜底条件提前终止。

此外，`knownHint=true` 只证明曾识别到某个费用提示，不能证明其他弹窗不存在。现有布尔门控还存在反向缺口：一个已知提示可能使另一个未知授权弹窗被放过。修复必须同时覆盖这种情况。

## 3. 修复范围与约束

本次修复聚焦 Studio 页面就绪判定，不修改 TOTP 算法、Google 挑战生命周期、重试次数或总执行期限。

必须保持：

- 费用提示仍需满足现有三个文案条件及非模态、尺寸规则。本次不扩大文案白名单，不通过忽略全部弹窗解决误判。
- 已识别非模态费用提示可以保留；没有关闭按钮不构成人工挑战，也不影响继续验证。
- 不点击“创建支出上限”、设置、授权、购买或升级等动作。
- 已知协议仍按既有流程处理；处理后重新观察当前页面。
- 未知阻塞授权、身份不匹配、目标应用连接失败仍禁止会话提交。
- 保留约 1500 毫秒的就绪稳定观察、目标应用原生连接验证，以及最终上下文中的协议与身份复查。
- 诊断只持久化枚举、布尔值、数量和尺寸，不写入原始文字、HTML、URL、凭据、验证码、密钥、Cookie 或原始异常消息。

## 4. 推荐实现

### 4.1 以一次 DOM 观察分类当前弹窗

在 `LoginPageHandlers` 增加用于业务判定的 Studio 弹窗观察接口。一次浏览器端 DOM 调用内完成候选枚举、可见性判断、文本规则、模态属性和尺寸读取，并输出逐弹窗分类及整体状态。

整体状态建议为：

| 状态              | 含义                                     | 后续动作                       |
| ----------------- | ---------------------------------------- | ------------------------------ |
| `clear`           | 当前没有需要判定的阻塞候选               | 继续应用就绪与身份验证         |
| `known_hint_only` | 当前阻塞候选均已确认为允许保留的费用提示 | 可继续验证；关闭为可选动作     |
| `terms_present`   | 当前仍有已识别协议                       | 调用既有协议处理，再重新观察   |
| `unknown_present` | 至少一个阻塞候选未分类                   | 进入受限复核；禁止推进就绪计时 |
| `incomplete`      | 候选超过处理上限、观察失败或读取不完整   | 不允许按无弹窗处理             |

同一次观察的字段用于同一次决定。不得将先前返回的 `knownHint` 与后来的独立 `visible()` 结果组合成失败条件，也不得将“某个已知提示存在”当成“所有弹窗安全”。

### 4.2 区分诊断容器与业务阻塞候选

当前诊断选择器包含 `.cdk-overlay-pane` 等外层容器，比业务兜底选择器更宽。不能直接把诊断快照中 `count>0` 当成人工挑战。

本次先保留现有业务阻塞候选范围：`[role="dialog"], dialog, mat-dialog-container`。提示分类在这组当前候选上执行，消除提示扫描与兜底范围不一致的缺口；更宽的 overlay 容器继续仅作为结构诊断。

同一逻辑弹窗可能同时匹配外层 Material 容器和内层 `role="dialog"`。可在能够确认属于同一逻辑弹窗时归并；仅凭包含关系或外层文字命中不能把内部所有未知授权视为已知提示。归并必须保留内部独立弹窗与未知操作；无法明确归并时保持未分类。

候选枚举应有业务处理上限，例如 20 个逻辑候选。超出上限标记 `incomplete`，不得截取前几个后宣称全部安全。诊断最多保存 10 个样本的上限继续独立保留。

### 4.3 未知状态先进行受限复核

费用提示可能先出现外框，稍后才填充标题和按钮。为了避免把过渡外框立即认定为人工挑战：

1. 首次 `unknown_present` 或可恢复的 `incomplete` 出现时，清空 `readySince`，记录脱敏状态并进入复核。
2. 沿用现有约 250 毫秒轮询节奏，最多追加两次当前 DOM 观察；不得重启步骤期限。
3. 复核后变为 `clear` 或 `known_hint_only`：恢复正常就绪观察。
4. 复核后出现已识别协议：按协议流程处理，并重新观察。
5. 第三次仍有未知候选、仍不完整，或步骤期限已经到达：保持阻止会话提交，返回对应错误。未知弹窗返回 `manual_challenge`；执行期限耗尽沿用现有超时分类，不通过诊断采集覆盖期限错误。

复核次数在一次连续未分类事件内累计，节点替换不能无限重置次数。确认恢复到允许状态后才结束这次事件。整次流程仍受现有步骤期限、尝试期限和队列监督限制。

这是对短暂未分类状态的有界等待，不是自动同意未知授权。

### 4.4 任何 UI 动作之后重新观察

协议接受或费用提示关闭之后，必须读取新的完整分类结果。不得继续使用动作前的快照。

保留费用提示关闭动作的现有次数限制。关闭按钮缺失时无需等待它出现；可继续按 `known_hint_only` 处理。关闭超时恢复只允许在确认目标提示消失或当前状态已达允许后置状态时继续；未知弹窗仍在或无法分类时不视为成功。

在决定是否推进就绪计时前，所有当前业务候选必须已经分类。稳定观察期间每轮继续分类；发现协议、未知候选或读取不完整时中断就绪计时。达到稳定时长后仍须执行邮箱一致性核验、目标连接核验和最终上下文复查，不能直接根据 `studio_shell` 导出成功。

一次 DOM 观察不能保证页面此后永不变化；多轮稳定观察及最终复查仍是必要的防线。

### 4.5 保留和补充诊断

沿用已有 `studioDialogs` 脱敏快照及采集失败状态，并补充：

- `dialogState`：当前整体分类枚举。
- `unknownRecheckCount`：当前未分类事件已追加的复核次数。
- `unknownCount`、`knownHintCount`、`termsCount`：当前逐弹窗分类数量。
- `failureSource`：区分稳定未知阻塞、观察不完整与其他实际失败来源。

持久化的业务分类与诊断采样应标明是否来自同一快照。失败后的额外快照继续视为辅助证据，不能反向替代业务决定。

只使用现有错误枚举时，无需扩展任务 API；新字段可继续通过 `diagnostics` 保存并展示。避免将业务用途的原始文本或元素引用混入诊断对象。

## 5. 修改位置与实施顺序

| 文件                                     | 计划修改                                             |
| ---------------------------------------- | ---------------------------------------------------- |
| `src/accounts/LoginPageHandlers.js`      | 当前弹窗整体观察、逐候选分类、动作后重新观察         |
| `src/accounts/AccountLoginWorker.js`     | 去掉跨快照布尔兜底；加入受限复核与就绪稳定控制       |
| `src/accounts/LoginDialogDiagnostics.js` | 必要时复用安全分类字段，继续隔离业务文本与持久化诊断 |
| `tests/account-login-browser.test.js`    | 将真实诊断对应的时序固定为浏览器回归                 |
| 相关流程测试                             | 验证未知状态复核次数、期限与最终提交条件             |

实施顺序：先建立完整分类结果，再接入 Worker 决策与受限复核，最后保留可选关闭动作和诊断投影。不要仅给旧兜底条件增加固定 sleep，也不要增加登录重试掩盖竞态。

## 6. 验收用例

| 场景                                                                           | 预期                                                 |
| ------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 复现本次记录：旧扫描无弹窗，随后出现三个文案均匹配、非模态、241×129 的费用提示 | 对当前提示重新分类，不报人工挑战，继续身份与目标验证 |
| 同一提示没有可识别关闭按钮                                                     | 允许保留，不等待或点击设置动作                       |
| 仅有 128×34 的非阻塞外层 overlay 容器                                          | 不因诊断容器存在而认定人工挑战                       |
| 已知提示先出现外框，随后填充完整文案                                           | 在复核上限内识别并恢复                               |
| 外框始终无法分类                                                               | 在固定复核次数或步骤期限内失败，不无限等待           |
| 未知授权与已知费用提示同时存在，无论 DOM 顺序                                  | 未知授权仍阻止提交，不被已知提示放过                 |
| 已知费用提示变为未知内容或增加独立授权弹窗                                     | 按当前分类阻止就绪，不能使用旧白名单结果             |
| 费用提示文字不匹配、模态属性为 true 或面积过大                                 | 不自动扩大白名单，受限复核后仍按未知阻塞处理         |
| 同一提示含外层 Material 容器和内层 dialog                                      | 明确归并或保守未分类，不能忽略独立未知弹窗           |
| 可见阻塞候选超过业务上限                                                       | 状态为 incomplete，禁止提交，诊断标明截断            |
| 提示出现后又消失，或节点被替换                                                 | 重新观察；不能无限重置复核次数                       |
| 关闭按钮点击或尺寸查询超时，目标提示已消失                                     | 确认当前完整后置状态后可恢复                         |
| 未知弹窗在就绪稳定区间内出现                                                   | 清空稳定计时，受限复核后决定，不直接提交             |
| Studio 模型升级页没有编辑器，当前只剩已知提示                                  | 继续账号身份及目标原生连接验证                       |
| 身份不匹配、未知授权、目标连接失败                                             | 禁止提交会话                                         |
| 最终会话上下文再次出现协议或未知弹窗                                           | 再处理并复查；未知阻塞禁止提交                       |
| 诊断采集失败、页面关闭或采集超时                                               | 不泄露原始异常，不将失败误报成功                     |

浏览器时序测试应通过明确的调用边界插入或展示弹窗，例如在旧提示扫描完成后、最终分类开始前触发变化；不要只依赖随机延迟制造概率故障。只测试处理函数返回值不足以证明修复，至少一个用例应运行完整 Worker，核验原错误不会提前发生，并验证身份及目标连接门槛仍然生效。

## 7. 交付与部署验收

后续代码修复需要满足：

1. 本次真实证据对应的浏览器时序回归通过。
2. 已知提示与未知授权并存的失败回归通过。
3. 复核次数、步骤期限、尝试期限及脱敏测试通过。
4. 相关 ESLint 和完整项目回归通过。
5. 若部署使用 Camoufox，使用部署实际浏览器另行验收；Firefox 合成页面通过不能替代部署验收。
6. 部署后观察自然发生的登录任务，确认不再因已识别费用提示报人工挑战；若仍失败，依据当前分类和失败快照继续定点。

本方案文档不是代码修复或部署完成记录。真实账号不必稳定复现才能开始实施：固定时序回归可先验证明确的代码缺口，实际环境再用自然故障与脱敏诊断验收。
