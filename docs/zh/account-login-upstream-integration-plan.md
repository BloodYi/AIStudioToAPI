# 自动登录兼容性改造方案

本文用于指导后续改造，尚不代表功能已经实现。

## 1. 目标与依据

在现有账号管理、登录队列和会话恢复框架中，吸收上游登录脚本的页面兼容能力。重点改善新账号首次进入 AI Studio、恢复邮箱确认和账号资料导入流程。

参考上游：

- [账号自动填充指南](https://github.com/iBUHub/AIStudioToAPI/blob/main/docs/zh/auto-fill-guide.md)
- [saveAuth.js](https://github.com/iBUHub/AIStudioToAPI/blob/main/scripts/auth/saveAuth.js)：协议处理、恢复邮箱确认、验证码输入和过渡按钮。
- [setupAuthBatch.js](https://github.com/iBUHub/AIStudioToAPI/blob/main/scripts/auth/setupAuthBatch.js)：批量账号输入格式。

以上链接指向可变的 main 分支，实施时记录实际参考的提交 SHA。移植代码应遵守仓库许可证并保留适用的作者信息。

当前实现入口：

- `src/accounts/AccountLoginWorker.js`：Google 登录状态识别、AI Studio 身份验证。
- `src/accounts/LoginInteraction.js`：有期限约束的输入与点击。
- `src/accounts/AccountLoginService.js`、`AccountLoginQueue.js`：凭据、队列、恢复和会话提交。
- `src/accounts/TargetSessionValidator.js`：目标应用初始化及原生 WebSocket 验证。
- `src/accounts/AuthenticatorImportService.js`、`AccountExport.js`：导入和导出。
- `ui/app/pages/AccountsPage.vue`：账号管理页面。

## 2. 已有能力与缺口

| 能力 | 当前状态 | 改造方向 |
|---|---|---|
| 邮箱、密码、标准 TOTP 登录 | 已实现 | 保留状态机及输入节奏 |
| 自动恢复、取消、重试和重启恢复 | 已实现 | 新页面处理遵守现有执行约束 |
| 身份确认及目标应用验证 | 已实现 | 继续作为提交会话的必要条件 |
| AI Studio 首次协议 | 缺少自动处理 | 优先增加弹窗识别、勾选和确认 |
| 恢复邮箱确认 | 当前转人工 | 增加凭据字段与对应挑战处理 |
| 分格 TOTP | 当前主要输入到单框 | 增加六个独立输入框兼容 |
| 登录过渡页面 | 支持部分固定按钮与验证方式切换 | 补齐明确识别的过渡页 |
| CSV 格式 | 管理页使用 `email,password,totpSecret` | 兼容上游字段并增加恢复邮箱 |
| 失败诊断 | 已有脱敏截图 | 增加受限的控件结构摘要 |

## 3. 实现原则

1. 提取可复用的页面识别与交互函数，接入现有执行器；不直接调用上游 CLI 作为后台登录引擎。
2. 所有等待、点击、轮询和 iframe 扫描受尝试总期限、单步预算和取消信号约束。处理函数不得吞掉取消或超时。
3. 输入与点击复用 `LoginInteraction`，TOTP 保留临近过期等待和最多一次换码机制。
4. 未知挑战、图片验证码、短信、设备确认及企业 SSO 继续转人工；不加入自动识别图片验证码。
5. 登录成功仍须验证实际邮箱、AI Studio 可用性及目标应用真实连接。标题出现、点击成功或 Cookie 数量均不能替代这些条件。
6. 保留账号代理绑定、凭据及会话版本校验、原账号编号更新和原子提交流程。

## 4. 第一阶段：首次协议、恢复邮箱与 CSV 兼容

### 4.1 AI Studio 首次协议

借鉴上游 `acceptAiStudioTermsIfPresent` 的弹窗、iframe、多语言和复选框处理，但收紧作用范围。

处理流程：

1. 到达 AI Studio 后，在等待编辑器就绪期间检测已知协议弹窗。
2. 确认来源属于预期服务，并根据协议文字及容器结构识别弹窗；仅出现“继续”或复选框不足以确认协议。
3. 在已识别的容器内处理明确必需的复选框，兼容原生 checkbox 与 `role="checkbox"`。已经勾选的不重复点击，不自动勾选可选订阅等项目。
4. 优先匹配明确的 `I agree`、`Accept`、`同意` 按钮；仅在已识别协议容器中使用“继续”等上下文按钮。
5. 检查弹窗消失、进入下一步或编辑器出现；无状态变化时有限重试，失败后给出明确原因。
6. 协议处理完成后继续既有身份与服务验证。

需要调整当前就绪等待：协议弹窗也是需要处理的页面状态，不能一直等待 textarea 后才检查协议。协议识别也不能绕过地区限制、Drive 授权或初始化错误。

建议新增 `aistudio_terms` 阶段；已识别协议但无法完成时使用 `terms_or_consent_required`，未知授权仍转人工。后台模式按本方案自动接受明确识别的首次协议，并在操作文档中说明行为。

### 4.2 恢复邮箱确认

新增可选字段 `recoveryEmail`，覆盖完整生命周期：

- 旧账号缺省为空，读取旧存储保持兼容；按现有持久化方式实施必要的数据迁移。
- 支持新增、编辑、清空、凭据读取、导入预览、冲突检查、合并去重和账密导出。
- 普通账号列表只返回是否已配置；具体值沿用现有受鉴权的凭据读取入口。
- 字段变更更新 `credentialVersion`，使旧任务无法提交过时结果。
- 队列通过现有 IPC 将字段发送给执行器，不通过命令行传递。
- 不写入认证 JSON、普通日志或诊断摘要。

页面处理先确认恢复邮箱挑战，再定位 `knowledgePreregisteredEmailResponse` 等已知输入框。允许选择明确的恢复邮箱确认选项；不向任意 `input[type="email"]` 填写恢复邮箱。

当已有可用 TOTP 路径时优先沿用该路径；进入明确恢复邮箱挑战时再使用恢复邮箱。每种方式切换次数有限，避免循环切换。缺少恢复邮箱或遇到邮件验证码收取要求时转人工，不把“输入恢复邮箱地址”与“读取邮箱验证码”混为一谈。

### 4.3 CSV 格式兼容

保留现有导入预览、显式覆盖、版本冲突检查、重复提交和密码原样保存行为。第一阶段支持以下带表头格式：

```csv
email,password,totpSecret
user@example.com,password,BASE32SECRET
```

```csv
email,password,recovery_email,totp_secret
user@example.com,password,recovery@example.com,BASE32SECRET
```

规则：

- 支持 `totpSecret` / `totp_secret` 与 `recoveryEmail` / `recovery_email` 字段别名。
- 表头允许 BOM 和首尾空白；密码内容不裁剪。邮箱使用既有规范化规则。
- 同一字段的别名列同时存在且值不同，按行返回冲突，不静默取其中一个。
- 未提供或空的可选字段不隐式清除已有凭据；清空使用明确的编辑操作。
- 预览展示恢复邮箱是否配置及是否冲突，不展示密码、密钥或完整恢复邮箱。
- 新导出采用 `email,password,recovery_email,totp_secret`，同时更新 ZIP 内的 `credentials.csv`。
- 上游批量 CLI 兼容新导出格式；检查并补齐现有 CLI 对旧管理页三列格式的读取。
- 首阶段管理页仍要求表头，无表头 CSV 明确提示补充表头，避免对三列数据猜测含义。

## 5. 第二阶段：验证码与过渡页面兼容

### 5.1 分格 TOTP

仅在已确认的 Authenticator 挑战内识别输入框：

- 一个可编辑输入框：填写完整验证码。
- 六个明确按位输入的可见、可编辑输入框：依次填写每一位。
- 其他数量或用途不明确：不猜测，不向其他数字框输入。

验证码在控件准备完成后即时生成，整个填写过程使用同一个验证码。明确拒绝时保留既有新窗口换码规则。兼容最后一位触发自动提交的页面，提交前重新检查状态，避免点击下一页按钮。

### 5.2 登录后过渡页面

借鉴上游 `clickGoogleTransitionButtons`，为实际确认的页面建立有限规则：服务来源、页面特征、按钮名称及预期下一状态必须同时明确。

- Google 验证方式切换继续沿用现有逻辑。
- AI Studio 的已知欢迎或引导页面可在识别后继续。
- 未知授权、Drive 权限、手机号绑定、修改密码和可选账号设置不因存在“继续”就自动确认。
- 点击后必须检测状态变化，并限制同一页面的点击次数。

具体规则以脱敏样本和浏览器回归用例为依据，不预先罗列未经确认的页面。

## 6. 第三阶段：受限页面结构诊断

在既有脱敏截图之外增加结构摘要，帮助定位协议容器、iframe 和新输入框：

- 仅记录登录阶段、已知页面类别、控件类型、可见数量，以及命中白名单的按钮标签。
- 不保存原始 HTML、任意正文、脚本内容、完整 URL、输入值、邮箱、Cookie 或 TOTP。
- 属性和控件标签可能包含账号信息；只输出白名单值或枚举，不依赖事后简单正则脱敏。
- 限制扫描数量、文件大小、保留时间和执行预算，复用现有诊断权限与清理机制。
- 诊断失败不改变原登录失败原因，不延长执行器清理期限。

## 7. 建议模块与实施顺序

可新增 `src/accounts/LoginPageHandlers.js`，集中放置协议、恢复邮箱、分格输入和过渡页的识别与处理函数。注入页面、交互器、期限和取消检查，避免另建队列或隐式全局状态。具体拆分以实现时的复杂度为准。

| 顺序 | 主要改动 | 完成条件 |
|---|---|---|
| 1 | 协议处理函数及执行器就绪等待 | 已知协议完成后继续验证；未知弹窗不误点 |
| 2 | 恢复邮箱字段、服务、队列和管理页 | 新增、编辑、清空及版本保护贯通 |
| 3 | 恢复邮箱挑战处理与 CSV 导入导出 | 两种表头格式兼容，导出可重新导入 |
| 4 | 分格验证码和已知过渡页面 | 单框、六格及自动提交分支通过回归 |
| 5 | 受限结构诊断与操作说明 | 失败可定位，敏感信息不进入产物 |

账号元数据、冲突合并和导出不仅涉及数据库字段；实施时检查所有凭据投影、任务失效判断和去重合并路径。旧会话文件结构保持兼容，仅新账号分配新编号。

## 8. 验收标准

### 离线回归

复用现有模拟登录页面和浏览器测试体系，新增有实际失败风险的用例：

1. 中英文首次协议、原生与 ARIA 复选框、已勾选状态、已知 iframe、按钮延迟启用和多步协议。
2. 页面上的无关复选框及“继续”不被点击；未知授权、地区限制和初始化错误保持原有处理。
3. 恢复邮箱确认成功、凭据缺失、错误地址和未知邮件验证码挑战；方式切换不循环。
4. 旧存储加载、恢复邮箱更新及清空、凭据版本变更、合并冲突和认证 JSON 不含恢复邮箱。
5. 两种 CSV 格式、别名冲突、BOM、带逗号或换行的密码、空可选字段与导出往返。
6. 单框、六格、错误框数、近过期等待、明确错误后换码及自动提交。
7. 新增处理中的取消、超时和 iframe 脱离；结束后不能继续交互或提交会话。
8. 诊断文件不包含注入的邮箱、密码、恢复邮箱、验证码或 Cookie。

运行适用测试及项目检查：`npm test`、`npm run lint`、`npm run build:ui`。针对失败或新变化补测，不重复已有队列全套实现。

### 真实验收

仅使用获授权的测试账号，优先采用既有 `scripts/auth/testAccountLogin.js` 的独立临时存储方式，避免修改生产认证目录。恢复邮箱测试输入需随实现补齐。

- 用首次进入 AI Studio 的账号验证协议处理，记录页面状态和是否完成会话提交。
- 若测试账号实际出现恢复邮箱挑战，验证该分支；未出现则报告未完成真实验收，不能用模拟结果冒充。
- 登录成功记录身份匹配、目标应用初始化、真实连接及会话提交结果。
- 新账号只创建一个绑定；过期恢复更新原编号；其他有效账号继续可用。
- 图片验证码转人工，保留脱敏诊断，不自动反复登录。

## 9. 暂不纳入本次改造

不调整当前随机交互参数、固定 headless 模式或 Google 登录入口，也不直接复制上游整套浏览器启动配置。这些差异没有充分证据证明会减少验证码。

上游当前使用 Camoufox，默认可见窗口，从 AI Studio 进入登录；邮箱和密码通过 `fill()` 输入，填写前各随机等待 1–5 秒。脚本未见图片验证码自动处理或显式高级指纹配置。

我们此前开启随机交互后未再遇到验证码，并随后完成过一次完整登录，但现有验收记录不能证明随机抖动是唯一原因。若后续研究行为差异，应独立制定少量获授权账号的对照方案，固定账号、浏览器版本和出口，分别记录验证码与完整登录结果。

## 10. 文档同步与交付

实施完成后同步 `docs/zh/account-auto-login-operations.md`、相关英文说明及账号导入界面提示，明确自动接受首次协议、恢复邮箱使用范围、新旧 CSV 格式和人工处理边界。

交付应包含代码、必要的数据兼容处理、回归结果和真实验收记录。报告区分已验证成功、仅模拟覆盖及尚未出现的挑战，避免宣称所有 Google 新账号都能无人值守登录。
