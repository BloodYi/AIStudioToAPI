# 浏览器恢复与调度负载优化方案

日期：2026-10-13（Asia/Shanghai）。

状态：2026-10-14 已实施项目代码修改，并完成本地自动化验收。未部署或修改生产服务。下文保留设计依据，具体实现与验证记录见第 12 节。

## 1. 依据与问题边界

主要依据：[meow_us build 整体浏览器恢复排查记录](/home/dev/workspace/infra/runbooks/meow-us-build-browser-recovery-investigation-20261013.md)。该记录位于本机工作区，不随项目分发。本文保留必要结论，原始日志仍按排查记录中的私有保存方式管理。

相关历史设计：[Context 初始化硬超时方案](./context-init-hard-timeout-design.md)。后续实施应同步修订其中“两账号超时触发浏览器恢复”的策略和硬超时表述，避免旧文档、测试与本方案冲突。

### 1.1 已确认的问题

- 初始化中的鼠标移动、认证快照等 RPC 超时进入同一个全局故障计数器，默认在 60 秒内涉及两个不同账号即触发全池恢复。
- 多次超时日志记录 `ws_console_success=true`，鼠标等页面操作失败与 WebSocket 初始化成功可以同时出现；连接成功本身不能证明生成业务正常，也不能作为跳过必要鼠标行为的依据。
- 恢复只暂停调度派发，没有完全阻止补池和新初始化。
- 浏览器启动锁只覆盖部分调用路径；旧浏览器断连及关闭收尾可能清空新实例状态。隔离模拟验证了竞态可达，生产日志独立记录了恢复期间重复启动。
- 初始化名额占满后，补池仍反复完整计算候选账号、模型和需求；逐请求提出需求又同步触发补池。隔离复现确认了纯调度 CPU 放大。
- 管理服务、公示面板、请求调度与浏览器管理共用应用进程的 JavaScript 主线程；生产出现跨端口 HTTP 超时，并采样到主线程接近单核满载。
- `Promise.race` 超时不自动取消底层 RPC；浏览器关闭不自动清空 Node 内所有等待请求、lease、Promise 和计时器。
- 恢复流程捕获失败后仍进入统一收尾，恢复调度并记录 `browser_recovery_finished`；该日志不能代表可服务能力已经恢复。

### 1.2 尚未确认的问题

- 最初鼠标 RPC 阻塞的具体原因。关闭期间带出的 Juggler 异常不能直接证明超时前的因果关系。
- 生产主线程各 JavaScript 函数的精确 CPU 占比。无 JIT 符号的 perf 采样不能把匿名地址直接归因到具体方法。
- 重复启动实例的完整生命周期及遗留资源量。
- 历史瞬时负载是否参与最初故障。已有资源采样不支持持续整机资源耗尽或 OOM，但不能排除未采样时段。

不得将本机模拟耗时或提速比例直接当作生产延迟，也不得据此将抗截断逻辑、某个代理节点或账号认定为根因。

## 2. 必须遵守的约束

1. 初始化失败、页面超时、Playwright RPC 异常和 context 清理失败属于浏览器资源处理范围。不得据此禁用账号、改变账号健康资格、标记 Cookie 过期或修改额度。
2. 暂停故障 context 派发、关闭页面或重建 context 属于资源可用性管理；账号仍保留原有资格。
3. 真正的认证、权限和额度异常依赖独立上游证据，继续使用相应业务规则，不能由浏览器错误推导。
4. 局部故障尽量保留其他健康 context 和现有流式请求；只有确认更大范围故障，才扩大恢复范围。
5. 超时返回、逻辑取消、物理资源释放必须分别记录和处理，不能互相替代。
6. 后续实施和验证优先使用本地模拟、隔离浏览器及测试环境；生产发布或主动生产故障注入不属于本文档编写授权范围。
7. 鼠标移动是必须保留的行为，不能因失败就跳过、永久停用或移出必要行为范围。用户补充其原设计目的涉及去除遮罩、维持 Google Cookie 可用性并避免请求 403；该业务约束必须遵守，具体上游机制仍需结合历史实现和隔离验证确认。

## 4. 调度与补池优化

### 4.1 提前检查与批量需求

- 在 `_poolCandidates()` 调用前检查初始化并发名额、生命周期状态和关闭状态。满额时直接返回，保留后续唤醒所需的有效需求。
- `requestContext` 负责记录需求，调度器一轮集中提交并触发一次补池；同账号重复需求合并。
- 合并时保留模型和请求排除规则的语义，避免覆盖需求后使某个等待模型永久饥饿。
- 补池由容量释放、初始化结束、有效需求变化或到期重试等事件唤醒，避免高频无进展循环。
- 不应仅通过把入口检查改为 `scheduler.paused` 完成生命周期控制；人工暂停、恢复暂停和关闭要有明确语义，避免一个入口解除另一个入口的暂停。

### 4.2 模型及账号扫描

- 原始模型名先去重，再规范化；规范化结果再去重，兼容别名。
- 将固定 thinking level 正则移到可复用位置，保持当前模型名解析兼容性。
- 优先建立每轮调度快照，再评估跨轮缓存。模型发现、隐藏/显示、allocation 修改、账号模型变更和账号导入/删除必须正确失效。
- 动态额度、冷却到期、inflight 和请求 excluded 不得被静态缓存冻结；按轮计算或维护独立版本。
- 限制解析缓存容量，避免未知模型字符串导致缓存无界增长。
- `rotation.includes`、反复 `filter` 和账号候选排序可在必要时优化为索引和复用快照，但不得破坏公平性、容量换入与模型分配规则。

### 4.3 调度预算与背压

- 在高成本调度前检查入队上限；明确每模型队列上限和全局上限。
- 恢复中、无可服务资源和过载时明确接纳策略，避免只暂停派发却继续无界积压。
- 队列满、暂时不可服务、等待超时及客户端取消保持可区分的响应；流式响应已开始后按现有协议结束，不能尝试改写已发送的 HTTP 状态。
- 给 `drain` 设置每轮处理量或时间预算，通过能让 I/O 执行的调度方式续跑，不能依赖连续微任务来实现让出主线程。
- 分批派发后仍须保证检查与 lease 预留原子性；跨批次重新核验容量、公平性和客户端取消状态。
- 暂停期间只进行必要且有界的清理，避免继续全量账号扫描和补池协调。

## 5. 浏览器生命周期与资源归属

建议将浏览器状态明确为停止、启动中、运行中、关闭中、恢复中。所有启动入口共享同一启动任务，关闭与恢复进入同一个生命周期协调机制。

### 5.1 归属规则

- 每个浏览器实例拥有 `browserId` 和 generation；attempt、context、连接及异步清理携带所属代际。
- 断连回调捕获具体实例，只能清理所属实例的资源；不能无条件执行 `this.browser = null` 或全池清空。
- 关闭开始时保存被关闭实例引用，关闭收尾核验归属；“主动关闭”标志应按实例维护。
- 不再发布旧代际的初始化结果。迟到创建的 context 应关闭，迟到回调不能触发新代际补池或删除新预留。
- 清理及释放要幂等，防止重复扣减容量、重复 release lease 或重复结束请求。

### 5.2 恢复屏障

恢复状态必须约束需求执行、容量预留、初始化启动、实际 RPC 发起及结果发布等关键入口，而非只约束顶层 pump。

停止旧代际工作后，有界等待旧任务清理；无法清理时升级处理所属浏览器或应用进程，不能无限等待。生命周期协调须避免恢复等待的任务反过来等待同一把锁导致死锁。

## 6. 故障分类与升级条件

| 信号                                  | 首选处理                                                                   | 升级依据                                                 |
| ------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------- |
| 必要鼠标移动失败                      | 保留执行需求；有界重试，资源失效时局部重建后重新执行；不以连接成功为由跳过 | 独立关键操作及现存资源共同指向浏览器故障                 |
| storageState 获取或写入失败           | 单独记录认证刷新失败，保留仍可服务的资源；有界重试                         | 获取阶段持续失败且伴随浏览器级证据；磁盘写失败独立处理   |
| 页面或 context 初始化失败             | 终止本次 attempt，关闭所属资源，退避重建                                   | 故障跨健康资源复现，或底层浏览器断连、持续无法清理       |
| context 清理超时                      | 保留未释放资源的容量记账，跟踪真实关闭结果                                 | 同实例持续不能清理、容量无法恢复，达到有界升级条件       |
| 浏览器断连或确认的关键 transport 故障 | 浏览器恢复                                                                 | 浏览器恢复无进展或应用工作无法退出时升级应用恢复         |
| 主线程持续失联或无进展                | 外部 supervisor 判断                                                       | 结合持续时间、外部响应及工作进展；不能因短时负载立即重启 |

初始化错误数量与不同账号数量只能作为诊断线索，不单独决定全池恢复。探针需要有界、低开销并避免产生生成请求；探针超时也可能来自事件循环迟滞，要结合外部观察判断。

WebSocket 连接状态与必要页面行为完成状态应分别跟踪；只有连接及本轮必要鼠标行为均满足要求，才可发布 READY。连接成功可以停止多余的连接等待，但不能跳过尚未完成的必要鼠标动作，也不能把鼠标失败静默标记为成功。

鼠标失败采用有界重试及退避；已有调用超时但底层仍挂起时，不在同一资源上无限叠加新调用。需要重建 page 或 context 时，保留鼠标执行需求，在新资源上重新执行。必要行为持续不能完成的 context 不接纳新请求，但账号资格不变，其他健康 context 继续服务。后台保活中的鼠标行为同样保留；持续失败时进入资源检查与恢复，不能仅吞掉异常后永久停止。

验收应区分初始化鼠标、后台保活、定期移至左上角和显式遮罩清理的调用路径，不能未经验证就认为它们可相互替代。当前源码中遮罩 DOM 清理是独立动作，具体哪些鼠标动作承担用户所述用途需在实施前核对，不能据此删除任何既有必要行为。认证刷新可从服务就绪关键路径拆出，并保持 sessionVersion 和存储写入的归属校验，防止旧任务覆盖新会话。

## 7. 恢复流程与结束标准

1. 建立恢复屏障，停止对应故障范围的新补池、初始化和请求接纳；健康资源按故障范围继续服务。
2. 对受影响 pending 和 active 请求执行明确且有界的结束策略，解绑取消监听、清理计时器及连接关联，并幂等释放 lease。避免旧请求重试又制造新积压。
3. 取消旧代际 attempt，丢弃迟到结果；尝试关闭所属页面、context 和浏览器。
4. 超时并不代表资源释放成功。无法完成物理清理时执行明确升级路径，不能清空容量记账后继续制造实例。
5. 启动一个受管理的新浏览器，先构建一个连接及必要鼠标行为均满足要求的可服务 context。
6. 按状态逐步开放接纳和派发，再以受控并发补齐目标池。
7. 在明确的观察窗口内检查 ready 资源及实际业务进展；无流量时不能要求生成完成数增长，应使用非生成就绪检查。

状态和日志应区分：恢复开始、浏览器启动成功、最低服务能力恢复、补池完成、恢复失败及升级应用恢复。失败分支不得记录成功完成，也不得无条件开放调度。

重试采用退避、抖动和次数预算。预算耗尽后明确呈现不可用状态并停止高频循环；允许受控低频探测或人工恢复。预算仅在达到持续稳定条件后重置，不能在 launch 成功时立即重置。

## 8. 外部监督与面板隔离

### 8.1 supervisor

现有 supervisor 已支持启动超时、退出处理及进程组终止，尚需设计运行期间的独立健康监督。

- 父进程通过带序号的 IPC 应答、外部 HTTP 响应和工作进展判断持续失联；不能只依赖子进程定时器主动报告健康。
- 根据是否有待处理工作解释进展，空闲进程不能因无完成请求而被重启。
- 应用恢复先有界优雅退出，必要时由父进程终止捕获的旧进程组；旧退出事件和旧 killTimer 不得误杀新子进程。
- 验证浏览器、统计/账号 worker 及其他后代进程均被清理，不能仅假设进程组信号覆盖所有后代。
- 明确账号认证、配置、额度和统计的持久化边界，检查写入完整性和重启后的状态一致性。
- 运行卡死、主动重启、启动失败和配置回滚分别处理，避免运行故障导致错误配置回滚。
- 自动应用恢复同样具有退避和预算，父进程自身监督成本须有界。

### 8.2 面板

在核心缺陷修复后评估独立面板进程。独立端口不能隔离事件循环。

若实施隔离，应通过只读快照或 IPC 提供状态，显示更新时间和数据失联状态；管理动作路由到唯一的业务状态拥有者。业务进程失联时，面板仍可明确展示故障，不能继续把旧快照当作当前健康状态。

不直接增加 Node cluster。当前账号池、浏览器、连接与额度具有进程内归属，复制应用进程之前需要单独完成所有权与跨进程一致性设计。

## 9. 指标与诊断

同步增加以下低开销指标和结构化日志：

- 事件循环延迟、每轮 drain 耗时、处理请求数、候选扫描次数、无容量跳过次数及需求合并数量。
- pending 总数、分模型队列长度、最老等待年龄、在途请求数、实际成功/失败/取消及业务进展。
- ready、初始化中、关闭中和容量预留数量；逻辑取消但物理清理未完成的资源数。
- browserId、generation、attemptId、恢复原因、阶段、耗时、预算及清理结果。
- 请求结束原因及连接归属，区别预期的断连后取消和真正丢失连接管理状态。

健康检查区分进程存活与服务就绪，正常检查不触发全量扫描。无 ready context、恢复中或预算耗尽要反映到就绪状态。

继续调查原始 RPC 阻塞时，应关联超时前后的操作、连接和实例生命周期；性能取样记录时段及符号解析能力。不记录认证内容、Cookie、请求正文或其他敏感数据。

## 10. 验证与验收

### 10.1 必须覆盖的回归场景

| 场景                             | 必须满足的结果                                                                                 |
| -------------------------------- | ---------------------------------------------------------------------------------------------- |
| 初始化名额占满，持续加入需求     | 不执行无效候选扫描；需求不丢失；容量释放后只进行必要补池                                       |
| 一轮大量请求需求                 | 合并补池；保持模型公平性、excluded 规则及容量约束                                              |
| 模型发现、隐藏和账号变更         | 缓存正确失效；不存在陈旧可见性和资格判断                                                       |
| 并发启动、关闭和恢复             | 只存在一个有效受管理启动；生命周期无死锁                                                       |
| 旧实例断连或迟到清理             | 不清空新 browser、context、预留、连接和代际状态                                                |
| 鼠标失败或超时，WebSocket 已连接 | 不跳过必要鼠标动作，不提前发布 READY；有界重试或重建后重新执行；不直接全池恢复，不改变账号资格 |
| 后台必要鼠标行为持续失败         | 保留后续执行需求；检查和恢复所属资源；无无限重试或挂起调用叠加                                 |
| 认证刷新超时，但健康资源仍可用   | 不直接全池恢复；不改变账号资格；没有无界残留 RPC                                               |
| 局部故障且其他 context 正常输出  | 正常流继续；只处理确认的故障范围                                                               |
| 底层 RPC 永不返回或迟到返回      | 逻辑退出有界；迟到结果不发布；物理资源释放或明确升级                                           |
| 恢复失败、首次 ready、逐步补池   | 失败不报成功；未 ready 不开放错误派发；补池遵守预算                                            |
| 恢复期间持续新请求和客户端取消   | 背压生效；监听、计时器和 lease 幂等释放；不会重试放大                                          |
| 子进程主线程被持续占用           | 父进程能判断持续失联并有界终止；新进程不受旧回调影响                                           |
| 连续恢复失败                     | 退避及预算有效；无无限重启；不可用状态可见                                                     |
| 应用进程强制终止                 | 浏览器后代与 worker 无遗留；持久化文件及业务状态可恢复                                         |

现有“两账号超时触发恢复”的测试应按新故障范围策略更新，不能仅为通过旧测试保留已经确认有问题的行为。

### 10.2 负载验证

- 使用固定规模账号、模型和 pending 构建隔离基线，包含排查中的 233 账号、初始化并发 2 且已占满场景；覆盖多模型、容量换入和取消。
- 同时比较扫描次数、drain 耗时、事件循环延迟及 HTTP 响应，不能只比较生成吞吐。
- 单独注入慢 RPC、永不结束 RPC、关闭超时和浏览器断连，验证故障情况下的稳定性。
- 数量不变量通过确定性测试断言；耗时按测试环境基线比较，不把本机绝对毫秒数写成生产保证。
- 各阶段执行相关 browser、scheduler、配置重启、账号会话及面板回归；最终执行项目规定检查。真实浏览器验证与纯模拟测试分别记录。

## 11. 实施顺序与待定参数

推荐按 P0-A、P0-B、P1-A、P1-B、P1-C、P2-A、P2-B 分阶段提交。每阶段记录行为变化、测试结果和剩余边界；上线后观察恢复频率、重复启动、队列年龄、事件循环延迟及 HTTP 可用性，再推进后续阶段。

以下参数需在实施时依据基线确定，并通过统一配置体系提供校验，不能另建互相冲突的配置入口：

- 调度单轮预算、全局队列上限及恢复期间请求接纳策略。
- 故障观察窗口、关键探针超时、旧任务退出及资源关闭时限。
- 恢复退避、冷却、次数预算与持续稳定后的重置条件。
- supervisor 失联阈值、退出宽限期和应用恢复预算。

验收目标是减少故障放大并保证恢复能退出旧工作、重新建立真实服务能力。延长超时、提高并发或增加重启频率不能代替上述修复。

## 12. 2026-10-14 实施记录

### 12.1 已实施行为

- 满额时提前跳过补池扫描；需求按批提交并保留同账号不同模型需求；单轮模型先去重，规范化缓存最多 1024 项，固定 thinking 正则复用。
- 调度验证与候选选择可跨 setImmediate 续跑，默认单轮预算 8 ms；增加默认 1000 的全局等待上限，模型队列满时先判断能否立即派发再决定接纳。
- 浏览器启动、关闭共享生命周期串行队列；启动共享 Promise，实例回调及初始化带代际归属。客户端连接携带 generation 和 attemptId，旧连接不能替换新资源的连接；未携带归属的旧客户端保持兼容。
- 必要鼠标动作失败仍按资源清理、退避重建后重新执行；即使 WebSocket 已连接，也执行初始化末尾的三段鼠标移动后才发布 READY。保留后台随机移动、定期左上角移动及显式遮罩清理，后台监控不再重叠执行。
- 鼠标和认证快照不直接进入全池 RPC 故障计数。关键 RPC 数量达到阈值后进行最多三个页面的独立有界探测，有响应资源时不全池恢复。
- 认证刷新异步执行，并在读取后及进入账号存储互斥区后核对资源归属；未结束的快照 RPC 不叠加重试。
- 恢复先关闭请求接纳与补池，结束 pending、取消 active 请求并幂等释放 lease；物理关闭仍占容量，超时升级处理。最少一个 context 真正 ready 后开放调度，失败不记录成功、不解除屏障。
- 浏览器重建退避默认 5 秒基数，连续预算 3 次，稳定 5 分钟才允许重置。context 初始化失败按资源退避至最多 60 秒，不改变账号资格。
- supervisor 使用父进程发起的有序 IPC 探测和独立 `/livez` HTTP 探测；默认探测间隔 5 秒、持续失联 60 秒、退出宽限 45 秒、应用恢复预算 3 次。无可服务 context 且工作无进展的检查窗口至少为初始化总时限的两倍，空闲状态不因没有生成完成而恢复。
- Linux supervisor 跟踪后代及进程启动时间，清理独立浏览器后代，旧 PID 不因复用而误清理新资源。运行恢复使用最后正常运行配置，保留待重启配置；预算耗尽后父进程保持存活、记录不可用状态，避免 Docker 自动重启形成循环。
- 公示面板独立子进程只接收白名单公开快照。快照超过 15 秒未更新时返回 stale，页面显示上次更新时间和数据中断；独立进程故障由应用恢复处理。管理 API 与业务状态继续由唯一应用进程拥有，未复制账号池。
- 新增 `/livez` 表示 HTTP 进程存活；`/health` 检查真实 context 可用性、恢复状态并返回事件循环延迟、队列等待及调度/补池指标。

### 12.2 配置与运行边界

新增配置通过现有统一配置面板保存，重启生效；默认值见 `.env.example`。运行恢复不会激活尚未手动重启应用的配置草稿。达到自动恢复预算后需要操作人员显式重启，不能靠进程自行无限循环。
