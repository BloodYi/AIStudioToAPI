# 调度面板模型隐藏功能改造方案

## 1. 背景

当前模型感知调度器会在收到请求时，根据请求中的真实上游模型名称，为各个轮换账号创建 `Account × Model` 状态槽。模型即使不在 `configs/models.json` 中，也会在首次请求后进入调度器的运行时状态。

调度面板展示的模型集合来自以下数据的并集：

- `MODEL_WORKER_ALLOCATION` 中配置的模型；
- 当前正在排队的模型；
- 所有账号历史上创建过的模型状态槽。

因此，只要用户请求过一次模型，即使该模型最终返回 403、404、无权限或实际不可调用，它仍可能长期出现在：

- 预估剩余额度卡片；
- 模型调度汇总表；
- 账号与模型详情表。

这些状态会持久化到 `scheduler-state.json`，服务重启后仍然存在。目前管理端没有移除或隐藏这类模型的入口，错误模型会持续污染调度面板和额度展示。

## 2. 改造目标

为调度面板增加一个由管理员控制、可持久化的“移除显示”功能。

管理员将模型从调度面板移除后，该模型应当：

- 不再出现在预估剩余额度区域；
- 不再出现在模型调度汇总表；
- 不再出现在账号与模型详情表；
- 不再参与管理端展示的剩余额度总数和已跟踪模型数；
- 不从 `configs/models.json` 中删除；
- 不从 OpenAI/Gemini 兼容接口的模型列表中删除；
- 不删除历史请求记录和使用统计；
- 不删除已有的 `Account × Model` 状态；
- 不清除请求次数、失败次数、429、冷却或不支持状态；
- 不影响后续请求、账号选择、重试和模型调度；
- 不因用户再次请求而自动恢复显示；
- 可以由管理员主动恢复显示。

本功能是管理端的显示控制，不是模型删除、模型禁用或访问控制功能。

## 3. 非目标

本次改造不包含以下能力：

- 自动发现 Google 新模型；
- 在管理面板中添加或编辑 `models.json`；
- 禁止用户调用某个模型；
- 删除某个模型的历史使用记录；
- 清除某个模型的调度状态或今日计数；
- 修改现有 Flash/Pro 额度估算规则；
- 修改协议转换、账号轮换或上游重试逻辑。

如果未来需要“禁止调用模型”，应单独设计模型允许列表或禁用列表，不能复用本方案的隐藏状态。

## 4. 核心语义

### 4.1 隐藏而不是删除

尽管前端可使用“从面板移除”作为操作名称，后端和持久化结构应使用 `hidden`、`hideModel` 等语义，避免将它理解为真正删除模型。

隐藏模型后，以下内部状态必须继续保留：

- `request_count`；
- `daily_request_count`；
- `daily_failure_count`；
- `failure_count`；
- `success_count`；
- `rate_limited`；
- `cooldown_until`；
- `unsupported`；
- `last_error`。

不建议从所有账号中删除模型状态槽。直接删除状态槽会导致以下问题：

- 已有 429 和冷却状态被解除；
- 今日请求数和历史累计数丢失；
- 恢复显示后无法还原原有数据；
- 下次请求会重新创建一个看似全新的模型；
- 可能与正在执行的 lease 产生状态引用冲突。

### 4.2 隐藏状态只能由管理员改变

运行时请求可以继续调用 `slot(account, model)` 并更新模型状态，但不能修改隐藏集合。

模型一旦被管理员隐藏，即使之后再次收到相同模型的请求，也必须继续保持隐藏。只有管理员执行“恢复显示”操作时，模型才能重新进入调度面板。

### 4.3 仅过滤管理端快照

隐藏状态只作用于管理端调度快照，不参与调度决策。

应保持以下关系：

```text
调度器完整模型集合
    ├── 调度、账号选择、429、计数和持久化继续使用完整集合
    └── 排除 hiddenModels 后生成管理端可见模型集合
            ├── 额度卡片
            ├── 模型调度汇总表
            └── 账号与模型详情表
```

## 5. 状态设计

### 5.1 隐藏集合

在 `ModelScheduler` 中增加一个集合：

```js
this.hiddenModels = new Set();
```

集合中的值统一使用真实上游模型 ID，不包含 `models/` 前缀，也不包含项目支持的 thinking、stream、search、code 等请求侧后缀。

示例：

```json
["gemini-3-flash-preview", "gemini-3.5-flash", "gemini-3.6-flash"]
```

### 5.2 持久化位置

建议将隐藏集合保存在现有 `scheduler-state.json` 顶层，而不是写入 `configs/models.json`。

原因如下：

- `models.json` 表示对外模型目录；
- 隐藏集合表示管理端运行时显示偏好；
- 隐藏模型不应改变 `/v1/models` 和 `/v1beta/models`；
- 可以复用调度器现有的延迟保存、临时文件和原子重命名机制；
- 隐藏状态与其对应的运行时模型状态可以一起迁移和恢复。

建议将状态版本从 3 升级为 4：

```json
{
  "version": 4,
  "hiddenModels": ["gemini-3.5-flash", "gemini-3.6-flash"],
  "accounts": [],
  "fileAffinities": []
}
```

加载版本 1、2、3 的旧状态时，`hiddenModels` 默认为空集合，并继续执行现有日统计字段迁移。加载版本 4 时，需要验证 `hiddenModels` 是字符串数组，并对模型名进行规范化和去重。

### 5.3 状态方法

建议在 `ModelScheduler` 中增加：

```text
hideModel(model)
showModel(model)
isModelHidden(model)
hiddenModelsSnapshot()
```

`hideModel(model)` 应执行：

1. 规范化并验证模型名；
2. 确认模型存在于调度器当前已知模型集合中；
3. 将模型加入 `hiddenModels`；
4. 更新调度快照 revision；
5. 立即持久化状态；
6. 返回操作结果。

`showModel(model)` 应执行：

1. 规范化并验证模型名；
2. 将模型从 `hiddenModels` 移除；
3. 更新调度快照 revision；
4. 立即持久化状态；
5. 返回操作结果。

重复隐藏或重复恢复应当是幂等操作。

## 6. 调度快照改造

### 6.1 保留完整模型集合

现有 `_snapshotModels()` 继续返回调度器知道的全部模型：

```text
配置模型 + 排队模型 + 账号模型状态槽
```

不要改变它的底层语义，以免影响调度、诊断或后续功能。

### 6.2 增加可见模型集合

增加 `_visibleSnapshotModels()`，其结果等于：

```text
_snapshotModels() - hiddenModels
```

所有面向管理端的模型和额度展示都基于该集合生成。

### 6.3 `summarySnapshot()`

需要过滤：

- `models`；
- `quota_by_model`；
- `quota_tracked_models` 的间接计算来源；
- 旧兼容字段 `estimated_remaining_quota` 的计算来源。

隐藏模型不再参与管理端额度合计，但其后台计数仍然继续更新。

应尽量在计算额度和账号状态之前排除隐藏模型，避免为了不可见模型额外创建状态槽或进行无效汇总。

### 6.4 `accountsSnapshot()`

需要过滤每个账号返回的 `accounts[*].models`，保证隐藏模型不会在账号详情展开后重新出现。

该过滤仅作用于序列化结果，不得从 `account.models` 内部对象中删除状态槽。

### 6.5 `snapshot()`

兼容接口 `/api/scheduler` 返回的以下字段也应保持一致：

- `models` 只包含可见模型；
- `accounts[*].models` 只包含可见模型；
- `quota_by_model` 只包含可见模型；
- `estimated_remaining_quota` 只汇总可见模型；
- `quota_tracked_models` 表示可见且可估算额度的模型数。

## 7. 管理 API

所有接口使用现有管理后台身份验证中间件。

### 7.1 隐藏模型

```http
POST /api/scheduler/models/hide
Content-Type: application/json

{
    "model": "gemini-3.5-flash"
}
```

成功响应：

```json
{
  "success": true,
  "model": "gemini-3.5-flash",
  "hidden": true,
  "changed": true
}
```

### 7.2 恢复显示

```http
POST /api/scheduler/models/show
Content-Type: application/json

{
    "model": "gemini-3.5-flash"
}
```

成功响应：

```json
{
  "success": true,
  "model": "gemini-3.5-flash",
  "hidden": false,
  "changed": true
}
```

### 7.3 查询已隐藏模型

```http
GET /api/scheduler/models/hidden
```

响应：

```json
{
  "models": ["gemini-3-flash-preview", "gemini-3.5-flash"]
}
```

列表按模型名排序，保证响应和前端展示稳定。

### 7.4 输入校验

接口至少需要执行以下检查：

- `model` 必须是非空字符串；
- 去掉前后空白和可选的 `models/` 前缀；
- 限制模型名最大长度；
- 拒绝换行、控制字符和明显无效的模型名；
- 拒绝 `__files__` 等内部模型；
- 隐藏模型时，模型必须存在于当前调度器已知模型集合中；
- 重复隐藏或恢复返回成功，并通过 `changed: false` 表示状态没有变化。

不建议使用 `DELETE /api/scheduler/models/:model`，因为该接口容易让调用者误以为模型状态、历史统计或 `models.json` 条目会被真正删除。

## 8. 前端设计

### 8.1 操作入口

在模型调度汇总表最右侧增加“操作”列，每个模型提供“从面板移除”按钮。

不建议在顶部额度卡片中重复放置按钮。模型汇总表信息更完整，也更适合承载管理操作。

### 8.2 确认提示

点击“从面板移除”后显示二次确认：

```text
确定从调度面板移除 gemini-3.5-flash 吗？

该操作不会删除模型配置、历史请求或调度状态，
也不会阻止用户继续调用该模型。稍后可以恢复显示。
```

确认按钮使用“移除显示”，避免仅使用“删除”。

### 8.3 已移除模型入口

在现有批量重置操作附近增加：

```text
已移除模型（3）
```

点击后显示已隐藏模型列表：

```text
gemini-3-flash-preview    恢复显示
gemini-3.5-flash          恢复显示
gemini-3.6-flash          恢复显示
```

隐藏列表必须由独立接口获取，不能依赖已经被过滤的调度快照反推。

### 8.4 操作后刷新

隐藏或恢复成功后应立即：

- 刷新实时调度摘要；
- 刷新已经展开的账号详情；
- 刷新已隐藏模型列表；
- 清除旧的操作错误提示；
- 通过状态消息告知管理员操作成功。

操作时增加局部 loading 和重复点击保护，不需要刷新整个页面。

隐藏或恢复操作必须推进调度器 revision，否则现有 ETag 缓存可能返回 304，导致界面不能立即反映变化。

### 8.5 空状态

如果所有模型都被隐藏：

- 额度区域显示“暂无可显示的模型额度”；
- 模型调度表显示“暂无可显示的调度模型”；
- 逻辑执行槽、队列、Context 和错误指标仍然正常显示。

## 9. 显示边界

| 页面或数据            | 隐藏后是否显示 | 说明                      |
| --------------------- | -------------- | ------------------------- |
| 预估剩余额度卡片      | 否             | 不再计算到前端展示合计    |
| 模型调度汇总表        | 否             | 整行隐藏                  |
| 账号与模型详情        | 否             | 所有账号下均隐藏          |
| 已移除模型列表        | 是             | 用于恢复显示              |
| 历史请求记录          | 是             | 保留审计能力              |
| 使用统计图表          | 是             | 不修改统计数据            |
| `/v1/models`          | 不受影响       | 继续由 `models.json` 生成 |
| `/v1beta/models`      | 不受影响       | 继续由 `models.json` 生成 |
| `configs/models.json` | 不受影响       | 不写入、不删除            |
| 调度和账号轮换        | 不受影响       | 继续使用完整状态          |
| 429 和冷却状态        | 继续生效       | 隐藏不等于重置            |

## 10. 特殊场景

### 10.1 模型正在执行请求时被隐藏

允许执行隐藏操作：

- 当前请求继续完成；
- 后续请求继续正常调度；
- 仅管理端不再展示该模型；
- 不修改正在使用该状态槽的 lease。

### 10.2 模型处于 429 冷却时被隐藏

429、冷却截止时间和不可用账号数继续在后台保留。恢复显示后，应重新展示当时的有效状态；如果冷却已自然到期，则按现有逻辑恢复为健康状态。

### 10.3 隐藏模型再次被请求

请求继续正常执行，计数和错误状态继续更新，但模型不得自动退出 `hiddenModels`，也不得重新出现在实时面板。

### 10.4 `models.json` 发生变化

隐藏状态与 `models.json` 解耦：

- 从 `models.json` 删除同名模型，不清除隐藏状态；
- 以后重新加入同名模型时，仍保持隐藏；
- 管理员恢复显示后，才重新进入调度面板。

### 10.5 调度状态文件被人工清除

如果管理员主动清除整个 `scheduler-state.json`，隐藏集合会与其他运行时调度状态一起丢失。这符合两者采用同一状态文件的设计语义。若未来要求隐藏偏好独立于调度状态备份和清理，再将其拆分为独立管理配置文件。

## 11. 安全与一致性要求

- 隐藏和恢复接口只能由已登录管理员调用；
- 不接受客户端提交账号索引或内部状态对象；
- 不根据前端传入内容直接修改账号模型槽；
- 持久化继续使用临时文件写入和原子重命名；
- 模型名在写入集合前统一规范化；
- 接口日志记录管理员操作和模型名，但不记录认证信息；
- 隐藏操作不得暂停调度、取消请求或重置账号；
- 后端负责过滤，前端不应成为隐藏逻辑的唯一实现位置。

## 12. 测试方案

### 12.1 后端单元测试

至少覆盖以下场景：

1. 隐藏模型后从 `summary.models` 消失；
2. 隐藏模型后从 `quota_by_model` 消失；
3. 隐藏模型后从所有 `accounts[*].models` 消失；
4. 隐藏操作不删除内部账号模型槽；
5. 隐藏操作不清除 429 和冷却时间；
6. 隐藏操作不清除今日请求数和失败数；
7. 再次请求隐藏模型不会自动恢复显示；
8. 隐藏模型的后台统计仍然继续增加；
9. 恢复显示后原统计和状态重新出现；
10. 重启并重新加载状态后仍保持隐藏；
11. 版本 1、2、3 状态升级后隐藏集合默认为空；
12. 重复隐藏和恢复保持幂等；
13. `__files__` 等内部模型不能被隐藏；
14. 隐藏模型不影响其他模型的额度和 429 状态；
15. 隐藏全部模型时快照结构仍然合法。

### 12.2 API 测试

覆盖：

- 未登录访问被拒绝；
- 合法隐藏和恢复；
- 空模型名返回 400；
- 无效模型名返回 400；
- 隐藏不存在的模型返回 404；
- 隐藏列表正确返回并排序；
- 重复操作返回 `changed: false`；
- 操作完成后 revision 发生变化；
- `/v1/models` 和 `/v1beta/models` 不受隐藏操作影响。

### 12.3 前端测试

覆盖：

- 点击移除时出现确认提示；
- 取消确认不会产生变化；
- 隐藏成功后额度卡片和模型表格行同时消失；
- 已展开的账号详情同步移除该模型；
- 已移除模型列表能够恢复显示；
- API 失败时显示错误，且不提前修改本地展示；
- 操作期间按钮不可重复提交；
- 所有模型被隐藏时显示正确空状态。

## 13. 推荐实施顺序

1. 扩展调度器状态版本，增加 `hiddenModels` 的加载和持久化；
2. 实现 `hideModel`、`showModel` 和隐藏列表快照；
3. 在 `summarySnapshot()`、`accountsSnapshot()` 和兼容 `snapshot()` 中统一过滤；
4. 增加隐藏、恢复和查询隐藏列表的管理 API；
5. 确保操作推进 revision，并验证实时接口不会错误返回 304；
6. 在模型调度表增加操作列和确认交互；
7. 增加“已移除模型”列表及恢复入口；
8. 补充中英文文案、空状态和错误提示；
9. 完成后端、API 和前端测试；
10. 使用真实 403、404、429 和成功请求进行端到端验证。

## 14. 验收标准

功能完成后，应满足以下条件：

1. 一个不可用模型因用户请求出现在调度面板；
2. 管理员可以将它从面板移除；
3. 额度卡、模型汇总表和账号详情均不再显示它；
4. 历史请求和使用统计仍然保留；
5. `configs/models.json` 没有发生变化；
6. 用户仍可请求该模型，并获得现有逻辑产生的正常响应或错误；
7. 该模型的后台计数、429 和冷却状态继续更新；
8. 再次请求不会使模型自动重新显示；
9. 服务重启后仍保持隐藏；
10. 管理员恢复显示后，原累计数据和当前状态重新出现；
11. 隐藏操作不影响其他模型和正在执行的请求；
12. 对外 `/v1/models` 和 `/v1beta/models` 响应不受影响。

## 15. 后续扩展

本方案可以作为未来人工模型管理功能的基础，但后续功能应保持语义分离：

- `hidden`：只控制调度面板是否展示；
- `enabled`：控制是否允许用户请求；
- `listed`：控制是否出现在对外模型列表；
- `quota_policy`：控制额度估算方式；
- `configured`：表示是否由管理员正式登记。
