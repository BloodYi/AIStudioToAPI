# 公示模式多节点汇总改造方案

状态：已实现。本文记录接口、配置、统计口径及验收要求；部署方法见第 12 节。

## 1. 目标与已确认前提

公益站通过多台服务器独立部署本项目，入口通过负载均衡分发 API 请求。需要在一个公示面板中汇总各节点的模型可用量、请求量、实时负载和历史统计。

已确认：

1. 各节点使用独立、不重复的账号池，可以按模型累加额度和账号数量。
2. agent 每隔几秒主动生成并更新本机公示快照；主控读取已经生成的快照，不能通过查询接口触发 agent 重新统计。
3. 主控定时读取各 agent 的快照并缓存汇总结果；公众访问面板只读取主控缓存，不触发远程采集。
4. 主控本身仍是本项目的完整部署，可以正常处理 API 请求，并将本机统计纳入公示；没有配置 agent 时也能独立公示。

这里的“agent 主动更新”指主动更新本机快照，不是向主控推送数据。第一版采用主控读取快照的方式，不增加推送注册接口。

agent 的快照生成频率和主控数量、公示页访问人数无关。查询仍有网络、鉴权和发送响应的开销，但不能产生额外数据库查询或统计计算。

## 2. 功能边界

新增三种公示角色：

| 角色 | 行为 |
| --- | --- |
| `standalone`（独立） | 保留现有公示功能，仅展示本机数据；作为默认值兼容旧部署 |
| `master`（主控） | 提供公示页面及汇总 API，汇总本机和配置的 agent |
| `agent` | 定时生成本机快照，提供受鉴权保护的快照查询接口，不提供匿名公示页面 |

`PUBLIC_DASHBOARD_ENABLED=false` 时，以上公示服务、快照定时任务和远程采集均不启动。

不改变 API 负载均衡、账号调度、重试、配额规则、管理端登录及请求处理流程。第一版不包含远程管理、自动发现、跨节点账号同步、主控高可用或历史统计中央持久化。

## 3. 数据流与缓存

```text
各节点应用进程
  └─ 定时生成本机统计快照（默认每 5 秒；同一轮生成公开投影与聚合计数）
       └─ IPC 发布给本机公示子进程，原子替换内存缓存

主控公示子进程
  ├─ 接收本机快照
  ├─ 定时读取各 agent 的受保护快照接口（默认每 5 秒）
  ├─ 按节点保存最近一次有效快照及采集状态
  └─ 生成并缓存汇总后的公开 JSON
       └─ 公众浏览器读取 /api/public/dashboard
```

### 3.1 Agent 快照生成

- 使用定时任务主动生成快照，启动后立即执行一次。
- 每轮取得一次统计时间 `asOfMs`，本轮近期窗口和快照时间都使用该时间。
- 单节点生成任务不得重入；上一轮未完成时跳过本轮，不堆积任务。
- 成功后原子替换完整快照；失败保留上一次成功快照及原始生成时间。
- 查询接口只读取缓存，不能调用 `getSnapshot()` 触发构建、查询 SQLite、等待新一轮生成或扫描账号池。
- 可以在更新缓存时预先序列化 JSON 和计算 ETag，读取时直接发送。
- 尚无成功快照时返回 `503`，不能返回一份零值冒充可用数据。

### 3.2 主控采集与汇总

- 后台定时并行采集；默认并发上限为 4，单节点请求超时为 2 秒。
- 每个节点最多存在一个在途请求，不因上一轮超时而无限累积采集任务。
- 主控启动后立即采集一次，不阻塞本机 API 服务启动。
- 本机快照直接经 IPC 获取，不通过 HTTP 查询自己。
- 某个 agent 失败不能中断其他节点的采集和汇总。
- 采用固定采集周期，失败后等待下一周期，不在同一周期连续重试。
- 新快照到达、采集状态改变、日期改变时重建汇总；另以每秒一次的轻量任务检查快照过期并更新状态，不查询数据库。
- 公示 HTTP 请求只读取已生成的汇总缓存，浏览器刷新不触发采集或汇总重算。
- 没有任何可用快照时返回 `503`；有部分有效节点时返回 `200` 并明确标记数据不完整。

最终应满足：无论有多少人访问公示页，单个 agent 的统计生成任务始终按固定周期运行，主控到 agent 的查询频率也保持固定。

## 4. 接口契约

### 4.1 Agent 本机快照接口

新增：

```http
GET /api/agent/dashboard
Authorization: Bearer <agent-token>
Accept: application/json
```

- 仅在 `agent` 角色启用，其他角色对此路径返回 `404`。
- 接口只能返回本机快照，不接受任意 URL、模型筛选、时间范围或路径参数。
- 不挂载匿名 `/api/public/dashboard`、公示首页和静态前端。
- 必须验证独立的 agent Token，不复用管理密码或 API 调用密钥。
- 未提供 Token 或 Token 无效时统一返回 `401`；错误信息不包含内部细节。
- 设置 `Cache-Control: private, no-store`，避免受保护的快照被公共代理缓存。
- 可以支持条件请求；`304` 只能表示原快照未变化，不能刷新其生成时间或使过期数据重新变新。
- 不开放浏览器跨域访问，主控通过服务器端 HTTP 客户端访问。

建议响应采用独立协议版本：

```text
agent_schema_version: 1
node_id: 稳定的节点唯一标识
snapshot_sequence: 本进程内递增的成功快照序号（仅诊断，不用于跨重启排序）
generated_at: 本次成功快照生成时间，UTC ISO 8601
service_status: ready | unavailable
snapshot: 现有本机公开 DTO
aggregation:
  history: 原始累计聚合计数
  models[]:
    model: 模型标识
    history: 原始分模型累计聚合计数
    recent_stats:
      24h: 原始近期聚合计数
      1h: 原始近期聚合计数
```

`snapshot` 保留现有额度、实时状态、统计日和窗口元数据。`generated_at` 与 `snapshot.generated_at` 必须一致。`aggregation.models` 必须严格等于本机公开可见模型集合，不得包含隐藏模型。

每组“原始聚合计数”定义为：

```json
{
  "status": "available",
  "total_requests": 100,
  "successful_requests": 97,
  "failed_requests": 3,
  "total_duration_ms": 125000
}
```

`status` 取 `available | disabled | unavailable`。不可用或未启用时，数值全部为 `null`；可用但无请求时，数值全部为 `0`。必须满足 `total_requests = successful_requests + failed_requests`。

这些计数应在安全投影层显式构造，并与本轮公开快照保持相同可见模型和时间范围。不能将包含账号或请求明细的管理统计整体发送给公示进程后再删除敏感字段。

### 4.2 主控公开接口

保留 `GET /api/public/dashboard` 及现有公开字段，继续使用 `schema_version: 1`；以新增字段表示汇总覆盖范围，不改变原指标含义。角色为独立模式时允许省略这些扩展字段。

主控新增元数据：

```text
cluster:
  expected_nodes: 配置的 agent 数量加本机
  fresh_nodes: 具有有效且未过期快照的节点数量
  serving_nodes: fresh 节点中 service_status=ready 的数量
  status: complete | partial | unavailable
  oldest_source_at: 本次使用的最旧源快照生成时间
  newest_source_at: 本次使用的最新源快照生成时间
coverage:
  history: 本组统计覆盖情况
  realtime: 本组统计覆盖情况
  today: 本组统计覆盖情况
  quota: 本组统计覆盖情况
models[]:
  coverage:
    history / recent_stats.24h / recent_stats.1h / realtime / today / quota
```

每组覆盖情况包含 `status: complete | partial | unavailable`、`included_nodes` 和 `expected_nodes`；分模型的 `expected_nodes` 是已知提供该模型的节点数量。节点模型清单从最近一次有效快照获知；尚未取得快照的节点是否提供该模型未知，因此还必须结合顶层 `cluster.status` 提示完整性，不能声称全站完整。

`history.enabled` 保留原有“是否有启用的统计来源”含义，不能承担覆盖完整性的表达。`generated_at` 表示汇总生成时间，源数据新鲜程度由源时间和 `coverage` 共同表达。

公开响应只包含聚合覆盖数量和状态。不要公开 agent URL、Token、内部节点 ID、内部错误信息或服务器地址。第一版不公开逐节点数据列表。

## 5. 汇总规则

### 5.1 模型与可加指标

- 按完整模型标识合并，不自行合并别名。
- 模型集合取各节点本机公开模型集合的并集；一个节点隐藏某模型，不影响其他节点公开该模型。
- 节点未提供某模型时不计入该模型，不能推断为统计故障。
- 额度规则继续由各节点调度器计算，主控不复制配额估算规则。
- 本机与 agent 使用完全相同的汇总逻辑，本机不通过 agent 列表再次加入。

对口径一致、满足新鲜度条件的数据，直接相加：

- 预估剩余额度。
- 今日请求（实际发往上游的尝试次数，重试会重复计数）。
- 可用账号、429 账号、排队数、正在执行数、并发上限。
- 历史及近期的逻辑请求数、成功数、失败数、耗时总和。

各节点账号池独立是额度和账号数量可加的部署前提，本方案不通过公开账号标识检测账号池重复。

### 5.2 成功率和平均耗时

使用原始计数汇总后计算：

```text
成功率 = Σ successful_requests / Σ total_requests × 100%
平均耗时 = Σ total_duration_ms / Σ total_requests
```

成功率保留一位小数，平均耗时四舍五入到整数毫秒。请求数为零时，二者返回 `null`。

不能平均各节点成功率，也不能平均各节点平均耗时；不能用已取整的节点平均耗时反推总耗时。耗时包含成功、失败和中止请求，失败包含错误和用户中止，延续现有口径。

累计全局历史仍来自各节点的全局累计统计，可能包含隐藏模型的请求；不能用可见模型表格求和替代现有全局历史定义。

### 5.3 缺失值与部分可估算

- `null` 表示未知或不可用，不能当作 `0`。
- 只有全部相关来源可用时，覆盖状态才是 `complete`。
- 部分来源可用时可展示已知部分的和，覆盖状态为 `partial`，界面必须明确标注“已知部分”或“部分可估算”。
- 所有来源均不可用时返回 `null`，覆盖状态为 `unavailable`。
- 额度部分可估算时，`quota.estimable=false`、`estimated_remaining=null`；新增 `known_estimated_remaining` 保存已知部分的和，配合覆盖字段展示，避免旧前端误认为是完整额度。
- 分模型保留最近一次已知的模型清单用于离线提示；如果模型只存在于过期节点，仍显示该模型，但其当前额度与实时指标为 `null`。
- 所有节点历史统计均明确关闭时显示“请求统计未启用”；因离线或查询失败无法获得统计时显示“统计暂不可用”，不能混为一类。

### 5.4 时间口径

- “今日”继续按 `America/Los_Angeles` 自然日统计，与管理端及现有配额重置口径一致。
- 主控按同一时区取得当前统计日；统计日或时区不匹配的快照，不参与今日请求及额度汇总，但可独立参与满足条件的其他指标。
- 跨日无需等待下一次采集才失效，主控轻量定时检查应及时更新缓存。
- 近 1 小时、近 24 小时沿用 agent 定时生成快照时的滚动窗口，窗口边界会有少量偏差；第一版接受这种近实时近似，不宣称各节点使用严格一致的时间边界。
- 汇总窗口元数据标记 `alignment: approximate`，并提供参与来源的结束时间最小值与最大值；不要给出一组虚构的共同 `from/to`。现有前端需要兼容这种扩展。
- 后续若要求严格对齐，需要 agent 预生成统一时间桶；不能改成主控请求时现场查询。

## 6. 新鲜度、故障与去重

默认快照有效期为 20 秒，依据 agent 的 `generated_at` 判断，不以 HTTP 请求成功时间刷新有效期。

- 快照在有效期内、结构合法且身份匹配：可参与相应指标汇总。
- 单次请求失败但原快照仍在有效期内：继续使用原快照，并标记该节点最近采集失败，使整体状态为 `partial`。
- 超过有效期：从当前额度、实时、今日以及历史和近期汇总中排除；可保留旧快照用于已知模型集合和状态判断。
- HTTP 正常但 `service_status=unavailable`：历史和近期统计仍可在有效时参与；当前额度、可用账号及实时负载不参与可用容量汇总，覆盖状态明确不完整。
- 全局 `service_status` 只要存在 ready 的新鲜节点即可为 `ready`，整体是否完整另看 `cluster.status`；不得让一个节点恢复中导致整个站点被标为不可用。
- 主控重启后先等待首轮有效数据，不将磁盘中的旧结果伪装为实时数据；第一版不持久化汇总缓存。

历史汇总默认表示“当前有效来源的累计历史”，节点离线、删除、恢复或本地统计清空都可能使合计下降；界面说明这一点。第一版不承诺全站累计历史永久单调递增，不从每轮计数差值追加总数，以免重启或重试导致重复记账。

节点 ID 使用持久化 UUID，首次启动生成并保存在 `data/public-dashboard-node-id`；复制部署时不得复制此文件。Token 与节点 ID 的职责不同，节点 ID 不作为认证凭证。

主控配置应绑定预期节点 ID，并拒绝本机 ID、重复 ID 和相同规范化 URL；响应 ID 不匹配时拒收。多条配置不能使同一节点统计多次。

校验 agent 协议版本、时间格式、统计时区、模型唯一性、字段类型、非负安全整数及计数关系。禁止超出安全整数范围后静默产生错误结果；聚合溢出时将对应指标标为不可用。响应体读取时设置上限，建议 1 MiB；拒绝未知协议版本，失败按节点隔离。

允许正常的轻微时钟偏差；快照时间超过主控时间 5 秒时拒收，旧于有效期的数据不作为新数据。部署说明要求节点校时。

## 7. 配置设计

沿用 `PUBLIC_DASHBOARD_ENABLED`、`PUBLIC_DASHBOARD_HOST`、`PUBLIC_DASHBOARD_PORT`，新增配置建议如下，均重启生效：

| 配置 | 默认值 | 适用角色 | 含义 |
| --- | --- | --- | --- |
| `PUBLIC_DASHBOARD_ROLE` | `standalone` | 全部 | 独立、主控、agent |
| `PUBLIC_DASHBOARD_SNAPSHOT_INTERVAL_MS` | `5000` | master、agent | 本机快照生成周期 |
| `PUBLIC_DASHBOARD_AGENT_TOKEN` | 空 | agent | agent 查询凭证，启用 agent 时必填 |
| `PUBLIC_DASHBOARD_AGENTS` | `[]` | master | 节点配置 JSON 数组 |
| `PUBLIC_DASHBOARD_POLL_INTERVAL_MS` | `5000` | master | 后台采集周期 |
| `PUBLIC_DASHBOARD_FETCH_TIMEOUT_MS` | `2000` | master | 单节点查询超时 |
| `PUBLIC_DASHBOARD_STALE_AFTER_MS` | `20000` | master、agent | 快照有效期 |

节点列表格式示例：

```json
[
  {
    "nodeId": "预期-agent-节点-UUID",
    "name": "节点 A",
    "url": "https://agent-a.example.org",
    "token": "独立生成的查询凭证"
  }
]
```

`url` 为部署根地址，可以包含固定路径前缀；主控在其后追加固定的 `/api/agent/dashboard` 路径。拒绝 query、fragment、URL 用户名密码和非 HTTP(S) 协议。生产环境使用 HTTPS 或可信私网，不关闭 TLS 证书校验，不跟随重定向以免泄露 Token。

节点 URL 只允许由管理员配置，不允许公众通过请求参数指定。允许显式配置私网地址，以支持实际多机部署。

所有时间参数必须为合理范围内的正整数；有效期需大于快照周期与采集周期之和再加请求超时，以留出传输余量。对异常配置给出不含凭证的明确报错。

配置应接入现有统一配置服务，不能只新增环境变量解析而漏掉配置保存、重启应用和敏感字段处理。agent Token 和节点列表中的 Token 必须按 secret 处理：管理端只返回脱敏值，保存时可保留未修改凭证，日志与错误信息不得输出原始列表；不把凭证写入公示静态资源。角色、节点列表及关联参数在配置页面提供中文说明。

主控无 agent 配置是合法情况，退化为仅公示本机。独立模式保持现有更新行为，避免默认部署的刷新性能发生无意变化。

| `src/public/PublicDashboardServer.js` | 区分公开路由与受保护 agent 路由；HTTP 处理只读取缓存 |
| `src/utils/ConfigLoader.js`、`src/config/*` | 默认值、参数校验、统一配置、敏感字段脱敏及重启应用 |
| `ui-public/app/App.vue`、`styles.less`、`mockData.js` | 节点覆盖提示、部分数据和未知值展示、近期窗口近似提示及预览数据 |
| `.env.example`、部署文档、`README.md` | 补充三种角色、独立账号池前提、Token 配置和网络部署示例 |

保持现有公示进程隔离方式：应用进程持有账号池与数据库，公示子进程只接收安全聚合投影。主控网络采集和汇总放在公示子进程，避免远程节点故障阻塞 API 请求处理。

当前单机快照向子进程发布时有 256 KiB 限制。实现时需区分单机公开响应、agent 内部协议及主控汇总响应，分别设置明确上限，不能让新增聚合字段或模型并集无意撞到旧限制，也不能取消所有大小保护。

关闭与重启需要清理本机快照任务、采集任务、过期检查任务，取消在途 HTTP 请求并阻止关闭后的缓存写入。不要因为远程 agent 故障触发现有本机应用恢复机制。

## 9. 公示页面行为

- 独立模式保持现有布局。
- 主控模式顶部增加“数据有效节点 3 / 4”“可服务节点 2 / 4”等覆盖提示。
- 状态区分“数据完整”“部分节点或统计不可用”“暂无可用数据”。
- 预估额度始终保留原有免责声明；部分可估算时显示“已知部分约 X 次”，不能展示为完整全站额度。
- 未知值显示 `—`，真实零值显示 `0`。
- 历史和近期覆盖不完整时，在对应区域提示“仅包含当前可用统计来源”；不能只在页顶放一个易被忽略的警告。
- 近 1 小时和近 24 小时继续切换，提示统计来自各节点最近快照，窗口存在秒级偏差。
- 显示源数据时间范围，避免主控不断更新时间造成 agent 数据一直很新的错觉。
- 不显示服务器地址、Token、节点 ID、内部异常或管理入口。
- 前端只访问主控同源 `/api/public/dashboard`，不持有 agent 凭证，不直接连接 agent。
- 主控接口请求失败时沿用最后一次成功数据并明确提示过期，不显示成当前正常结果。

## 10. 实施顺序

1. 增加角色、节点配置及敏感字段处理，默认行为兼容原部署。
2. 扩展本机安全聚合投影，建立独立于查询请求的快照生成任务。
3. 实现 agent 认证接口及缓存读取，验证大量读取不触发快照生成。
4. 实现主控后台采集、身份校验、新鲜度判断和独立可测试的汇总逻辑。
5. 将汇总结果接入现有公开接口和前端，补充覆盖状态与未知值展示。
6. 更新部署说明与针对性测试，完成三种角色及两台以上 agent 的集成验证。

## 11. 验收标准

1. 不设置新配置时，原有独立公示模式和已有测试保持兼容。
2. 主控不配置 agent 时，正常展示本机；配置两个独立账号池的 agent 后，模型及各项统计按本方案汇总。
3. 固定时间内连续读取 agent 接口，不会增加快照生成次数、SQLite 查询次数或账号池扫描次数。
4. 固定时间内增加公示页请求量，不会增加主控到 agent 的请求次数；测试允许定时调度边界误差。
5. 主控与 agent 的定时任务不重入，慢查询及慢节点不会造成无限任务堆积。
6. 使用不同请求量的节点验证成功率与耗时的加权结果，并验证空数据、统计关闭、查询失败和部分可估算情况。
7. 验证超时、网络断开、`304`、无变化的旧快照和 agent 快照生成失败；旧时间不能因请求成功而刷新。
8. 验证应用恢复中的节点不贡献当前可用容量，但有效历史数据可继续参与；部分节点异常不导致整个公示接口失败。
9. 验证太平洋时间跨日、不同统计日、近期窗口偏差和过期节点模型保留。
10. 验证身份不匹配、同一节点重复配置、自引用、重定向、错误协议版本、异常计数和超大响应被隔离处理。
11. 未认证调用 agent 返回 `401`；agent 无匿名公示入口；公开 JSON、前端资源、日志及配置读取不泄露凭证和内部地址。
12. 节点重启、主控重启及配置切换后无残留任务；节点恢复后自动重新纳入汇总，历史请求不通过差值重复累计。

实施时增加有意义的快照生产/读取隔离测试、汇总单元测试和角色路由集成测试，并执行项目已有公示面板、隔离进程及统一配置相关测试。

## 12. 部署示例

### 12.1 Agent 服务器

各服务器独立部署本项目并分配互不重复的账号池。在 agent 的 `.env` 中配置：

```dotenv
PUBLIC_DASHBOARD_ENABLED=true
PUBLIC_DASHBOARD_ROLE=agent
PUBLIC_DASHBOARD_PORT=7861
PUBLIC_DASHBOARD_AGENT_TOKEN=替换为独立生成的随机凭证
```

Token 使用可打印 ASCII 字符，例如通过 `openssl rand -hex 32` 生成；不要直接使用以上中文占位值。首次启动后读取 `data/public-dashboard-node-id`，将其作为主控的预期节点 ID。保留此文件以保证重启后的身份不变，复制部署时不要复制此文件。

将该端口经 HTTPS 反向代理提供给主控，或者只在可信私网开放。代理需要转发 `Authorization` 请求头，不能缓存 `/api/agent/dashboard`。容器部署还需为公示端口添加端口映射，并持久化 `data` 目录。

Agent 不提供公示首页和匿名公示 API。可在本机验证：

```bash
curl -H "Authorization: Bearer YOUR_AGENT_TOKEN" http://127.0.0.1:7861/api/agent/dashboard
```

尚未生成首份快照时返回 `503`，认证失败返回 `401`，健康接口 `GET /healthz` 不需要 Token。

### 12.2 主控服务器

主控仍独立处理 API 请求，并纳入本机统计；本机不要再次写进 agent 列表。

```dotenv
PUBLIC_DASHBOARD_ENABLED=true
PUBLIC_DASHBOARD_ROLE=master
PUBLIC_DASHBOARD_PORT=7861
PUBLIC_DASHBOARD_AGENTS='[{"nodeId":"替换为节点A的实际ID","name":"节点 A","url":"https://agent-a.example.org","token":"REPLACE_WITH_AGENT_A_TOKEN"},{"nodeId":"替换为节点B的实际ID","name":"节点 B","url":"https://agent-b.example.org","token":"REPLACE_WITH_AGENT_B_TOKEN"}]'
```

节点 ID 必须替换为实际文件中的 UUID。访问主控公示端口的 `/` 查看汇总，`/api/public/dashboard` 提供公开 JSON。节点 URL 支持路径前缀，例如 `https://example.org/node-a` 会读取 `https://example.org/node-a/api/agent/dashboard`。

默认本机生成和主控采集均为 5 秒，查询超时 2 秒，快照 20 秒后过期；状态有效期每秒检查。修改周期时需同步调整有效期，端到端数据延迟包括生成、传输与采集等待。

也可在管理控制台的“多节点公示”分组配置角色、节点与凭证，保存后重启生效。已有节点不填写新 Token 时保留原凭证；新节点必须填写 Token。管理配置优先于环境配置，已在控制台保存的字段需通过控制台修改或恢复环境值。

### 12.3 已实现的接口补充

- 主控 `history.status` 区分 `available`、`disabled`、`unavailable`，用于区分统计关闭与数据缺失。
- 近期窗口提供 `alignment: approximate`、`source_to_min`、`source_to_max`，不提供虚构的统一窗口边界。
- 未知节点尚无模型清单时，已知模型的覆盖状态同样降级，不把已知额度表示成完整全站额度。
- 原始耗时总和在投影边界统一四舍五入为整数毫秒，再按请求量加权；不通过已取整的平均耗时反推。
- 单节点 agent 协议和主控公开 JSON 各设 1 MiB 上限；原有单机 IPC 快照保持 256 KiB 上限。
