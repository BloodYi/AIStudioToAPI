# 公示面板分模型统计时间范围切换方案

本文用于后续实施，描述拟议接口和行为；当前代码尚未实现这些改动。本文补充 [公示面板设计](./public-dashboard-design.md) 中的“分模型历史统计”部分。

## 1. 改造目标与范围

累计成功率受早期数据影响，不能及时反映近期服务表现。将公示面板底部的“分模型历史统计”改为“分模型统计”，支持以下范围：

| 切换项     | 接口标识 | 含义                     |
| ---------- | -------- | ------------------------ |
| 历史       | `all`    | 现有累计历史数据         |
| 近 24 小时 | `24h`    | 当前快照时间向前 24 小时 |
| 近 1 小时  | `1h`     | 当前快照时间向前 1 小时  |

默认选择“近 24 小时”。三个范围均展示模型、请求数、成功率、失败请求数和平均耗时。

切换只影响底部分模型表格。顶部全局概览继续展示累计历史，模型额度卡片继续展示今日请求和实时状态。

## 2. 当前实现与可复用能力

| 文件                                   | 当前职责                              | 拟议改动                                 |
| -------------------------------------- | ------------------------------------- | ---------------------------------------- |
| `src/core/UsageStatsWorker.js`         | SQLite 写入、累计聚合、明细查询与清理 | 新增按完成时间聚合的 worker 命令         |
| `src/core/UsageStatsStorage.js`        | worker 异步通信                       | 复用 `call()`，通常无需修改              |
| `src/core/UsageStatsService.js`        | 使用统计及公开白名单投影              | 新增异步近期分模型统计方法               |
| `src/public/PublicDashboardService.js` | 公开 DTO、快照缓存                    | 扩展时间范围数据，支持异步查询及缓存合并 |
| `src/public/PublicDashboardServer.js`  | 独立只读公开接口                      | 路由等待异步快照，保留现有响应与错误处理 |
| `ui-public/app/App.vue`                | 公示面板渲染与轮询                    | 新增范围选择、表格数据映射和状态提示     |
| `ui-public/app/styles.less`            | 公示面板样式                          | 新增切换控件与窄屏布局                   |

现有 `GET /api/public/dashboard` 只提供累计历史数据，因此需要扩展后端响应。现有 `requests` 表已经保存 `model`、`finished_at_ms`、`outcome` 和 `duration_ms`，并有 `idx_requests_finished(finished_at_ms, id)` 索引，不需要新增数据字段或修改请求采集流程。

累计历史来自 `usage_totals` 及内存中的累计聚合；近期数据应来自 SQLite 中的请求明细。不能用有限长度的内存 `records` 列表或浏览器收到的累计数推算近期统计。

## 3. 统计口径

### 3.1 时间范围

后端在构建快照时捕获统一时间 `asOfMs`，两个近期范围共用这个时间：

- 近 24 小时：`[asOfMs - 86400000, asOfMs)`。
- 近 1 小时：`[asOfMs - 3600000, asOfMs)`。
- 以请求完成时间 `finished_at_ms` 判断归属；不纳入仍在执行的请求。
- 下界包含、上界不包含；未来时间的记录不纳入。
- 使用绝对毫秒时间计算，接口时间以 UTC ISO 8601 返回。近期范围不受太平洋时区或夏令时影响。
- “近 24 小时”与额度卡片的“今日”是两种不同口径，不能共用每日统计结果。

### 3.2 指标计算

| 指标       | 计算方式                                                         |
| ---------- | ---------------------------------------------------------------- |
| 请求数     | 范围内已完成逻辑请求的数量                                       |
| 成功率     | `success` 数量 / 请求数 × 100，保留一位小数                      |
| 失败请求数 | `error` 数量 + `aborted` 数量                                    |
| 平均耗时   | 范围内全部请求的 `duration_ms` 总和 / 请求数，四舍五入到整数毫秒 |

保持现有历史统计口径：重试后最终成功算一个成功逻辑请求；平均耗时包含失败和中止请求，并沿用现有请求耗时定义，不改为上游单次响应耗时。

近期统计反映用户请求的最终结果，不能解释为每次上游尝试的健康度。用户中止也会影响成功率。第一版不增加逐次重试、错误类型或账号维度统计。

### 3.3 空数据、禁用与查询失败

- 统计可用但范围内无请求：请求数、失败数为 `0`，成功率和平均耗时为 `null`，页面显示 `—`。
- 使用统计关闭：状态为 `disabled`，所有统计值为 `null`，页面提示“请求统计未启用”。
- 近期查询失败：状态为 `unavailable`，所有该范围统计值为 `null`，页面提示“近期统计暂时不可用”；不伪造为零，也不回退到历史数冒充近期数据。
- 模型行始终来自调度器当前公开的可见模型集合。无请求的可见模型仍保留；隐藏模型、空模型及不在可见集合中的模型不进入表格。

## 4. 接口设计

### 4.1 一次返回全部范围

继续使用 `GET /api/public/dashboard`，不增加查询参数或新端点。一次响应返回两个近期范围，前端切换时直接读取本次快照。

保留现有顶层 `history` 和 `models[].history` 的结构、含义，历史范围直接使用 `models[].history`。在顶层增加 `model_stat_windows` 元数据，在各模型中增加 `recent_stats`。

这是对现有版本 1 响应的增量扩展，建议保持 `schema_version: 1`；如项目约定任何字段扩展都需升级版本，再同步调整版本契约及测试。旧客户端可继续读取原字段。

以下为新增字段示例，非完整响应：

```json
{
  "model_stat_windows": {
    "24h": {
      "status": "available",
      "from": "2026-10-04T08:00:00.000Z",
      "to": "2026-10-05T08:00:00.000Z"
    },
    "1h": {
      "status": "available",
      "from": "2026-10-05T07:00:00.000Z",
      "to": "2026-10-05T08:00:00.000Z"
    }
  },
  "models": [
    {
      "model": "gemini-flash",
      "recent_stats": {
        "24h": {
          "total_requests": 100,
          "success_rate": 95.0,
          "failed_requests": 5,
          "average_duration_ms": 12000
        },
        "1h": {
          "total_requests": 10,
          "success_rate": 90.0,
          "failed_requests": 1,
          "average_duration_ms": 15000
        }
      }
    }
  ]
}
```

`status` 只允许 `available`、`disabled`、`unavailable`。同一范围对所有模型使用同一组边界和可用状态；`from` 与 `to` 表示查询范围，不承诺期间持续有流量或部署前已有数据。

公开投影仅输出模型名、聚合值、范围与状态，不返回请求明细、账号标识、客户端 IP、错误原文或数据库信息。数字校验与现有公开 DTO 保持一致。

### 4.2 缓存、并发与降级

- 复用现有服务快照缓存，保留 HTTP ETag、304、短期 Cache-Control 和响应大小限制。
- 将 `getSnapshot()` 改为异步，并同步修改路由及相关测试调用方。
- 缓存过期时，多个请求共享同一个正在构建的 Promise，避免并发重复扫描 SQLite；失败后必须释放该 Promise，以便下次重试。
- 同一快照的 `generated_at` 与近期范围的 `to` 使用统一 `asOfMs`。缓存命中时原样返回快照，不能只推进时间标签而保留旧聚合值。
- 模型可见集合发生变化时失效旧缓存，包含待完成的构建结果，避免继续返回已隐藏模型。
- 近期查询失败时仍可返回有效历史和实时数据，近期范围标为 `unavailable`；整个公开快照无法构建时才沿用现有 503 行为。
- 不额外引入长期近期数据缓存，避免窗口离开后的请求长时间留在结果中。

## 5. 后端聚合实现

### 5.1 SQLite worker

建议新增命令 `public_model_windows`，接收后端生成的可见模型集合与 `asOfMs`，一次扫描近 24 小时明细，同时聚合 24 小时与 1 小时数据。

SQL 思路：

```sql
SELECT
    model,
    COUNT(*) AS total_24h,
    SUM(CASE WHEN outcome = 'success' THEN 1 ELSE 0 END) AS success_24h,
    SUM(CASE WHEN outcome IN ('error', 'aborted') THEN 1 ELSE 0 END) AS failed_24h,
    SUM(duration_ms) AS duration_24h,
    SUM(CASE WHEN finished_at_ms >= ? THEN 1 ELSE 0 END) AS total_1h,
    SUM(CASE WHEN finished_at_ms >= ? AND outcome = 'success' THEN 1 ELSE 0 END) AS success_1h,
    SUM(CASE WHEN finished_at_ms >= ? AND outcome IN ('error', 'aborted') THEN 1 ELSE 0 END) AS failed_1h,
    SUM(CASE WHEN finished_at_ms >= ? THEN duration_ms ELSE 0 END) AS duration_1h
FROM requests
WHERE finished_at_ms >= ? AND finished_at_ms < ?
  AND model IN (/* 根据可见模型数生成绑定占位符 */)
GROUP BY model;
```

四个条件聚合参数均绑定 1 小时下界，WHERE 参数绑定 24 小时下界、上界和可见模型名。参数必须绑定，不能直接拼接模型值。可见模型集合为空时直接返回空结果。

SQL 返回计数和耗时总和，由服务层统一转换公开指标并补齐无数据模型。查询应等待统计初始化完成，并遵守现有写入队列的顺序，避免读取尚未入库的已完成请求。

### 5.2 数据保留与性能

- 明细默认保留 30 天，足以覆盖两个近期范围；累计聚合在明细清理后仍保留，因此历史统计继续使用累计数据源。
- 改造不改变数据保留配置。需核实允许的保留天数满足 24 小时范围；如未来允许更短保留期，应显式标记统计覆盖不足，不能宣称为完整 24 小时统计。
- 新部署、迁移或缺失明细时，只能统计已保存记录，不能由累计总数恢复不存在的明细。
- 重启后近期统计从 SQLite 重新查询，不能只统计本次进程运行期间。
- 先复用现有时间索引，通过 `EXPLAIN QUERY PLAN` 和代表性数据测量查询耗时。只有实测需要时再评估新增复合索引，避免无依据增加写入成本。
- 聚合在 worker 内执行，不阻塞主线程；大量公开请求通过快照缓存及进行中 Promise 合并查询。

## 6. 前端交互

1. 标题为“分模型统计”，标题旁提供“历史 / 近 24 小时 / 近 1 小时”按钮组。
2. 默认选择近 24 小时，刷新数据时保持当前选择，不自动跳回默认值。
3. 历史时请求列表头为“历史请求”；近期时为“请求数”。其余列不变。
4. 历史选择读取 `model.history`，近期选择读取 `model.recent_stats[range]`。
5. 保持现有轮询、后台页面降低刷新频率、手动刷新机制。切换本身无需发起请求。
6. 按钮支持键盘操作、明确焦点样式与 `aria-pressed`；窄屏允许换行，不挤压表格布局。
7. 表格下说明：“近期统计按请求完成时间滚动计算；失败数包含用户中止，重试后成功按成功请求计。”
8. 近期范围为 `unavailable` 时显示独立提示，并让页面状态提示反映“部分统计不可用”。
9. 整体请求失败时沿用上次快照，同时明确“显示上次结果”；保留原更新时间，不把旧窗口标为当前最新数据。
10. 兼容旧后端：缺少新增字段时仍提供历史数据，禁用两个近期选项并提示“当前服务暂不支持近期统计”，不得用历史数据填充近期列。

开发 Mock 应包括近期恢复、近期恶化、零请求、统计关闭、近期查询不可用、旧接口响应等情形，以验证三个范围确实读取不同数据。

## 7. 实施步骤

1. 在 worker 中新增只读聚合命令，验证两个时间范围的边界与结果。
2. 在 UsageStatsService 中增加异步公开近期统计方法，处理初始化、写入顺序、补零及白名单投影。
3. 扩展 PublicDashboardService 的 DTO、异步快照和缓存并发控制，更新公开路由。
4. 完成前端选择控件、数据映射、降级提示和 Mock 数据。
5. 更新测试和原公示面板设计文档，运行相关检查。
6. 部署时重新构建公开前端并重启服务；旧客户端依然可读原有字段。

## 8. 验收与测试

后端测试优先扩展 `tests/sqlite-storage.test.js` 与 `tests/public-dashboard.test.js`，至少覆盖：

- 固定 `asOfMs`，混合两个范围内外的记录，验证两个范围的请求数、成功率、失败数和平均耗时。
- 恰好在下界、恰好在上界与未来的记录，验证包含下界、排除上界与未来记录。
- 成功、错误和用户中止，验证失败合并及平均耗时分母。
- 长请求跨越范围：按完成时间纳入；未完成请求不计入。
- 无数据的可见模型补齐零值与 `null`；隐藏模型和敏感信息不出现在响应。
- 统计关闭、查询失败及恢复，验证不同状态和不伪造数据。
- 重启后近期结果仍正确；清理旧明细不改变历史累计结果。
- 缓存命中、过期、并发查询合并、构建失败后重试及隐藏模型变化。
- 公开路由异步响应、ETag/304、原字段兼容与完整快照失败时的 503。

前端验证三个范围的数据映射、刷新保留选择、旧后端兼容、不可用提示、键盘操作和移动端布局。按仓库已有测试方式验证功能，避免只断言源码中存在按钮文字。

完成标准：三个范围可以切换且指标符合上述口径；默认近 24 小时；顶部概览与额度实时卡片行为保持原定义；隐藏模型及私有数据不泄露；重启和刷新后数据正确；无数据与不可用状态能明确区分。
