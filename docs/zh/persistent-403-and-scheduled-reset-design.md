# 长期 403 标识与太平洋时间定时重置改造方案

## 1. 背景

当前模型感知调度器会把上游 HTTP 403 归类为 `risk_controlled`，在账号 × 模型槽位上执行带抖动的 1、3、6、18 倍退避，并受 `RISK_CONTROL_MAX_COOLDOWN` 限制。这个机制适合一段时间后可自行恢复的短期 403。

实际运营中还存在另一类 403：账号 cookie 可能已经被长期标记，等待退避结束后仍会继续返回 403，通常只能删除认证信息并重新登录。现在两类 403 共用 `RISK_CONTROLLED` 展示，管理员无法快速区分需要重新登录的账号。

同时，Build 配额按 `America/Los_Angeles` 的 00:00 重置。当前只能依赖固定时长冷却，或由管理员每天手动恢复账号。固定时长冷却仍有价值，但还应允许系统在指定的太平洋时间主动清理可恢复的调度限制。

## 2. 改造目标

本次改造包含两项彼此独立的能力：

1. 记录账号“持续只得到 403”的起始时间。持续时间达到 48 小时后，在管理前端增加醒目的长期 403 标识，辅助管理员判断该账号是否需要重新登录。
2. 增加每日定时重置，可配置是否启用以及太平洋时区的执行时间。默认启用，默认每天太平洋时间 00:00 执行。

必须满足以下约束：

- 长期 403 标识只用于管理端显示，不参与候选账号过滤、租约分配、重试、冷却、浏览器 context 生命周期或账号健康判断。
- 被长期标识的账号仍可正常接受 probe 和后续调用；现有 403 退避逻辑保持不变。
- 单模型恢复、账号恢复、全部账号恢复、429 重置、定时重置以及服务重启都不能清除长期 403 计时。
- 只有该账号的一次真实上游成功，或一次能够确认状态并非 403 的上游错误，才能清除计时和标识。
- 原有按时长计算的 403、429 和临时错误冷却继续生效；定时重置与冷却到期是并行的两条恢复路径，任一先发生即可让账号重新参与调度。

## 3. 不在本次范围内

- 不自动删除 auth 文件，不自动重新登录，也不自动判定 cookie 已永久失效。
- 不因为长期 403 标识而禁用账号或模型。
- 不改变 403 的错误分类、退避倍率、重试次数和跨账号切换策略。
- 不向匿名公益站看板暴露账号级长期 403 信息。
- 不把定时重置扩展为认证修复、浏览器重启或 context 强制重建。
- 不让定时任务恢复管理员手动禁用的账号，也不清除模型 `unsupported` 状态或账号 `unhealthy` 状态。

## 4. 长期 403 的状态模型

### 4.1 账号级字段

在 `ModelScheduler` 的账号对象上新增持久化字段：

```json
{
  "continuous_403_since": 1789430400000
}
```

字段语义：

- `null`：账号当前不处于“持续只得到 403”的观察窗口。
- Unix 毫秒时间戳：本轮连续 403 窗口中第一次收到真实上游 403 的时间。

不建议持久化一个可被任意按钮修改的布尔值。前端标识应由下面的条件派生：

```text
persistent_403 = continuous_403_since != null
                 && now - continuous_403_since >= 48 hours
```

这样可以保留准确的起始时间，也能避免布尔标识与计时字段不一致。48 小时使用固定的 `172800000` 毫秒，不按两个自然日计算，因此不受夏令时切换影响。

字段放在账号层而不是账号 × 模型槽位层。只要同一账号跨任意模型的可确认调用结果一直都是 403，就视为同一个连续窗口；任意模型出现一次非 403 结果，均可证明该账号并非“持续只得到 403”，应清零。

### 4.2 状态迁移规则

| 事件 | `continuous_403_since` 的变化 |
| --- | --- |
| 第一次真实上游 403 | 若为空，写入当前时间 |
| 后续真实上游 403 | 保持原时间，不向后顺延 |
| 真实上游成功 | 清为 `null` |
| 能确认 HTTP 状态不是 403 的上游错误，包括 4xx、429、5xx | 清为 `null` |
| 客户端主动取消 | 不变 |
| page、context、WebSocket、MessageQueue 等本地传输错误 | 不变，因为未得到可用于判断 cookie 状态的上游结果 |
| 排队超时、无可用账号、context 初始化失败 | 不变 |
| 任何管理端恢复/重置按钮 | 不变 |
| 每日定时重置 | 不变 |
| 冷却自然到期 | 不变 |
| 服务重启 | 从持久化状态恢复 |

这里将“非 403 报错”限定为能够确认上游响应不是 403 的错误。未知状态的本地故障既不能证明 cookie 正常，也不能证明 cookie 异常，因此不应打断连续观察窗口。

### 4.3 与现有槽位状态的关系

现有 `risk_control_failures`、`last_error_kind`、`last_http_status` 和 `cooldown_until` 继续保留在账号 × 模型槽位中，用于实际调度和当前 403 状态展示。新增字段只描述账号级的长期历史窗口，两者不能互相替代：

- 当前槽位可能已过冷却或被手动恢复，但账号仍带有长期 403 标识。
- 账号可能刚收到第一个 403，当前显示为 `RISK_CONTROLLED`，但尚未达到长期标识阈值。
- 达到 48 小时不会修改 `healthy`、`disabled`、`unsupported` 或 `cooldown_until`。

## 5. 后端改造

### 5.1 `ModelScheduler` 写入点

在 `failure(lease, error)` 完成错误分类后处理账号级计时：

1. `kind === "risk_controlled"` 时，仅在 `account.continuous_403_since == null` 时写入 `Date.now()`。
2. 对具有明确非 403 上游结果的其他错误，将该字段清为 `null`。
3. `aborted`、`transport` 和本地调度错误不修改字段。

在 `release(lease, true)` 确认一次已开始、未记录失败的成功调用时，将字段清为 `null`。

为避免未来新增恢复入口误清状态，建议把清零集中到一个语义明确的私有方法，例如 `_recordAccountObservedResult(account, status)`；`reset()`、`resetAllAccounts()` 和每日重置不得调用它。所有字段变化继续使用现有 `saveSoon()` 合并持久化。

### 5.2 快照字段

管理接口的账号概要和账号详情均增加：

```json
{
  "continuous_403_since": 1789430400000,
  "continuous_403_duration_ms": 172900000,
  "persistent_403": true
}
```

其中 duration 使用 `Math.max(0, now - since)`，避免系统时钟回拨后出现负值。`persistent_403` 和 duration 均为响应时派生值，不写回状态文件。

`accountsOverviewSnapshot().summary` 增加独立计数：

```json
{
  "persistent_403": 3
}
```

这个计数不取代现有 `risk_controlled`，同一个账号可以同时计入两者。账号主状态的优先级仍保持 `disabled → risk_controlled → rate_limited → healthy/unhealthy`，防止新增展示信号改变现有筛选和状态语义。

涉及接口：

- `GET /api/scheduler/accounts`
- `GET /api/scheduler/accounts?ids=...`
- `GET /api/dashboard/realtime` 中的 `scheduler.accounts_summary`
- 兼容快照 `GET /api/scheduler`

匿名公开看板 `publicSummarySnapshot()` 不增加该字段。

### 5.3 持久化升级

将 `scheduler-state.json` 版本从 6 升到 7：

- 版本 1～6 仍可读取；缺失的 `continuous_403_since` 初始化为 `null`。
- 版本 7 校验该字段只能为 `null` 或非负有限整数时间戳。
- 不尝试依据旧版 `last_error_kind` 反推开始时间。旧状态没有可靠的首次 403 时间，升级时从下一次真实 403 开始计时，避免误报。
- 正常停机继续由 `scheduler.close()` flush；损坏状态的备份策略保持不变。

## 6. 每日定时重置

### 6.1 配置项

在 `SchedulerConfig` 和 `.env.example` 增加：

```dotenv
# 每天按 America/Los_Angeles 时区清理可自动恢复的调度冷却。
SCHEDULER_DAILY_RESET_ENABLED=true
SCHEDULER_DAILY_RESET_TIME=00:00
```

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `SCHEDULER_DAILY_RESET_ENABLED` | `true` | 仅字符串 `false` 表示关闭，与现有布尔环境变量风格一致 |
| `SCHEDULER_DAILY_RESET_TIME` | `00:00` | `America/Los_Angeles` 时区的每日执行时间，严格使用 24 小时制 `HH:mm` |

启动时严格校验小时 `00..23` 和分钟 `00..59`，非法值应使配置加载失败并指出变量名，不能静默回退。时区固定为 `America/Los_Angeles`，不跟随容器 `TZ`，也不新增第三个时区配置项。

该功能仅在模型感知调度模式启用；`ACCOUNT_ROTATION_STRATEGY=legacy` 下不创建定时任务。

### 6.2 自动重置的范围

新增独立方法 `resetDailyCooldowns()`，不要直接复用 `resetAllAccounts()`。每日任务遍历所有当前轮换账号的模型槽位，清除可由配额日界线或重试重新探测的运行状态：

```text
cooldown_until = 0
rate_limited = false
risk_control_failures = 0
consecutive_failures = 0
last_error = null
last_error_kind = null
last_http_status = null
```

但必须保留：

- `account.disabled`、`disabled_at`、`disabled_reason`，防止自动解禁管理员主动停用的账号；
- `account.healthy` 与账号级认证错误，避免把过期 cookie 伪装成健康账号；
- `slot.unsupported`，模型权限不会因每日配额重置而改变；
- 所有累计和当日请求/失败统计；当日统计仍由现有太平洋日期 rollover 独立处理；
- `account.continuous_403_since`，确保定时重置不能清除长期 403 标识；
- 当前活动 lease 和 inflight 计数。

清理完成后立即 `flush()`、`drain()`，并记录结构化日志，包括太平洋日期、配置时间、受影响账号数和槽位数。任务在有请求执行时也可运行：Node 单线程内的状态修改是同步的，已取得的 lease 不被中断；重置后到达的错误可以重新写入冷却状态。

手动的“一键启用所有账号”保持原语义，但同样不得改动 `continuous_403_since`。这样自动任务和管理动作边界清晰，也避免每日自动恢复手动禁用或明确不支持的资源。

### 6.3 定时器实现

建议由 `ModelScheduler` 管理定时任务，因为状态修改、持久化和关闭生命周期都在该类中：

1. 构造完成并加载状态后，若配置启用，计算下一次 `America/Los_Angeles` 指定 `HH:mm` 对应的绝对时间。
2. 使用一次性 `setTimeout`，触发后执行 `resetDailyCooldowns()`，再重新计算下一次时间；不要使用固定 24 小时 `setInterval`。
3. 每次都按 IANA 时区重新换算，以正确处理太平洋夏令时的 23/25 小时自然日。
4. `close()` 中清除 timer，防止停机期间再次执行，并保持现有最终 flush。
5. timer 调用 `unref()`，不阻止进程正常退出。

`00:00` 在太平洋时区不存在夏令时重叠问题。若用户配置到夏令时切换附近的时间，实现仍应定义稳定行为：不存在的本地时刻执行于该日第一个不早于配置值的有效时刻；重复的本地时刻只执行一次。可通过“上次执行的太平洋日期”做进程内幂等保护。

### 6.4 重启与错过任务

默认不补跑停机期间错过的定时重置。服务启动时只计划下一次未来触发时间，原因是状态文件没有记录服务停机期间上游是否已经重置，盲目补跑可能提前解除仍有效的短期冷却。

如果服务恰好在配置时刻启动，也按下一次计算结果执行一次，并通过太平洋日期幂等键确保同一进程同一自然日最多执行一次。多实例仍不得共享同一个 `scheduler-state.json` 或同一账号池；本功能不提供分布式锁。

## 7. 前端展示

### 7.1 独立的覆盖标识

在 `SchedulerStatus.vue` 的账号卡片标题区增加独立警示徽标，例如：

```text
疑似 Cookie 长期 403 · 已持续 2天4小时
```

该徽标是覆盖信息，不替换当前的“健康 / 403 风控 / 429 / 禁用 / 异常”主状态。即使定时重置刚刚清除了当前冷却、账号主状态暂时变为健康，长期 403 徽标仍然显示，直到后端因真实非 403 结果清零。

建议使用与当前紫色 403 风控不同的高对比警示色和图标，并提供 tooltip：

```text
该账号已连续至少 48 小时未观察到非 403 上游结果，可能需要删除认证并重新登录。
此标识不会禁用账号，恢复按钮和定时重置也不会清除它。
```

持续时长由服务端时间戳计算并格式化为天/小时；无需显示秒。中英文文案必须同时加入 `ui/locales/zh.json` 和 `ui/locales/en.json`。

### 7.2 汇总与筛选

在账号区域汇总 pill 和筛选栏增加“长期 403”数量及筛选项。该筛选是独立条件：

- “403 风控”继续筛选当前有 `RISK_CONTROLLED` 槽位的账号；
- “长期 403”筛选 `persistent_403 === true` 的账号；
- 同一账号可以出现在两个筛选结果中；
- 搜索框与现有筛选的组合逻辑保持不变。

不要把长期 403 塞入 `getAccountState()`，否则会破坏当前互斥主状态、边框颜色和汇总计数。

### 7.3 时间越过阈值

管理页每 5 秒轮询，接口响应中的派生布尔值会在越过 48 小时时发生变化，响应体 ETag 也会随之变化，因此无需单独的前端长定时器。展开账号详情时同样从详情接口读取该字段。

## 8. 兼容性与安全性

- 两个新环境变量有默认值，旧部署无需修改配置即可启用太平洋时间 00:00 重置；不希望自动重置的部署应显式设置 `SCHEDULER_DAILY_RESET_ENABLED=false`。
- 状态文件向前兼容版本 1～6。升级后写出的版本 7 不承诺可被旧程序读取，回滚前应备份 `data/scheduler-state.json`。
- 账号时间字段和特殊标识只通过已有登录保护的管理接口返回，不进入匿名公开接口和日志正文中的账号凭据。
- 系统时钟是持续时间判断与任务调度的依据。时钟大幅回拨时 duration 钳制到 0；时钟前跳可能提前显示标识或触发任务，部署环境应保持 NTP 正常。
- 定时重置是可用性操作，不修改 auth 文件，不能替代重新登录。

## 10. 测试方案

### 10.1 长期 403 单元测试

- 第一次 403 设置起始时间，后续不同模型的 403 不顺延。
- 48 小时前 `persistent_403=false`，达到边界时为 `true`。
- 任意模型成功清零。
- 明确 429、400、500 等非 403 上游错误清零。
- abort、本地 transport、排队失败和冷却自然到期不清零。
- 单模型恢复、账号恢复、全部恢复、429 重置和每日重置均不清零。
- 长期标识不改变 `eligibleAccounts()`、`canLease()` 和 `_slotStatus()` 结果。
- 版本 6 文件升级后字段为 `null`；版本 7 重启后保留时间戳；非法字段触发既有损坏状态保护。
- 账号 auth 编号变化时，计时跟随现有稳定账号 key/email，而不是跟随旧 index。

### 10.2 定时重置单元测试

- 两个配置的默认值、关闭值和非法时间校验。
- 到达配置时间只执行一次，并计划下一自然日。
- 太平洋标准时和夏令时日期均在正确的本地 `HH:mm` 触发。
- 自动重置解除 403、429、temporary 冷却并唤醒排队，但保留手动禁用、unhealthy、unsupported、统计和长期 403 时间。
- 与活动 lease 并存时不中断请求；定时重置后返回的新错误能重新建立冷却。
- `close()` 清理 timer；启动不补跑历史任务。

为使测试确定，时间相关实现应支持注入 `now()` 和 timer/调度函数，或至少把“计算下一次太平洋执行时间”提取为无副作用函数，避免测试依赖真实等待和宿主机时区。

### 10.3 前端与回归验收

- 账号刚发生 403 时只显示现有风控状态，模拟超过 48 小时后出现长期标识。
- 点击所有现有恢复按钮后标识仍在；模拟一次成功或非 403 上游响应后标识消失。
- 长期 403 筛选、账号搜索、展开详情和中英文切换正常。
- 被标识账号在冷却结束或定时重置后仍能获得租约。
- 验证命令：

```bash
npm test
npm run lint
npm run build:ui
```

## 11. 推荐实施顺序

1. 先实现账号字段、状态迁移规则、持久化版本 7 和单元测试。
2. 再扩展管理快照及前端徽标/筛选，确认标识完全不进入调度判断。
3. 实现每日重置的纯状态方法并验证它与各类手动恢复的边界。
4. 最后接入太平洋时区定时器、配置说明和停机清理，并进行夏令时测试。

完成后的核心行为可以概括为：**403 退避负责短期自动恢复，48 小时标识负责提示人工重新登录，每日太平洋时间重置负责贴合 Build 配额日界线；三者互不替代，也互不误清状态。**
