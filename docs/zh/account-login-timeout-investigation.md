# 自动登录超时排查与修复方案

排查日期：2026-10-02。代码基线：`6c11be4`。

本次只排查并形成方案，没有修改业务代码、测试代码或登录配置，没有尝试真实账号登录。依据为用户提供的六张截图、当前代码、现有回归及本地拦截页面的 Firefox 实验。未取得截图对应生产任务的异常栈、操作轨迹或 DOM，因此下文区分已确认的代码问题与生产故障推断。

## 1. 结论

1. **代码已经支持直接进入 Authenticator 验证码页，不要求先经过通行密钥或验证方式选择页。** 本地浏览器模拟“邮箱 → 密码 → 直接验证码”时，默认交互节奏和快速填充两种模式均成功。不能直接得出“漏写直接验证码分支”的结论。
2. **TOTP 分支存在状态识别过宽、操作期间页面变化缺少复核、返回方式选择页后状态难以恢复等问题。** 用户截图中的失败记录停在 `totp`，最终截图却是方式选择页。这说明失败时的页面与最后记录的操作阶段不同；优先排查页面切换期间仍操作旧输入框/旧按钮的情形。现有记录不足以确认具体是输入框点击、下一步点击，还是其他 UI 操作。
3. **首登协议处理存在可复现的 DOM 消失竞态。** 协议点击成功后，弹窗可能在 `isVisible()` 与 `innerText()` 之间消失。读取旧弹窗会等待到超时，最终成为 `ui_operation_timeout`。这与“截图已经进入 AI Studio、授权完成，重试成功”的现象吻合，但尚不能证明生产中的该次超时一定发生在这条语句。
4. **`ui_operation_timeout` 是多种未分类 UI 超时的兜底名称，不等于登录失败，也不等于总尝试期限耗尽。** 其中包括点击前的 `boundingBox()` 超时。现有错误分类和阶段粒度不足，容易让不同故障看起来是同一个问题。
5. **AI Studio 就绪判定还依赖编辑器输入框。** 截图中的模型升级页可能已登录却没有编辑器，这应与身份验证结果分开处理。单独缺少编辑器通常会触发 `page_transition_timeout`，不能直接用它解释截图中的 `ui_operation_timeout`。

建议优先修复首登弹窗竞态、补齐操作诊断，再收紧 TOTP 页面分类并为下一步操作增加后置状态复核。单纯加长超时或增加登录重试次数不能消除这些问题。

## 2. 当前登录链路与错误含义

截图来自账号管理页的任务历史，对应后台执行器 `src/accounts/AccountLoginWorker.js`，不是 `scripts/auth/saveAuth.js` 的 CLI 登录流程。应优先修改后台执行器及其页面处理模块。

当前链路：

```text
Google 登录：邮箱 → 密码/挑战 → Authenticator 验证码
AI Studio：首次协议处理 → 页面就绪 → 邮箱身份核验
目标应用：初始化 → 原生连接核验
最终会话：重新检查 AI Studio 协议与身份 → storage_state → 提交会话
```

Google 登录完成、AI Studio 首页出现、协议消失，都只是中间结果；完整成功还要求后续服务验证和会话提交通过。

| 错误                      | 当前来源                                                            | 含义                                                                 |
| ------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `ui_click_timeout`        | `LoginInteraction.click()` 内 `locator.click()` 抛出 `TimeoutError` | 点击操作没有在期限内完成，可能是目标消失、遮挡、不稳定或后续页面变化 |
| `ui_operation_timeout`    | Worker 捕获未带 `reason` 的 `TimeoutError` 或含 timeout 的异常      | 兜底分类，可能是元素定位、文本读取、点击前取尺寸、按键或导航超时     |
| `page_transition_timeout` | `waitForPage()` 或 TOTP 提交后的等待                                | 页面未在步骤期限内进入预期状态                                       |
| `attempt_timeout`         | Worker 总期限或队列监督期限                                         | 单次执行的整体预算耗尽                                               |

默认配置为步骤 30 秒、单次尝试 180 秒、最多 3 次尝试，来自 `src/accounts/AccountConfig.js`。实际部署可能覆盖这些值。队列第一次失败后等待约 30 秒，第二次失败后等待约 120 秒，另有小幅随机延迟。

用户 TOTP 历史三个结束时间之间约为 82 秒、175 秒；这与重试间隔叠加执行时间相容。任务显示的 307 秒是多次尝试及等待的总耗时，不能据此推断某个点击连续等待了 307 秒。

任务历史的 `phase` 是最后收到的阶段名，截图是在异常之后另行采集；它们都不是逐操作轨迹。`totp` 只表明曾进入验证码处理块，不证明验证码已成功输入或提交；`aistudio_terms` 也不证明失败时协议弹窗仍在。

## 3. 问题一：直接验证码页超时

### 3.1 已确认：直接验证码分支存在

`AccountLoginWorker.js:78` 的 `totpReady()` 识别验证码页；主循环在 `AccountLoginWorker.js:317` 根据 `codeReady` 填写并提交验证码。

选择 Authenticator 的分支仅在 `!codeReady` 时运行。只要验证码页被正确识别，就不会要求先点击“试试其他方式”。验证码处理本身也不依赖 `passwordSubmitted`，因此邮箱之后直接挑战的路径没有被这个标志排除。

本次浏览器实验复用了现有浏览器测试的 `run()`，只在内存中将合成密码页的跳转从 `/security` 改成 `/totp`，未修改仓库文件。使用本地 Firefox、合成凭据，所有 HTTP 页面请求由本地拦截提供：

| 路径                                                      | 交互模式             | 结果 |
| --------------------------------------------------------- | -------------------- | ---- |
| 邮箱 → 密码 → 直接 TOTP → AI Studio → 目标验证 → 会话导出 | `humanize=false`     | 成功 |
| 同上                                                      | 默认 `humanize=true` | 成功 |

该实验验证正常直接 TOTP 路径，未复现 Google 真实页面的动画、账号差异或生产失败。它也没有验证“邮箱后完全跳过密码”的真实账号情形。

### 3.2 已确认的实现缺口

**A. 页面就绪判断与输入框选择不够精确。**

`totpReady()` 的后备条件是正文包含 Authenticator 文案，同时存在宽泛选择器匹配的可见输入框。`totpSelector` 包含所有 `input[type="text"]`、`tel`、`number` 及未声明类型的输入框。方式选择页本身也包含 Authenticator 文案；如果转换期间还残留其他可见输入框，就可能误判为验证码页。

明确 `totpPin` 分支只检查可见性，不检查可编辑性。后续 `totpInputs()` 虽然会检查可编辑性和框数，但操作对象仍由宽泛集合的动态 `nth()` 定位，页面重绘后不保证仍对应先前识别的输入框。多个可编辑候选当前会转为 `manual_challenge`；不能把所有歧义都描述成超时。

**B. 直接 TOTP 处理缺少与页面切换绑定的操作完成判断。**

`clickForState()` 已为“切换验证方式”提供点击超时后的目标状态复核，但 `nextButton()` 只点击按钮，没有相同机制。`nextButton()` 还在全页面用匹配名称的 `.first()`，未限定当前挑战表单，也未过滤可见目标。

TOTP 提交前会等待 250 毫秒并复查 `totpReady()`，但复查和实际点击之间仍存在异步窗口。如果自动提交或页面刷新在这个窗口发生，脚本仍可能等待已经消失的“下一步”。固定等待不能消除这类竞态。

`interaction.type()` 是多次独立操作：点击、全选、删除、逐字输入。任何两个操作之间，挑战页面都可能切换；目前缺少针对已识别挑战变更的恢复逻辑。

**C. 返回方式选择页后缺少挑战生命周期管理。**

`authenticatorSelected`、`alternativeAttempted`、`totpSubmissions` 在整次尝试中保持，不随新的挑战页面更新。已经选择过 Authenticator 后返回方式列表，可能因 `authenticatorSelected=true` 不再选择；已经提交过验证码后重新进入输入页，若没有可识别的错误文案，又会因 `totpSubmissions>0` 只等待跳转。

这些限制有助于阻止无限操作，但当前把“本次登录尝试”和“某次具体验证码挑战”混在一起，无法正确处理有界的挑战重入。

### 3.3 对截图的判断与剩余不确定性

用户描述的入口差异可信，但截图不能证明是某一个选择器失配。尤其失败记录为 `totp`、最终页面为方式列表，值得优先检查以下顺序：

1. 验证码阶段进入后，页面是否重绘或返回方式列表，输入/点击却仍在等待旧目标。
2. `totpReady()` 是否曾把包含 Authenticator 文案的过渡页面误判为验证码页。
3. 验证码提交或自动提交后，是否仍执行了一个已无目标的“下一步”点击。
4. 如果页面返回方式列表，是否被一次性标志阻止了重新选择。

当前没有操作异常栈，无法从 `ui_click_timeout` 区分“点击验证码输入框失败”和“点击下一步失败”。也没有证据显示验证码算法或密钥本身错误；换码生成逻辑不是本轮首先应改的地方。

### 3.4 建议修改

- 增加统一页面分类：邮箱、密码、TOTP 输入、验证方式列表、通行密钥挑战、其他挑战、AI Studio。先明确当前状态，再执行该状态允许的动作。
- 对验证码页优先匹配明确的验证码字段，并检查可见、启用、可编辑；后备字段限定在已识别的 Authenticator 挑战容器内。正文关键词加任意输入框不能单独作为就绪依据。
- 区分验证码输入页和方式选择页，直接进入验证码页时直接填写，不额外点击“试试其他方式”。保留方式列表的明确 `data-challengetype="6"` 选择，未确认的页面转为明确诊断。
- “下一步”限定到当前表单的可见、启用按钮；提交动作结束或超时后，检查是否已离开当前挑战、进入 AI Studio 或出现明确错误。达到预期后置状态才能继续，不能仅因为旧按钮消失就判成功。
- 页面在输入前变化时重新分类，禁止继续向另一种挑战中的宽泛输入框打字。对填写途中变化同样进行有界复核。
- 为挑战重入设独立上限，并保留整次尝试的提交总上限。确认是新挑战后才重置相关局部状态，不要在每次轮询时重置 `totpSubmissions`，否则会造成反复提交。
- 保留每次生成新 TOTP 的时间窗口检查及最多一次明确错误后的换码，不通过无限重试掩盖页面识别问题。

## 4. 问题二：首登授权已完成，仍报 ui_operation_timeout

### 4.1 可复现的弹窗消失竞态

`LoginPageHandlers.js:108–117` 的关键顺序：

```js
const before = await found.innerText(...);
await this.interaction.click(button, ...);
this.termsOutcome = "clicked";
// 后续轮询
if (!(await found.isVisible()) || (await found.innerText(...)) !== before) {
    changed = true;
}
```

`isVisible()` 和 `innerText()` 是两个独立的异步调用，不是同一个 DOM 快照：

```text
确认按钮点击成功
→ isVisible() 返回 true
→ 协议弹窗被异步移除
→ innerText() 再次定位已消失的弹窗
→ 等待到期限后抛出 TimeoutError
→ Worker 报 ui_operation_timeout
→ 截图显示协议已经消失、AI Studio 页面已经打开
```

本次在真实 Firefox 的合成协议页中，精确注入“可见性检查返回 true 后、文字读取前移除弹窗”的时序，调用未修改的 `LoginPageHandlers.terms()`，结果为：

```json
{
  "name": "TimeoutError",
  "reason": null,
  "termsOutcome": "clicked",
  "dialogRemaining": 0,
  "operation": "locator.innerText: Timeout 475ms exceeded."
}
```

实验使用缩短的步骤期限以快速复现；移除发生在测试注入的明确边界，证明该代码窗口能够导致故障，不代表已取得生产该次故障的调用栈。

`terms()` 还在扫描弹窗时读取文字，在确认按钮前读取 `before`，这些位置同样会遇到扫描与读取之间的 DOM 变化。已有 catch 仅处理 frame 脱离，没有处理同一 frame 内弹窗已经关闭的正常情况。

### 4.2 为什么第二次重试正常

协议接受是服务端/账号侧的状态变化。即使后台执行器后来报错、没有提交本地会话，第一次点击也可能已完成协议接受。第二次登录不再出现同样的首登弹窗，便避开了上述竞态。

这是解释该现象的合理机制，不表示队列沿用了第一次失败的浏览器。代码每次尝试都启动新的浏览器并创建新上下文；失败执行器会被清理。真正可能保留的是账号侧已接受协议的状态。

用户记录中第一次 `aistudio_terms / ui_operation_timeout`、第二次 `storage_state / OK` 与该机制一致。若能取得历史中的 `termsOutcome=clicked`，可以进一步支持这一判断；若值为 `identified`，应优先核查确认前的控件操作。

### 4.3 点击超时分类也存在缺口

`LoginInteraction.js:33–54` 在 `try/catch` 之外执行了 `boundingBox()`。默认交互模式会先暂停 180–450 毫秒，然后获取目标尺寸；目标若已消失，尺寸查询就可能超时，还未进入负责设置 `ui_click_timeout` 的 catch。

本地 Firefox 对一个不存在的目标执行未修改的 `interaction.click()`，得到：

```json
{
  "name": "TimeoutError",
  "reason": null,
  "operation": "locator.boundingBox: Timeout 200ms exceeded."
}
```

这样的异常在 Worker 中会成为 `ui_operation_timeout`。因此两个错误名有时只反映点击在不同子步骤失败，不代表两种完全不同的登录问题。

### 4.4 模型升级页是另一项就绪判定问题

失败截图显示 AI Studio Playground，并提示 “Upgrade to unlock Gemini 3 Flash Preview”。这至少说明页面已经进入 AI Studio；但不能只靠页面外观核实实际账号，也不能证明目标应用的原生连接已经通过。

`validateStudio()` 当前主要等待可见 `textarea` 或可编辑 textbox，再核验邮箱。若已登录页面因为模型权限展示升级面板而没有编辑器，它会一直等编辑器出现。正常走完轮询后应报 `page_transition_timeout`；若其中某个 DOM 操作先超时，则可能进入兜底 UI 错误。

应分别判定：

- Google/AI Studio 的账号身份是否匹配。
- 是否仍存在已知协议或阻塞授权。
- 当前 Playground 模型是否可用、是否展示模型权限升级页。
- 项目配置的目标应用是否能初始化并建立原生连接。

若项目把目标应用连接作为可用会话的条件，身份正确且无阻塞协议的已登录应用界面可允许继续目标验证，即使当前 Playground 模型没有编辑器；若业务要求该模型本身可用，则应返回明确的模型权限错误。不能自动点击购买/升级按钮，也不能直接看到侧边栏就提交成功。

### 4.5 建议修改

- 协议观察尽量在同一次 DOM 读取中得到“容器是否仍存在、可见、文字是否改变”，避免先检查可见性再对旧 locator 长时间等待。容器消失或更换后重新扫描当前页面。
- 如采用捕获异常的方式，只对已识别协议容器消失/替换、同源 frame 变化等明确后置状态进行恢复；弹窗仍在且无法读取、按钮不可操作、账号不匹配等仍应失败。
- 确认点击超时后，也检查已知协议是否已消失并继续页面验证。不能把任意 `TimeoutError` 都吞掉或直接当成功。
- 将 `boundingBox()` 等点击准备操作纳入统一错误处理，并记录子操作名称。尺寸采样仅为交互辅助，不应在已达成后置状态时把流程判失败。
- 完成协议处理后更新阶段，例如 `aistudio_ready_wait`，并记录 `termsOutcome=completed` 等准确结果，避免后续等待仍标为 `aistudio_terms`。
- 将已登录界面与模型可用性分开识别；继续保留邮箱一致性核验、未知授权阻塞检查、目标原生连接核验及最终上下文复查。

## 5. 最小诊断补充与实施顺序

建议按以下顺序实施，避免一次性扩大兼容规则：

1. **补齐诊断，并修复已复现的首登竞态。** 涉及 `LoginPageHandlers.js`、`LoginInteraction.js`、Worker 错误投影及任务历史字段。保留完整执行期限与清理机制。
2. **收紧 TOTP 页面分类及输入框定位。** 涉及 `AccountLoginWorker.js` 的 `totpReady()`、`nextButton()`、主循环及 `LoginPageHandlers.totpInputs()`。
3. **为验证码/协议提交增加后置状态复核与有界挑战重入。** 状态推进替代一次性标志；不在仍运行的点击旁并发发起下一次输入。
4. **处理已登录但无编辑器的应用状态。** 新增明确模型权限分类，按目标应用验证的业务要求决定继续验证或明确失败。

建议增加的诊断仅使用枚举和数量，不保存原始页面文字、完整 URL、输入值、邮箱、验证码、密钥、Cookie 或未经脱敏的 Playwright 异常：

| 字段                                 | 示例                                                       | 作用                           |
| ------------------------------------ | ---------------------------------------------------------- | ------------------------------ |
| `operation`                          | `totp_focus`、`totp_submit`、`terms_read`、`terms_confirm` | 确认实际失败操作               |
| `operationPart`                      | `bounding_box`、`click`、`text_read`、`keypress`           | 区分兜底 UI 超时来源           |
| `pageStateBefore` / `pageStateAfter` | `totp_input`、`challenge_choice`、`studio_shell`           | 确认是否切页                   |
| `inputKind` / `editableCount`        | `explicit_totp` / `1`                                      | 识别选择器歧义                 |
| `challengeAttempt` / `submitCount`   | 数值                                                       | 确认重入与提交次数             |
| `termsOutcome`                       | `identified`、`clicked`、`completed`                       | 区分已发现、已点击和已确认完成 |
| `operationElapsedMs` / `remainingMs` | 数值                                                       | 区分元素等待与整体预算耗尽     |

不要直接把 Playwright 的 `cause.message` 或 `cause.stack` 原样输出到管理页：其中可能含选择器、页面片段和账号信息。诊断应对操作类别及错误类型显式映射。

## 9. 概率性 Studio 弹窗误判的诊断采集

新增诊断只采集证据，不调整弹窗白名单、模态判断、点击动作或人工挑战判定条件。Studio 未识别弹窗导致 `manual_challenge` 时，任务历史的“操作诊断”会包含：

- `failureSource: "studio_unrecognized_dialog"`：明确本次人工挑战来自 Studio 弹窗兜底。
- `studioDialogs.transitionScan`：提示扫描最初的 `scanCount`、实际扫描的 `scannedDialogs` 和扫描时视口尺寸；保留现有最多扫描 5 个弹窗的行为。若当时没有候选，数组为空。
- `studioDialogs.failureSnapshot`：失败已判定后采集的可见候选弹窗、视口尺寸及 `status`。最多保存 10 个候选，超出时 `truncated=true`，数量仍保留。

每个弹窗仅记录标签与属性的白名单枚举、宽高、面积占比，以及以下布尔值：

- `textMatches.title/cap/create`：现有费用提示标题、支出上限说明和创建按钮文案三个正则是否匹配，不保存文字。
- `transitionCandidate/gateCandidate`：该节点是否属于提示扫描选择器或人工挑战兜底选择器。
- `nonblockingRule`：采样时是否满足现有非模态且面积小于视口四分之一的规则。扫描记录另有 `nonblockingResult`，仅在业务实际执行这项判断时记录其结果。
- `closeButtonCandidate`：是否存在可见且标签匹配关闭文案的按钮候选，仅做 DOM 观察，不点击。该字段基于 DOM 标签近似检查，不等同于完整的浏览器无障碍名称计算。

失败快照中的 `count` 包含更宽范围的候选容器，可能包含嵌套外层；比较出现时序时，应优先将 `failureSnapshot.transitionCount` 与 `transitionScan.scanCount` 对照，它们对应同一类 `role="dialog"` 节点。`gateCount` 则对应人工挑战兜底选择器。快照中的节点顺序不作为持久身份标识。

失败后的采集最多等待 500 毫秒，并受剩余尝试预算限制；页面关闭或采集超时只记录 `capture_failed` 或 `capture_timeout`，仍返回原来的人工挑战结果。快照可能与判定瞬间有短暂时间差，例如失败快照为空可能表示弹窗已消失，不能据此否认判定时有弹窗。

部署此代码并重启服务后，等待故障自然出现，再从账号管理页的登录任务历史复制整段“操作诊断” JSON 即可，无需手动复现或打开浏览器开发者工具。诊断不会输出原始弹窗文字、HTML、输入值、邮箱、验证码、密钥或 Cookie；异常信息也不原样记录。

验证覆盖了模态费用提示、无 `role` 的 Material 容器、文案空白差异、扫描后新出现的弹窗、诊断数量上限、属性脱敏及采集失败/超时。上述失败场景仍返回 `manual_challenge`，已知非模态费用提示仍按原流程处理。
