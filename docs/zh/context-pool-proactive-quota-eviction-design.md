# 按前端显示模型主动淘汰耗尽账号 context 的改造设计

本文描述模型感知调度模式已实施的主动额度淘汰规则；legacy 模式保持现有行为。自动化验收采用模拟浏览器与连接，真实 VPS 的内存和恢复延迟仍需部署后观测。

## 1. 背景与目标

当前 context 热池主要在收到冷账号需求且容量不足时置换账号。即使账号在公益站提供的所有模型上都已耗尽额度，也不会因此主动释放 context。持续到来的其他请求还可能使置换等待账号排空。

本次改造让额度状态直接参与热池维护：

- 账号在所有前端显示模型上都明确耗尽额度时，主动停止给该账号分配新请求，排空后关闭 context。
- 存在其他可用账号时，后台提前换入，减少真实请求等待 context 初始化的时间。
- 所有账号都耗尽时，允许热池缩到 0，减少 VPS 内存占用。
- 最少 ready context 数量作为可用账号范围内的保温目标，不强制保留耗尽账号。
- 首次部署仍正常预热；新增模型首次请求允许等待初始化。

提前换入减少的是请求路径上的等待，不会消除 context 初始化本身的成本。

## 2. 已确定的产品语义

### 2.1 显示模型就是热池关注模型

公益站提供调用的模型与前端显示模型一致，不增加独立的“热池关注模型”配置。

已隐藏模型禁止新增调用，恢复显示后才能再次调用。隐藏不删除历史统计、模型状态或文件归属，不中断已获得租约的请求。

从未出现的新模型与已隐藏模型不同：通过项目现有的模型名称、路由和协议校验后，允许首次调用，沿现有发现流程进入显示集合。新模型首次调用可能等待 context 初始化，这是可接受的少数情况。

本方案调整了 `scheduler-hidden-models-design.md` 中“隐藏仅影响展示、不影响调用和调度”的旧规则。实施时应同步修改旧文档、前端说明和相关测试，避免存在相互矛盾的产品语义。

### 2.2 空显示集合不是全部耗尽

首次部署没有运行时模型记录、前端没有显示模型时，不能把空集合判定为“所有模型耗尽”。此时按配置正常建立启动热池，让第一次模型请求可以执行并建立模型状态。

管理员隐藏全部已知模型后，同样按空集合规则保留启动热池。已隐藏模型仍被拒绝，未知新模型仍可首次调用。这是本方案明确采用的空集合语义，避免引入额外的启动状态字段。

## 3. 耗尽判断

### 3.1 统一模型集合

在调度器中提供统一的公开方法，返回用于前端展示和热池判断的真实上游模型 ID 集合：

```text
已配置调度模型 ∪ 排队模型 ∪ 账号已记录模型
    - 已隐藏模型
    - 内部资源槽（例如 __files__）
```

集合以规范化后的真实模型 ID 为准，沿用协议层已有的模型后缀转换，不能让请求侧变体重复计算。前端和热池必须消费同一集合，不能各自维护列表。

`__files__` 等内部资源槽不能作为账号仍有模型额度的依据，否则文件操作会阻止真正耗尽账号退出热池。相应内部操作在需要时按真实需求加载 context。

### 3.2 明确耗尽的定义

某账号在某模型上“明确耗尽”，同时满足：

```text
该模型状态槽存在
且 rate_limited === true
且 cooldown_until > 当前时间
```

此状态来自实际 429 / RESOURCE_EXHAUSTED，按项目当前 429 冷却策略处理。它表示调度器观察到的额度或限流不可用，不保证上游确实耗尽了整天额度。

账号可因额度主动退出热池的条件：

```text
显示模型集合非空
且集合中的每个模型在该账号上都明确耗尽
```

下列情况不能按本机制判定为全部耗尽：

- 任意显示模型没有状态槽，或从未得到足够信息：未知视为可能可用。
- 面板估算剩余额度为 0，但没有有效的实际 429 冷却。
- 冷却已到期，即使 `rate_limited` 标记尚未被现有懒更新逻辑清除。
- 只有 403、临时错误、本地传输错误或 unsupported 状态。

账号禁用、不健康、认证过期等继续按原有账号资格和清理机制处理。本次不扩大为“所有不可用状态均主动关闭”，避免短暂错误引发反复重建。

判断函数应直接读取现有槽，不调用会创建槽的 `slot()`，也不通过快照生成来驱动生命周期。未知状态必须保持未知；状态判定应显式接收同一个 `now`，方便测试时间边界。

## 4. 最少 context 配置的优先级

沿用 `CONTEXT_POOL_MIN_READY`，改变其说明为：

> 后台维持的最少就绪 context 目标；只对具备热池驻留资格的账号生效，可用账号不足时允许低于该值。

优先级如下：

1. 已获得租约的请求继续执行，不能为了额度淘汰中断流或关闭繁忙页面。
2. 禁用、不健康等原有资格限制，以及全部显示模型耗尽规则，决定哪些账号可以常驻热池。
3. 在具备驻留资格的账号中，尽量满足最少 ready 数量。
4. 所有初始化和置换仍受最大 context 数量及初始化并发限制。

被动预热目标：

```text
effectiveWarmTarget = min(CONTEXT_POOL_MIN_READY, 具备热池驻留资格的账号数量)
```

具体示例：

| 最少 ready 配置 | 具备驻留资格的账号数 | 被动预热目标 |
| --- | --- | --- |
| 10 | 20 | 10 |
| 10 | 3 | 3 |
| 10 | 0 | 0 |
| 0 | 任意数量 | 0，真实请求仍可按需初始化 |

启动空集合场景下，符合原有账号资格的账号都具有驻留资格。`CONTEXT_POOL_MIN_READY` 不是最大 context 数量，也不是逻辑 worker 数量；真实需求可以把 context 数量增加到 `MAX_BROWSER_WORKERS`。

`GLOBAL_MAX_CONCURRENCY`、模型分配优先级、账号并发和单 context 并发限制保持现有语义。新机制改善账号驻留与置换，不能保证在执行槽满时立即执行 Pro 请求。

## 5. 生命周期与补池流程

### 5.1 主动评估

以下事件触发一次后台热池协调：

- 上游 429 更新账号模型状态。
- 新模型被接受并进入已知显示集合。
- 管理员隐藏或恢复模型。
- 手动清除 429、恢复模型或恢复账号。
- 每日自动重置或相关 429 冷却到期。
- 账号集合变化、context 初始化结束或关闭结束。
- 活动请求释放租约。
- 服务启动并完成状态加载。

协调流程先生成统一的模型集合和账号资格结果，然后标记需退出的账号、关闭已空闲 context、安排真实请求需求，最后补足有效保温目标。

事件合并执行，协调器必须幂等，不能每个失败都并发运行一套关闭和初始化流程。

### 5.2 排空与关闭

账号被判断为全部耗尽后，记录明确的排空原因，例如 `visible_models_rate_limited`。账号是否允许接收新租约的检查必须识别这种排空状态，不能仅复用调度器当前单个 `drainingAccount`：可能同时有多个耗尽账号需要排空。

- 空闲 context：立即进入关闭流程。
- 繁忙 context：保留已有租约，拒绝分配新租约；`account.inflight` 与本地活动消息队列都清空后关闭。
- 初始化中的 context：使用现有取消、晚到结果清理机制；如果无法立即取消，初始化完成后重算资格，耗尽账号不得发布为可租用的 ready context。

被淘汰账号的 storageState、额度状态、使用统计与文件归属均保留，只释放浏览器 context/page 及相应监控资源。

### 5.3 补池必须过滤耗尽账号

`_poolCandidates()` 的普通预热候选必须调用与淘汰相同的驻留资格判断。淘汰排序和关闭回调也应复用该判定，不能继续用“所有历史槽都不可用”替代显示模型的耗尽规则。

否则会产生“全部耗尽 → 关闭 → 低于最少 ready → 重新加载同一账号”的循环。

真实请求需求与被动预热分开判断：真实需求仍按所请求资源的账号资格、冷却、排除集合及文件归属选择。不能为一个仍处于 429 冷却的模型重新加载账号；新增模型及必要的内部文件操作可以按需加载。

内部文件操作不永久解除模型耗尽状态：操作结束后，账号仍全部耗尽且无其他真实需求时，再次排空关闭。

有空位时可以先初始化替代账号，再关闭需退出的 context；池满时先排空、释放再换入。始终遵守容量上限，不为了先补后退临时突破上限。

### 5.4 资格变化与关闭竞态

新模型进入显示集合、手动恢复或冷却到期，都可能使待淘汰账号重新具备资格。

- 尚未开始关闭：取消由额度耗尽引起的待关闭标记，恢复租约资格。
- 已开始关闭：完成当前关闭，完成后根据最新需求和资格重新加载。
- 其他关闭原因（例如人工禁用、账号不健康、容量置换）不能被额度恢复误取消。

关闭前和初始化发布 ready 前都重新验证最新资格，使用已有初始化任务去重机制防止同账号重复创建。多个账号同时淘汰时仍执行有界初始化和现有 context 创建串行保护。

## 6. 首次部署与新模型

### 6.1 首次部署

```text
加载账号和持久化状态
    → 显示模型为空
    → 按最少 ready 目标初始化合格账号
    → 首次请求经过现有校验
    → 接受并登记真实模型，更新显示集合
    → 执行请求，持续建立账号 × 模型状态
```

缺少账号、禁用账号或认证失效时仍受原有资格限制，不承诺创建配置数量的 context。

### 6.2 全池耗尽后的新模型首次请求

```text
旧显示模型在所有账号上都耗尽，context 已缩到 0
    → 收到未隐藏的新模型请求
    → 通过现有校验并登记模型，形成真实调度需求
    → 各账号对该新模型状态未知，重新具备可能可用资格
    → 优先初始化请求所需账号
    → 其余热池按有效目标、初始化并发限制逐步补足
    → context ready 后取得租约并执行
```

首次请求允许等待初始化，继续受现有调度超时约束；不保证一定在超时前完成。流式请求沿用现有 accepted/keepalive 行为。

模型登记和热池协调应发生在请求验证成功后，不应为格式非法或协议校验失败的请求创建模型状态或启动 context。不要新增免费上游探测请求来发现模型；只使用实际请求结果。继承当前首次请求产生模型状态的规则，失败模型可由管理员隐藏。

### 6.3 隐藏模型的访问控制

在真实模型规范化后、模型槽创建和租约申请前检查 `hiddenModels`。建议返回 HTTP 403 及明确的模型禁用错误；流式请求须在提前发送 headers 前完成此检查。

在调度器 `acquire()` 增加防御性检查，并在 `drain()` 中清理刚被隐藏模型的排队请求。已发出的租约不撤销，继续执行；请求被隐藏后不得通过新一轮重试获得新的租约。

所有模型调用协议都应执行同一规则，内部文件操作不作为被隐藏模型拒绝。现有 `/v1/models` 等目录展示行为不在本次调整范围内，但实际调用必须执行访问检查。

## 7. 零 context 时的恢复

不能依赖“下一个请求调用 `slot()`”才发现冷却到期。context 缩到 0 后也需要后台恢复入口。

沿用每日重置任务，重置完成后主动协调热池。对自然到期的 429 冷却，增加单个可重排的一次性唤醒定时器，安排到最早影响热池资格的未来冷却截止时间。

- 新增 429、模型集合变化、恢复操作和账号集合变化时重新计算截止时间。
- 到期后重算资格、推进状态 revision、补池，再安排下一次唤醒。
- 服务重启时依据持久化冷却和当前时间重建定时器，不恢复旧计时器句柄。
- 服务关闭时清理计时器；已过期的时间不能导致立即重排死循环。
- 定时器只恢复本地调度资格，不调用上游做健康探测。

即使关闭每日重置功能，自然冷却到期仍可以恢复热池。手动恢复也应立即触发补池。不要恢复人工禁用、不健康或 unsupported 状态。

context 降到 0 仅承诺释放 context/page 及附属资源，浏览器主进程可以继续存活。自动退出和重启整个浏览器进程不属于本次范围。

## 8. 代码改造位置

| 位置 | 改造内容 |
| --- | --- |
| `src/core/ModelScheduler.js` | 统一显示模型集合、无副作用的额度耗尽判断、驻留资格查询、多账号额度排空的租约限制、隐藏模型访问检查、状态变更触发协调、冷却唤醒 |
| `src/core/BrowserManager.js` | `_poolCandidates()` 资格过滤、有效保温目标、主动排空和空闲关闭、关闭原因区分、取消待关闭、初始化发布前重验、需求优先补池 |
| `src/core/ScheduledRequestHandler.js` | 在真实模型解析完成且提前发送流 headers 前检查隐藏状态，保证首次新模型需求能走按需初始化路径 |
| `src/core/SchedulerConfig.js` | 保持现有配置项和默认值，补充 `contextPoolMinReady` 的新语义 |
| `src/routes/StatusRoutes.js` | 隐藏、恢复和手动重置接口完成后触发协调，沿用现有管理鉴权 |
| 管理前端与语言资源 | 修订隐藏模型说明、最少 ready 字段说明、热池状态与缩容原因展示 |
| 调度和 context 池测试 | 覆盖主动淘汰、零 context 恢复、模型发现、隐藏访问规则及生命周期竞态 |

实现前先确认各协议真实模型转换位置，避免重复或不完整的后缀处理。新增判断统一放在调度器中，由浏览器管理器查询；前端不决定淘汰。

派生的驻留资格、有效目标和排空状态不需要持久化。继续使用现有模型 429 状态与隐藏集合，启动时重新计算；如最终实现新增持久化字段，应单独定义状态版本迁移。

## 9. 管理界面与观测

展示至少包含：配置最少 ready、有效保温目标、当前 ready、正在排空和因全部显示模型耗尽而不参与预热的账号数。

例如：

```text
最少就绪目标：10
当前有效目标：3
当前就绪：3
全部显示模型处于 429 冷却：7 个账号
```

全池耗尽时显示“所有显示模型在全部账号上均处于 429 冷却，已释放空闲 context；额度状态恢复后自动预热”。若有冷却唤醒任务，可以展示下一次本地检查时间，不能将它标成上游保证的额度恢复时间。

关闭日志记录账号、原因、显示模型数和 inflight；补池日志记录有效目标和候选数。快照应反映真实状态，避免界面长期显示健康或把正常主动关闭计为传输故障。

## 10. 验收与测试场景

1. 首次部署模型集合为空：有合格账号时正常达到最少 ready 目标，首个模型请求能执行。
2. Pro 全部耗尽但同账号 Flash 可用：保留 context，Flash 正常调度。
3. 某账号所有显示模型均处于实际 429 冷却：空闲时主动关闭，无需等到冷账号请求。
4. 耗尽账号仍有流式请求：停止发放新租约，已有流正常结束后关闭。
5. 多个账号同时耗尽：全部按各自活动请求排空，不受单个 `drainingAccount` 限制。
6. 其他冷账号仍可用：主动补入，遵守最大 context 和初始化并发限制。
7. 最少 ready 为 10、仅 3 个驻留候选：有效目标为 3，不重新加载耗尽账号。
8. 所有账号耗尽：context 最终缩到 0，后台补池不会形成关闭与重建循环。
9. context 为 0 后每日重置、手动恢复或自然冷却到期：无需新请求即可逐步补池。
10. 每日重置关闭：自然冷却到期仍能唤醒；重启后也能恢复正确的唤醒时间。
11. 全池耗尽后请求未知新模型：允许按需初始化；其他账号的未知状态让有效热池目标重新增长。
12. 有显示模型在某账号上状态未知：不判断该账号全部耗尽；判定不会创建模型槽。
13. 估算额度为 0、未收到有效 429：不触发主动额度淘汰。
14. 403、temporary、transport、unsupported：不被误判为全部额度耗尽，现有错误策略不变。
15. 已隐藏模型调用：各协议统一拒绝，不创建状态、不预热、不自动恢复显示。
16. 隐藏排队模型：清理排队请求；已获租约的请求继续执行，后续重试不得取得新租约。
17. 隐藏仍可用模型，剩余显示模型均耗尽：触发排空；恢复未知或可用模型后取消尚未执行的额度关闭。
18. 管理员隐藏全部模型：空集合按启动热池语义处理，不阻断未知新模型入口。
19. 内部文件槽不阻止额度淘汰；必要文件操作遵守归属，按需加载后可再次释放。
20. 关闭、初始化与恢复交错：无重复 context、无关闭活跃请求、无误取消人工禁用关闭、无容量超限。
21. 模型变体映射到同一真实模型：展示、隐藏访问控制和耗尽判定结果一致。
22. `CONTEXT_POOL_MIN_READY=0`：真实需求仍能初始化，恢复后不强制被动预热。
23. legacy 模式：账号轮换和 context 管理行为不受影响。

单元测试采用模拟时间、浏览器和连接；集成测试重点覆盖真实 ready-only 热池，不能只测试没有 BrowserManager 的调度器。真实 VPS 验收应观察全池耗尽后的 context 数与进程内存变化，并验证恢复后首批请求的延迟。

## 11. 建议实施顺序

1. 提取统一显示模型集合和纯函数式额度判定，补齐空集合、未知状态与时间边界测试。
2. 修改热池候选和有效保温目标，先保证耗尽账号不被重新补回。
3. 实现多账号主动排空、空闲关闭、恢复取消与初始化重验。
4. 接入额度、模型集合、账号和租约事件，合并协调任务。
5. 完成零 context 的冷却唤醒、每日重置和手动恢复补池。
6. 更新隐藏访问规则和新模型首次调用路径，覆盖各协议及提前流 headers。
7. 更新管理界面、文案、快照和相互冲突的旧设计文档。
8. 运行相关调度、请求和 context 生命周期测试，再执行项目要求的 lint 与 UI 构建，最后进行真实环境验收。

本方案不新增独立关注模型配置、不改变额度估算、不发送额外上游探测，也不引入 context 空闲 TTL。淘汰依据是显示模型的实际 429 状态；恢复依据是本地冷却、重置和新的真实模型需求。
