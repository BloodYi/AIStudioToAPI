# Context 池残留需求导致初始化后立即淘汰：修复方案

日期：2026-10-15（Asia/Shanghai）。状态：已完成本地代码修复；未部署生产。第 1–8 节保留诊断与修复设计背景，实际实施及验证结果见第 10 节。

## 1. 问题与证据边界

当前项目存在冷账号历史需求（`contextDemand`）未根据就绪 context 的实际服务能力失效的问题。满池时，历史需求仍能触发容量替换，关闭刚初始化成功且能处理排队请求的 context；随后其他账号初始化成功，又可能重复相同过程。

这会消耗初始化时间、降低有效容量并延长排队。“第十二个初始化不成功”是生产观察到的表现，不是固定容量或账号编号限制；其他池容量也可能触发相同缺陷。

## 2. 根因链路

| 文件                         | 方法                          | 问题或关联行为                                                       |
| ---------------------------- | ----------------------------- | -------------------------------------------------------------------- |
| `src/core/ModelScheduler.js` | `_signalContextDemand()`      | 无就绪可派发账号时，为冷账号登记需求；登记后环境可能发生变化         |
| `src/core/BrowserManager.js` | `_hasValidContextDemand()`    | 检查目标账号资格和同模型排队请求，未检查其他就绪账号能否处理该请求   |
| `src/core/BrowserManager.js` | `_startPooledContext()`       | 初始化成功只删除该账号自己的需求，其他历史需求仍可能有效             |
| `src/core/BrowserManager.js` | `_poolCandidates()`           | demanded 候选不受 `needWarm=0` 限制，满池仍可返回冷账号              |
| `src/core/BrowserManager.js` | `_reserveContextCapacity()`   | 满池时进入空闲替换，未区分实际需求与纯预热目的                       |
| `src/core/BrowserManager.js` | `_replaceIdlePooledContext()` | 选取空闲 context 后直接标记 draining、异步关闭，未再次验证替换必要性 |
| `src/core/BrowserManager.js` | `rankContextForEviction()`    | 新 context 的自身 demand 已删除、`lastRequestAt=0`，容易成为淘汰对象 |

`no_queued_demand` 当前只表示被淘汰账号没有自己的 `contextDemand` 条目，不能证明没有它能处理的排队请求。

另外，`ModelScheduler._drainRound()` 在派发请求前调用 `coordinateContextPool()`；初始化释放回调也先协调池、再 `drain()`。因此，仅在 `_signalContextDemand()` 中停止新增需求不足以修复：旧需求可能在真正派发前就触发淘汰。

## 4. 修复目标与不变量

1. 冷账号需求根据当前请求和可派发能力重新评估，不能只由历史条目和模型名维持有效。
2. 就绪 context 已能处理的排队请求应获得派发机会，不能因历史需求先被淘汰其服务资源。
3. 纯预热只使用可用容量，不为追逐预热目标反复关闭健康、可服务的 context；DRAINING 占位时允许暂时低于预热目标。
4. 无可服务的就绪账号时，真实模型需求仍能换入合格冷账号，不能因本次修复导致模型切换永久饥饿。
5. 不关闭有 inflight 或活动消息队列的 context，不破坏现有流式请求。
6. 保留容量同步预留、按所有者释放、single-flight、初始化并发上限、关闭完成前保留容量、超时与恢复隔离等已有保障。
7. 所有服务账号忙时，应区分“有空位可扩池”和“满池必须替换”：存在真实缺口且有空位时仍允许扩池；满池且无安全、必要替换时等待事件唤醒。
8. 不通过提高容量、重置额度、禁用健康账号、重启共享浏览器或增加固定保护时长替代需求纠正。

## 5. 建议实现方案

### 5.1 统一当前需求判断

建议由 `ModelScheduler` 提供一个共享的需求评估入口，供需求登记、候选筛选和替换前复核使用。具体命名与返回结构由实现确定，避免 BrowserManager 复制另一套模型资格规则。

对每个模型需求，至少检查：

1. 对应请求仍在当前 `pending` 中。
2. 待换入账号仍有效，符合该请求的资源资格，且其 key 不在该请求的 `excluded` 中。
3. 按该请求的 `excluded` 调用现有 `readyCandidates()`，并用 `canLease()` 判断是否已有可派发账号。
4. 已有可派发账号时，该请求不应继续支持满池换入；先让调度器派发，容量耗尽后再根据剩余请求重新登记需要的冷账号需求。

按请求判断，不能仅按模型判断：同模型的不同请求可能有不同排除账号。`demand.models` 中任一模型存在真实未满足请求时，可以保留该账号需求；只删除已经失去必要性的部分或整条需求。

一个可派发槽不等于能覆盖全部队列。实现可采用“先派发，再为剩余缺口重算需求”的方式；不要永久删除需求后遗漏唤醒，也不要让多个历史 demand 各自重复占用同一个缺口。存在在途初始化时，还应避免重复规划相同缺口，同时保留有用的初始化任务。

`unscoped`、无 model 需求及内部 `__files__` 请求必须单独梳理调用来源与生命周期。当前代码会直接认可无 model 的需求，不能直接套用普通模型队列规则使文件或前台初始化入口失效，也不能让无主需求永久触发满池替换。

### 5.2 分离需求换入与预热

候选或准入信息应能表达目的，例如实际排队需求、后台预热、前台显式初始化。不要仅靠候选数组中的位置推断目的。

- 实际排队需求：使用当前需求评估结果；满池时再判断是否确有必要替换。
- 后台预热：仅在物理容量可用时准入；不足时等待，不淘汰健康、可服务的 context。
- 前台显式初始化：保留原有用途与超时语义，使用相同容量保护，避免在公共准入方法上增加模型队列条件后误伤该入口。
- 额度耗尽 context：继续使用现有 drain 与关闭流程；不能为腾位提前结束请求。

### 5.3 替换前复核

在同步标记 victim 为 draining 前，用最新状态复核候选目的、真实未满足需求和 victim 的服务能力。候选生成时的判断不能作为稍后关闭资源的唯一依据。

替换应能说明将解决哪项当前缺口；关闭 victim 后仍无法改善需求的替换应被跳过。例如刚就绪 victim 能处理当前请求，而换入账号没有额外必要性时，不得关闭它。

复核与标记之间保持同步，保留当前 replacement 所有者检查和单次关闭保护。异步关闭开始前如需再次检查，必须按 owner 验证，并安全撤销自己设置的 draining 标记；不能覆盖其他 drain 原因。开始真实关闭后不要求撤回该关闭，但关闭完成后必须重新评估待换入账号，不能盲目使用旧候选继续初始化。

### 5.4 调度顺序与唤醒

梳理初始化成功发布、释放初始化标记、池协调和请求派发的调用顺序，使新就绪 context 能在被评估为可替换资源之前服务当前请求。

顺序调整是配套措施，需求复核仍须独立成立。不要只交换两行调用或添加定时器来规避当前复现。

需求取消或派发能力不足后，保留明确唤醒来源：租约释放、活动消息队列释放、初始化结束、关闭完成、请求到达或取消、账号资格变化及冷却到期。满池且无进展时退出本轮，避免无条件 pump/drain 互调形成空转。

## 8. 日志与上线验收

建议在已有池日志中补充需求来源、当前未满足模型、换入目的、跳过替换原因及容量状态；日志按状态变化输出或限频。`no_queued_demand` 应改为能准确表达账号自身 demand 状态的描述，或附加说明，避免误读成没有可处理的请求。

- 已能被就绪 context 服务的请求，不再引发该 context 初始化完成后立即因历史 demand 被替换。

- 真正的模型切换、额度耗尽和资格变化仍能触发必要换入。
- 总容量、初始化并发和已有请求完整性保持正确；DRAINING 期间的暂时预热不足可解释。

## 10. 本地实施与验证结果

### 10.1 已完成的修改

`src/core/ModelScheduler.js`：

- 新增共享的逐请求需求判断，核对模型资格、账号轮换资格、请求取消、排除集合及现有就绪账号的 `canLease()` 能力。历史需求不能再仅因同模型请求仍在队列中而持续有效。
- 在需求登记和历史需求检查中识别已准入的初始化任务，合并同一批次可由同一账号满足的需求。初始化完成后重新判断剩余队列，避免并发冷账号重复追逐同一个派发机会。
- 初始化任务在发布前评估自身需求时不把自己的新 context 当成替代服务能力，保留 `__files__` 等非常驻账号初始化路径。
- 派发消耗最后一个就绪槽位后，在本轮时间预算内重新评估剩余队列，允许有空位时继续扩池，无需等待已有租约结束。

`src/core/BrowserManager.js`：

- 根据实时需求确定准入目的：模型需求、前台指定账号等待、后台恢复或纯预热。后台恢复与预热仅使用可用容量，不触发满池淘汰；同账号已占容量的 context 重建仍可执行。
- 在同步标记淘汰对象前再次检查模型需求；候选生成后出现可派发账号或请求取消时，不再因过期模型需求关闭 context。
- 对已失效且不属于当前预热候选的账号，不再启动后台初始化。替换关闭完成后沿用重新扫描流程，不直接初始化旧候选。
- 为 `ensureWorkerContext()` 增加按账号计数的前台等待者，保留指定账号的空闲容量替换；成功、失败和超时均在 `finally` 中释放等待者。最后一个等待者退出时清理无模型需求部分，保留独立模型需求。
- 后台无模型恢复需求增加有效期，使用当前排队超时配置（缺省回退 120 秒），在池扫描时清理；不增加独立重试定时循环。
- 初始化标记与容量预留释放后先调用派发，再协调和补池；原有预留、single-flight、关闭所有者及并发控制保持不变。
- 替换日志附带 `purpose`，容量等待日志附带当前目的；将 `no_queued_demand` 改为 `no_account_context_demand`，明确其仅描述账号自身 demand 条目。

异步关闭开始前没有增加撤销 draining 的新流程：必要性复核与 draining 标记在同一同步调用内完成；真实关闭启动后按既有所有者规则完成关闭，再重新评估候选。
