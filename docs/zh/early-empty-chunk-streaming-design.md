# 提前发送空首块模式设计

本文为待实施方案。本次文档新增不代表功能已经实现。

## 1. 目标与使用场景

在前端现有“流式响应模式”下拉框中新增“提前发送空首块”。当下游请求流式响应时，服务通过本地校验后立即发送合法的流式 JSON，首块包含 `content: ""`；等待完整结果期间持续保活，结果准备好后整段发送。

适用场景包括上游非流式模型，以及需要等待完整工具输入后才能交付正文的抗截断网关。用户可以更早看到客户端进入接收状态，避免长时间没有反馈。本模式改善等待体验，不缩短上游生成时间，也不人为延迟播放完整结果。

酒馆能否立即建立 AI 楼层、何时启动计时器，需要用实际使用的版本和连接方式验收。空首块表示本服务已接受请求，不表示模型已经开始生成。

## 2. 配置与前端切换

扩展现有 `STREAMING_MODE` 枚举，不新增独立开关。

| 配置值  | 下拉框文案     | 下游流式响应行为                           |
| ------- | -------------- | ------------------------------------------ |
| `real`  | 真实流式       | 保留当前逐步转发行为                       |
| `fake`  | 缓冲后模拟流式 | 保留当前缓冲、转换和输出行为               |
| `early` | 提前发送空首块 | 立即发送空正文首块，等待完整结果后整段输出 |

前端在原来的两个选项后追加新选项。说明文案建议为：

> 流式请求立即发送空正文首块，等待期间保活，完整结果返回后一次填充。非流式请求仍返回完整 JSON。

保存后对新请求生效；已接收的请求使用接收时的配置快照，不能在请求中途改变模式。保持既有默认值与旧配置语义，保存、读取、重启和恢复默认值均应正确处理第三种枚举。

模型后缀同步支持 `-early`，与已有 `-real`、`-fake` 使用相同的解析位置和优先级：请求侧后缀覆盖全局模式。剥离模式后缀后再做真实模型匹配、隐藏检查与调度，不能把 `early` 传给上游作为模型名称的一部分。

`early` 对上游使用现有 `fake` 缓冲策略。应分别保存“下游响应模式”和“上游传输模式”，避免把新枚举直接传给只识别 `real` / `fake` 的浏览器或注入脚本。

## 3. 首期协议范围

首期在 OpenAI Chat Completions 接口 `/v1/chat/completions` 实现空首块，覆盖 legacy 和模型感知调度两种运行模式。

仅当下游请求体 `stream: true` 且有效模式为 `early` 时启用。下游 `stream: false` 时使用完整 JSON 响应，不能发送 SSE 或在 JSON 中混入心跳。

Responses、Anthropic、Gemini 协议不能直接发送 OpenAI 的 `choices[].delta.content`。首期选中 `early` 后，这些接口明确回退到既有 `fake` 行为；前端说明中注明“空首块当前适用于 OpenAI Chat Completions，其余接口按缓冲模式处理”。后续如需扩展，应分别设计其原生协议的开始事件。

## 4. 请求时序与数据格式

### 4.1 发送时机

完成鉴权、请求结构与模型校验、模式解析、隐藏模型检查等已有本地准入检查后，立即建立 SSE 并发送空首块。可同步判断的准入拒绝应保持普通 HTTP 错误，不能先发成功首块。

首块应在等待账号、调度队列、BrowserContext 或上游完整结果之前发送，不能等到获得租约后再发送。每个下游请求只发送一次开始首块，上游内部重试不会再次发送。

响应头采用现有 SSE 设置，并确保数据及时写出：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

调用已有的响应头 flush 能力；核对压缩、中间件和部署代理是否缓冲响应。不要为发送首块等待上游返回数据。

### 4.2 空首块

以下为格式示例，`id`、`created`、`model` 必须按请求实际生成：

```text
data: {"id":"chatcmpl-example","object":"chat.completion.chunk","created":1791763200,"model":"MODEL_ID","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

```

每个 SSE 事件以两个换行结尾。首块必须是合法 JSON，并包含字符串类型的空 `content`，不能使用空 `data:`、裸空行、正文空格、零宽字符或提示性正文代替。

首块不能携带结束原因、伪造 usage 或发送 `[DONE]`。流 ID 和创建时间在首块前生成，并注入后续协议转换状态；同一响应的所有 completion 块保持一致的身份字段。重试换账号时保持这个下游响应身份。

### 4.3 等待与完成

首块之后立即补发一个无 role 的合法空增量，随后每 1000 ms 发送一次并 flush：

```text
data: {"id":"chatcmpl-example","object":"chat.completion.chunk","created":1791763200,"model":"MODEL_ID","choices":[{"index":0,"delta":{"content":""},"finish_reason":null}]}

```

立即补发使暂存一条事件的 NewAPI 释放首块；周期空包让下游持续收到数据事件，触发酒馆现有进度刷新。必须使用空字符串，不能加入空格、换行正文或零宽字符。后续空包不重复 role，不携带 usage、工具调用、结束原因或 `[DONE]`，并保持同一流身份。

legacy 与模型感知调度共用一个 early 心跳计时器，固定间隔不改变其他模式的 `STREAM_KEEPALIVE_INTERVAL_MS` 或随机注释保活。真实内容开始交付、成功、失败或取消后停止；空包通过专用写入状态排除在模型首输出判断之外。

完整结果准备好后，复用现有协议转换器输出正文、工具调用、结束原因及客户端请求的 usage，再发送 `[DONE]` 并关闭连接。正文一次交付，不增加逐字切片或播放延迟。工具调用与 usage 不应被强制改写为普通正文；空首块本身也不触发工具执行。

转换器若会自动生成 `role: assistant` 开始块，应复用首块的发送状态，避免重复开始事件。结束块与 `[DONE]` 也必须只发送一次。

## 5. 状态、重试与错误处理

### 5.1 区分首块与真实模型输出

现有 `ScheduledRequestHandler` 的 `res.write` 包装将大多数非注释写入视为模型首输出。新增空首块必须通过显式状态或专用写入方法排除，不能仅把格式化后的 JSON 加入字符串白名单。

建议明确区分：

- `streamStartSent`：本地开始首块已经发送。
- `modelOutputStarted`：真实正文、推理内容或工具调用已经交付给下游。
- 请求是否已终结：成功、失败或取消后不再写入。

发送空首块不能设置 `modelOutputStarted`，不能停止等待心跳，也不能因为 `headersSent` 已经为真就取消原有的输出前重试资格。

模型感知调度器保持原有重试预算、账号排除、冷却、租约释放和客户端取消语义。在没有交付真实模型内容时，可按已有策略换账号重试；内部重试对下游维持同一条流。

### 5.2 错误与取消

发出首块前的错误使用普通 HTTP 错误。发出首块后的调度超时、上游失败或重试耗尽使用现有 OpenAI 流内错误格式，保留错误类型与原始状态信息，然后按错误终结约定关闭连接，不能伪装为成功的空回复。

发送过 HTTP 200 后无法再改为 HTTP 429 或 500；这是模式的明确语义，应在配置说明或文档中说明。

客户端取消后立即停止心跳、取消排队或上游工作，并按现有机制释放资源。成功、错误、取消和断连都必须清理计时器，禁止向已关闭的响应继续写入。

## 6. 与已有提前响应头配置的关系

`STREAM_EARLY_HEADERS` 继续控制既有模式的提前响应头与注释行为。

选择 `early` 即明确要求发送空首块，因此即使 `STREAM_EARLY_HEADERS=false`，本模式仍提前发送响应头和空首块。配置说明应写明这一优先级，避免用户选择新模式后没有获得对应效果。

`real`、`fake` 的既有行为保持不变。不要将 `early` 简单等同于 `fake` 后就失去发送首块的时机，也不要使新模式只在模型感知调度下可用。

## 7. 网关部署边界

若链路为“酒馆 → 本项目 → 上游或抗截断网关”，本项目生成空首块即可直接改善下游等待体验。

若链路为“酒馆 → 抗截断网关 → 本项目”，网关必须透传首块和心跳，或在面向酒馆的一侧主动生成等效首块。网关若缓冲整个下游响应，本项目发送首块无法让酒馆立即收到数据。

不能假定网关声明支持流式就会即时转发。部署验收必须检查酒馆实际连接入口收到首块的时间。

## 8. 实施位置与可观察性

| 位置                                         | 需要处理的内容                                        |
| -------------------------------------------- | ----------------------------------------------------- |
| `src/config/definitions.js`                  | 扩展枚举、说明和保存校验                              |
| `src/utils/ConfigLoader.js` 与配置保存链路   | 新枚举加载、持久化与默认值兼容                        |
| `ui/app/components/UnifiedConfiguration.vue` | 新增下拉选项文案与协议范围说明                        |
| `src/core/FormatConverter.js`                | 解析 `-early`，复用流身份和开始块状态                 |
| `src/core/RequestHandler.js`                 | legacy 与共用 OpenAI 缓冲路径的空首块、心跳和终结处理 |
| `src/core/ScheduledRequestHandler.js`        | 调度前首块、真实输出分类、重试与单一保活管理          |
| 状态页、日志与使用记录                       | 正确显示第三种模式，避免被二元判断显示成旧假流式      |

请求记录中的下游有效模式应记录为 `early`。非 OpenAI 接口回退时，记录实际生效的 `fake`，必要时另行记录请求模式用于诊断。

分别观察连接建立、空首块发送、真实模型首输出和请求完成时间。不能把空首块记入 `model_first_output_ms` 或当作模型吞吐、token 用量；缓冲模式下真实模型首输出指正文或工具结果实际交付下游的时间。

## 9. 验收标准

1. 前端可以选择、保存并重新读取三种模式，重启后选择保持一致；旧配置和默认值保持兼容。
2. 使用可阻塞的模拟上游：在上游结果尚未释放时，下游已经收到合法的空首块，且 `content` 严格等于空字符串。这项检查同时覆盖 legacy 与模型感知调度。
3. 请求排队时仍收到首块和持续心跳；关闭 `STREAM_EARLY_HEADERS` 后，`early` 仍按约定发送首块。
4. 等待期间仅有一个心跳来源；上游释放结果后正文完整且只出现一次，身份字段一致，结束与 usage 符合现有协议。
5. 首块后发生可重试错误仍能换账号成功，首块不重复、不污染正文，也不提前设置 `modelOutputStarted`。
6. 首块后的最终失败被客户端识别为错误；首块前鉴权失败、无效请求和隐藏模型拒绝仍保留正常 HTTP 状态。
7. 取消、断连、成功和失败都清理心跳与资源，断连后不继续写流。
8. `stream: false` 始终返回完整 JSON；其他协议按说明回退，没有混入 OpenAI 首块。
9. `-early` 与全局配置的优先级正确，调度与隐藏检查使用剥离后缀的真实模型名称。
10. 在实际酒馆中确认立即建立 AI 楼层、计时器开始、最终整段填充，以及停止生成和错误提示的行为；记录酒馆版本和连接方式。若需要通过网关接入，必须通过实际网关入口重复验收。

自动化检查应验证时序、重试与资源清理；酒馆和真实网关的界面效果需要单独实测，不能由格式正确的单元测试替代。
