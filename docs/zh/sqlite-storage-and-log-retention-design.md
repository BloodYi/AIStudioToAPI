# SQLite 请求统计存储与日志过期管理改造设计

状态：已实施。本文同时作为存储结构、配置与运维行为说明。

## 1. 目标与范围

将请求明细和使用统计从 JSONL 与全量内存存储迁移到 SQLite，支持按配置自动清理过期明细，并在管理面板显示实际生效的保留期限、每条记录的过期时间和清理状态。

本期范围：

- 请求明细、账号尝试记录、每日汇总、累计统计入库。
- 保持现有筛选、分页、统计看板和公开看板的数据口径。
- 流式迁移旧 JSONL，保留 JSONL 导入、导出能力。
- 增加保留期限配置、定时清理和前端过期信息。
- API 调用过程、浏览器、WebSocket 等运行日志继续输出标准输出/标准错误，由 Docker 轮转管理；不重复写入 SQLite。

调度状态、代理映射、认证文件本期保持现有存储方式。独立审计日志、完整调度事件历史、Token 用量统计属于后续功能。PNG、HTML 调试文件也不受本期请求明细清理任务管理。

## 3. 存储结构

### 3.1 requests：请求明细

使用独立字段保存查询维度，避免把整条记录作为 JSON 字符串存入单列。

| 字段组     | 建议字段                                                                                              | 说明                                   |
| ---------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 标识       | `id`、`request_id`                                                                                    | `id` 为持久递增序号；`request_id` 唯一 |
| 时间       | `started_at_ms`、`finished_at_ms`、`duration_ms`                                                      | UTC 毫秒整数；接口按原有约定返回时间   |
| 接口       | `method`、`path`、`api_format`、`request_category`                                                    | 对应已有字段                           |
| 模型与模式 | `model`、`is_streaming`、`stream_mode`                                                                | 保留现有流式分类                       |
| 客户端     | `client_ip`                                                                                           | 仅管理接口可见，不进入公开看板         |
| 账号       | `account_key`、`initial_auth_index`、`initial_account_name`、`final_auth_index`、`final_account_name` | 保存请求发生时的账号信息               |
| 结果       | `outcome`、`status_code`、`error_message`、`attempt_count`                                            | 成功、失败、中断口径保持一致           |

初始索引：`request_id` 唯一索引，以及 `finished_at_ms`、`(model, id)`、`(account_key, id)`。其他索引结合实际查询计划补充，不为每种字段组合创建索引。

`expires_at` 根据当前保留配置与完成时间计算，不作为固定列存储。这样修改保留期限后，已有记录也遵循新配置。

### 3.2 request_attempts：账号尝试记录

字段：`request_row_id`、`attempt_number`、`account_key`。以请求行 ID 和尝试序号为联合主键，外键关联 `requests.id`，启用级联删除。

本期仅迁移已有信息。逐次尝试的开始/结束时间、状态码、错误原因目前没有完整采集，不能从旧数据推测填充。

### 3.3 统计表

- `usage_daily`：按日期、最终账号、模型、API 格式、请求类别、流式模式组合聚合，保存请求数、成功数、失败数、中断数、总耗时。
- `usage_totals`：按同样维度保存累计值，另保存账号最近使用时间、最近路径等现有界面需要的数据。
- `storage_meta`：数据库结构版本、统计起始时间、数据集版本、迁移状态和最近清理结果。

每日日期键统一使用 `America/Los_Angeles`，与现有调度面板的自然日口径一致；这是日统计口径，不影响明细按 UTC 时长过期。空维度使用统一非空规范值，确保联合唯一约束能正确去重。

平均耗时用总耗时除以请求数计算，成功率用成功数除以请求数计算，不累计平均值。用户请求按最终结果统计一次；调度的上游尝试计数保持独立，避免重试导致请求数放大。

汇总不含客户端 IP、请求 ID、错误正文。每日与累计统计本期长期保留，体积随日期和维度组合增长，不能宣称数据库整体具有固定容量上限。

### 3.4 写入和运行方式

一次完成请求的明细、尝试记录、每日统计与累计统计在同一事务提交。只有新插入请求才能更新汇总；重复 `request_id` 不重复累计。

新增存储服务隔离 SQL 和连接管理。数据库操作采用专用 worker 与有界队列，避免同步数据库调用阻塞代理主线程；批量提交、队列长度、写入失败均应可观察。写入失败不得伪报已持久化，有限重试后输出错误并将存储状态标为异常。优雅退出等待已入队记录提交；进程被强制终止时，尚未提交的队列记录可能丢失。

数据库默认使用本地持久卷，启用外键、WAL、忙等待超时，并以 `synchronous=FULL` 作为初始耐久性设置。WAL 支持读写并行，但仍只有一个写入者，且不适用于跨主机网络文件系统。[SQLite WAL 文档](https://www.sqlite.org/wal.html)

驱动在实施时依据项目支持的 Node.js 版本选择并锁定版本；当前 Dockerfile 使用 Node.js 24，同时需要核对非 Docker 部署兼容性。优先提供薄存储接口，避免驱动细节进入业务代码。

## 4. 配置与过期规则

### 4.1 新增配置

| 配置项                               | 默认值                      | 语义                                       |
| ------------------------------------ | --------------------------- | ------------------------------------------ |
| `USAGE_DB_PATH`                      | `./data/usage-stats.sqlite` | 数据库文件路径，相对路径以进程工作目录解析 |
| `USAGE_LOG_RETENTION_DAYS`           | `30`                        | 请求明细保留天数；正整数；`0` 表示永久保留 |
| `USAGE_LOG_CLEANUP_INTERVAL_MINUTES` | `60`                        | 自动清理检查间隔，正整数分钟               |
| `USAGE_LOG_CLEANUP_BATCH_SIZE`       | `1000`                      | 单次删除事务最多处理的请求条数，正整数     |

现有 `ENABLE_USAGE_STATS=false` 时，不读写统计数据库、不迁移、不启动清理；管理面板显示“使用统计已关闭”，已有磁盘数据保持原样。

配置在服务启动时读取。本期管理面板只展示实际生效值；修改 `.env` 或容器环境变量后重启生效，不新增网页编辑配置能力。未配置使用默认值；空字符串、负数、小数、非数字、超出安全整数或计时器支持范围的值必须明确报错，不能静默变成 `0`。配置校验失败时停止启动，防止错误期限触发删除。

示例：

```dotenv
USAGE_DB_PATH=./data/usage-stats.sqlite
USAGE_LOG_RETENTION_DAYS=30
USAGE_LOG_CLEANUP_INTERVAL_MINUTES=60
USAGE_LOG_CLEANUP_BATCH_SIZE=1000
```

### 4.2 过期与清理时间

当保留天数大于零时：

```text
过期时间 = finished_at_ms + 保留天数 × 24 × 60 × 60 × 1000
过期条件 = finished_at_ms <= 本轮服务端时间 - 保留时长
```

“30 天”表示连续 30 × 24 小时，不是本地自然月；夏令时不改变明细保留时长。

过期表示记录具备清理条件，实际物理删除发生在后续成功的清理批次。管理界面显示“已过期，待清理”，不能承诺在过期时刻精确删除。查询和导出可以包含尚未清理的过期记录，但必须标明状态。

当配置为 `0` 时，`expires_at=null`，显示“永久保留”，不执行过期删除。

缩短期限时，现有记录按新期限重新计算，并在启动清理时处理；延长期限不会恢复已经删除的数据。配置注释和面板说明必须写明这一点。

### 4.3 清理任务

1. 数据库初始化与迁移成功后执行一次清理，以处理停机期间过期的记录。
2. 随后按配置间隔检查；同一实例禁止并行执行多个清理任务。
3. 固定本轮截止时间，按 `finished_at_ms` 索引分批选取请求 ID，在短事务中删除，尝试记录级联删除。
4. 批次间让出执行机会，允许正常请求写入；清理不触碰汇总、活跃请求和调度状态。
5. 记录最近尝试时间、最近成功时间、累计删除数、耗时、运行状态、错误和下一次计划时间。空批次也视为成功完成检查。
6. 失败保留已提交批次结果，并在下个周期重试；不能把失败显示为完成。

删除明细会改变历史列表，更新持久化数据集版本。游标版本不一致时，沿用现有 `reset` 机制通知前端重新查询第一页；每个返回页必须来自一致的数据库读取快照。

数据库删除后的空闲页优先供后续写入复用，不等同于文件立刻缩小。实施时为新数据库配置增量空间回收，在清理后限量执行；完整压缩作为维护操作，不在每个清理周期执行。监控数据库和 WAL 文件大小、清理积压及 checkpoint 进度。空间回收方式需按驱动能力验证。[SQLite VACUUM 文档](https://www.sqlite.org/lang_vacuum.html)

## 5. API 与管理面板

### 5.1 存储状态接口

新增受现有管理登录鉴权保护的 `GET /api/usage-stats/storage`。返回服务端实际配置和状态，不返回数据库绝对路径，不向匿名公开看板开放。

响应示意：

```json
{
  "enabled": true,
  "backend": "sqlite",
  "server_time": "2026-09-25T12:00:00.000Z",
  "retention_days": 30,
  "retention_mode": "days",
  "cleanup_interval_minutes": 60,
  "expiration_cutoff": "2026-08-26T12:00:00.000Z",
  "next_record_expires_at": "2026-09-25T12:15:00.000Z",
  "last_cleanup_attempt_at": "2026-09-25T11:00:00.000Z",
  "last_cleanup_success_at": "2026-09-25T11:00:01.000Z",
  "next_cleanup_at": "2026-09-25T12:00:01.000Z",
  "cleanup_status": "idle",
  "last_deleted_records": 1200,
  "cleanup_error": null,
  "storage_status": "healthy",
  "retained_records": 123456,
  "database_bytes": 104857600,
  "wal_bytes": 1048576
}
```

`next_record_expires_at` 指当前仍未过期记录中最早的过期时间；没有记录时为 `null`。清理状态取 `disabled/idle/running/error`。永久保留时模式为 `forever`，截止时间、下一次过期时间、下一次清理时间均为 `null`。从未成功清理时最近成功时间为 `null`；任务执行期间下一次运行尚未确定时也可为 `null`，前端应显示对应文字。

记录数量和磁盘大小采用短时缓存或维护计数，避免每次面板轮询执行全表扫描。

### 5.2 请求列表接口

保留 `/api/usage-stats/records` 的现有筛选参数、游标分页和返回字段；内部改为参数化 SQL 查询，增加每条记录的 `expires_at` 与 `expired`。

游标中的序号由数据库持久 ID 映射，不能在每次重启时重新编号。保留数据集版本检查，并对修改保留配置后的列表执行刷新。禁止通过加载全部数据库行再在 JavaScript 中分页。

现有 `/api/usage-stats/summary` 与公开看板使用独立汇总。旧 `/api/usage-stats` 的调用方需要同步迁移，移除无上限返回全部 records 的路径；明确兼容字段与有界结果范围，不能悄悄返回截断数据并称其为完整历史。

### 5.3 前端展示

在“使用统计”页面的请求记录区域上方新增“日志保留”信息卡：

```text
日志保留
请求明细：保留 30 天
自动清理：每 60 分钟检查
最近清理：2026-09-25 19:00:01（本地时区），删除 1,200 条
下次清理：2026-09-25 20:00:01（本地时区）

请求结束满 30 天后过期，由后续清理任务删除。
每日与累计统计长期保留。
```

具体要求：

- 请求记录桌面表格新增“过期时间”列；移动端在记录详情中显示。
- 时间以浏览器本地时区展示并标明时区，保留完整时间提示；倒计时以接口 `server_time` 校准，避免客户端时钟偏差。
- 永久保留显示“永久保留”；过期但未删除显示“已过期，待清理”；无记录显示“暂无记录”，不推算虚假日期。
- 清理失败显示“清理失败，将在下次检查重试”及脱敏错误，同时保留最近成功时间。
- 信息卡说明“保留期限由服务配置决定，修改后需重启；已删除记录无法通过延长期限恢复”。
- 系统日志页增加简短说明：“此处显示近期运行日志；历史日志由 Docker 管理。”Docker 使用容量轮转，无法据此给每条终端日志显示精确过期日期。
- 状态接口只在相关页面可见时定期刷新（建议 30 秒），页面首次打开和重新聚焦立即刷新；不增加全局高频轮询。
- 中英文文案同步添加。

统计口径必须明确：累计卡片使用长期汇总；按客户端 IP、状态码、错误等明细字段筛选的结果，只覆盖尚存明细。历史时间范围超出明细保留范围时提示“部分请求明细已过期清理”。每日汇总仅支持其已保存的维度和完整日期范围，任意时刻范围不能伪装成精确历史统计。

## 6. 迁移、导入、导出与回滚

### 6.1 首次迁移

- 迁移在统计对外可用之前执行，停止旧文件写入，保证数据源稳定。
- 流式读取旧 JSONL，校验请求 ID、时间、结果和耗时；保留现有字段兼容规则。缺失 ID、无效时间、坏行单独计数并报告，不能用当前时间替代。
- 在临时数据库分批导入全部有效历史并生成汇总；请求 ID 去重，同 ID 内容冲突需要报告，不能覆盖后再次累加。
- 校验有效唯一记录数、各结果计数、总耗时、账号与模型汇总，并检查数据库完整性及外键。
- 迁移完成标记、结构版本与统计起始时间持久化；关闭连接并处理 WAL 后切换到正式数据库。
- 再按生效保留期限清理旧明细。因此旧明细虽然会过期，其累计统计仍得到保留。
- 原 JSONL 保留为迁移备份，不自动删除；提示备份仍占磁盘空间。中断后根据迁移状态重试，不把半成品当作正式数据库，也不重复累计。

### 6.2 后续导入与导出

运行期间的 JSONL 导入仅接收保留窗口内的记录（永久保留模式不限制时间）；过期记录计入 `expired_skipped`，不进入汇总。这样历史明细清理后，再导入同一旧文件不会重复增加累计值。

**延长期限后仍可能重新导入已经清理的旧记录。** 因此数据库持久保存已清理时间水位，普通导入同时拒绝 `finished_at_ms` 不晚于该水位的记录，并报告 `purged_history_skipped`。水位只在按时间顺序完成相应删除批次后推进；它表示禁止回填的历史范围，不能因延长期限而倒退。需要修复这段历史时走离线重建工具，不走普通合并导入。该限制必须显示在导入说明中。

保留窗口内通过唯一请求 ID 去重，新增记录与汇总在同一事务更新。导入和清理通过存储队列协调，清理水位检查与插入处于同一事务；导入不丢弃正常完成的请求。

导出以流式 JSONL 输出当前仍保留的明细，不拼接成单个内存字符串。明确提示：明细导出不是包含全部累计统计的数据库备份。长导出需限制读取事务持续时间，避免阻止 WAL 回收。

### 6.3 备份与回滚

在线备份使用 SQLite 一致性备份机制，不能仅复制正在使用的 `.sqlite` 文件并忽略 WAL。[SQLite 备份文档](https://www.sqlite.org/backup.html)

迁移后未接受新请求时，可恢复旧程序和原 JSONL；接受新请求后，回滚必须先导出并合并新增明细。已经清理的历史无法从明细导出恢复，旧程序也不能直接读取新汇总，必须事先验证回滚工具或恢复迁移前完整备份并明确数据缺口。

## 7. Docker 运行日志

部署示例：

```yaml
services:
  app:
    environment:
      USAGE_DB_PATH: /app/data/usage-stats.sqlite
      USAGE_LOG_RETENTION_DAYS: "30"
      USAGE_LOG_CLEANUP_INTERVAL_MINUTES: "60"
    volumes:
      - ./data:/app/data
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"
```

数据库与 WAL 所在目录一起挂载持久卷。Docker 日志按容量轮转，每个容器约保留至多 5 个 20 MB 日志文件，不保证固定天数；修改日志设置后需重建容器。此设置不清理应用 JSONL、数据库或截图文件。[Docker json-file 文档](https://docs.docker.com/engine/logging/drivers/json-file/)

## 8. 实施顺序与验收

实施顺序：存储层与迁移工具 → 写入与独立汇总 → 查询和导入导出 → 配置与清理任务 → 管理面板 → 部署说明与验证。

验收必须覆盖：

1. 迁移后请求数、结果计数、账号/模型汇总与旧数据一致；重复迁移和重复导入不增加累计值。
2. 清理旧明细后重启，累计统计不下降；外键子记录无残留，调度状态不受影响。
3. 永久保留、空数据库、关闭统计、无效配置、修改期限、夏令时、过期边界相等时的行为符合定义。
4. 到期时间、待清理状态、最近成功时间、下一次检查时间在前端正确显示；中文、英文、移动端均可用。
5. 并发请求、分页、清理、导入同时发生时不重复计数、不静默丢请求；失效游标可正确刷新。
6. 迁移中断、磁盘满、数据库忙、清理失败时不会把半成品当成成功，错误状态可见，恢复后可继续。
7. 延长保留期限后导入已经清理过的历史仍被水位拒绝，累计值不重复增加。
8. 百万级明细下启动不全量加载历史，内存不随历史条数线性增长；分页、清理耗时和代理请求延迟有实测记录。
9. 导出 JSONL 可重新解析；一致性备份可还原；公开接口不泄露 IP、账号敏感信息或存储状态。
10. Docker 轮转与数据库清理独立工作；文档中的“已实现”说明仅在对应代码交付后更新。
