# 403 风控、账号禁用与 Context 调度改造文档

## 1. 背景

本项目使用模型感知账号池和多 browser context/page 调度请求。在公益站实际运营中，HTTP 403 既可能是短时风控，也可能是持续数十分钟甚至更久的账号级风控。当前 403 虽已被分类为 `risk_controlled`，但冷却时间仍复用普通临时错误配置，容易让尚未恢复的账号频繁重新进入候选池。

其直接影响包括：

- 请求反复命中同一个仍处于风控期的账号；
- 浪费请求重试预算并增加用户等待时间；
- 触发无效的 context 换入、初始化和淘汰；
- 占用 browser context 名额和内存，加剧调度拥堵；
- 运维人员无法快速将明确异常的账号移出调度池。

## 2. 当前实现

### 2.1 403 错误处理

`ModelScheduler.classifyError()` 优先将所有 HTTP 403 归类为 `risk_controlled`，包括错误消息中含有 `PERMISSION_DENIED` 的 403。这可以避免把普通 403 永久标记为模型不支持。

但是 `failure()` 对 `risk_controlled` 和 `temporary` 使用相同退避：

```text
TEMP_ERROR_COOLDOWN × min(4, 2 ^ (consecutive_failures - 1))
```

在默认 `TEMP_ERROR_COOLDOWN=30` 时，冷却序列为 30、60、120、120 秒。冷却到期后，`slot()` 会清除 `cooldown_until`，下一个真实请求作为 probe，账号重新进入候选池。

现有问题是 403 与 5xx 共用 `consecutive_failures` 和冷却基数，无法针对风控独立调参，也可能出现不同错误类型相互放大退避的情况。

### 2.2 当前请求和账号选择策略

调度器先选择账号，账号再使用与其绑定的 browser context/page，不会在选中账号后另行选择一个无关 context。

账号候选阶段会排除：

- `healthy=false` 的账号；
- 当前请求已尝试过的账号；
- 当前模型被标记为 `unsupported` 的账号；
- `cooldown_until` 尚未到期的账号 × 模型 slot；
- 没有 READY context 的账号（开启 `SCHEDULER_READY_CONTEXT_ONLY` 时）；
- 已达账号、账号 × 模型或 context 并发上限的账号。

对剩余的 ready 账号，按以下顺序升序比较：

1. 账号 × 模型 inflight；
2. 账号总 inflight；
3. 最近一分钟的本地传输故障数；
4. 当策略为 `least_used` 时的累计请求数；
5. 账号 × 模型 `last_used_at`；
6. `last_selected`；
7. 账号 index。

模型队列自身先按 min/preferred 配额等级排序，同级按入队顺序处理。同一请求的重试会排除已尝试账号，不会在该请求中再次使用同一账号。

### 2.3 当前冷 context 换入策略

如果某个排队请求有合格账号，但这些账号没有 READY context，调度器会向 `BrowserManager` 提交 context demand。

- 调度器按 pending 请求顺序扫描；
- 每个请求从 auth rotation 顺序中选取第一个合格的冷账号；
- 显式 demand 优先于为达到 `CONTEXT_POOL_MIN_READY` 而进行的普通预热；
- 多个 demand 按 `contextDemand` Map 的插入顺序处理；
- 同时初始化数受 `CONTEXT_INIT_CONCURRENCY` 限制。

### 2.4 当前 context 淘汰策略

在 context 池已达 `MAX_BROWSER_WORKERS` 时，当前模型感知调度逻辑会从 `contexts` Map 中找到第一个没有 account inflight 的 context 并关闭，然后初始化目标 context。

该策略的特征是：

- 不会为换入新 context 强制关闭有在途请求的 context；
- 选中的空闲 context 通常近似“最早插入 Map”，但并非严格 LRU；
- 淘汰时没有比较账号是否冷却、不健康、已禁用或有新的排队需求；
- 池满且所有 context 均繁忙时，新 context 无法立即换入；
- 在容量压力下，调度器可选择 inflight 最少的活跃账号作为 `drainingAccount`，停止给它发放新租约，等待其变为空闲。

## 3. 改造目标

1. 403 使用独立且明显更长的冷却策略，不影响普通 5xx 恢复速度。
2. 允许运维人员人工禁用整个账号，并确保禁用状态不会被自动成功、冷却到期或单模型恢复意外清除。
3. 禁用账号不再获得新请求，也不占用无效的预热 context 名额。
4. context 淘汰从“第一个空闲 context”改为可解释的优先级策略。
5. 不中断已经在途或正在输出的请求。

## 4. 403 独立冷却改造

### 4.1 新增配置

建议新增：

```env
# HTTP 403 风控的初始冷却时间，单位秒
RISK_CONTROL_COOLDOWN=600

# HTTP 403 连续风控的最大冷却时间，单位秒
RISK_CONTROL_MAX_COOLDOWN=10800
```

`TEMP_ERROR_COOLDOWN` 继续仅用于普通短时错误，`RATE_LIMIT_COOLDOWN` 继续仅用于 429 / `RESOURCE_EXHAUSTED`。

### 4.2 建议退避

推荐默认序列：

```text
10 分钟 -> 30 分钟 -> 1 小时 -> 3 小时（封顶）
```

可以用显式倍数表达：

```js
const multipliers = [1, 3, 6, 18];
cooldown = Math.min(maxCooldown, baseCooldown * multipliers[Math.min(failures - 1, 3)]);
```

建议加入±10% 随机抖动，避免多个账号在同一时刻解冻并同时 probe。测试中应允许注入随机数或关闭抖动，保证断言稳定。

### 4.3 独立计数器

在账号 × 模型 slot 中新增：

```js
risk_control_failures: 0;
last_error_kind: null;
```

行为要求：

- 403 只增加 `risk_control_failures`；
- 5xx 仍使用临时错误计数，不放大 403 退避；
- 该 slot 产生一次真实成功响应后，将 `risk_control_failures` 清零；
- 手动恢复账号或模型时清零；
- 只是冷却到期时不清零，否则持续 403 永远只会得到首档冷却。

### 4.4 作用粒度

单次 403 继续只冷却当前“账号 × 模型” slot，不自动永久禁用整个账号。这样可以保留不同模型权限、区域策略和局部风控的兼容性。

后续可选增加“疑似账号级风控”状态：仅当同一账号在多个模型上连续发生 403 时提示运维，首版不自动永久禁用。

## 5. 人工禁用账号

### 5.1 数据模型

禁用状态必须与系统健康状态分离：

```js
{
    healthy: true,
    disabled: false,
    disabled_at: null,
    disabled_reason: null
}
```

禁用时设置：

```js
disabled = true;
disabled_at = Date.now();
disabled_reason = "manual";
```

不应用 `healthy=false` 代表人工禁用。`healthy=false` 保留给登录失效、Cookie 失效、账号暂停等自动健康判断。

### 5.2 调度行为

`eligibleAccounts()` 增加 `!account.disabled` 条件。

禁用账号时：

- 立即停止发放该账号的新租约；
- 不中断现有在途请求；
- 已经获得租约但尚未开始的请求不强制迁移，避免引入新竞态，后续可单独优化；
- 调用 `drain()` 使排队请求立即重新评估其他账号；
- 从 `contextDemand` 移除该账号，防止尚未开始的 context 预热；
- 若 context 已经空闲，将其关闭或标记为首选淘汰对象；
- 若 context 仍有在途请求，标记 draining，等其空闲后关闭。

### 5.3 恢复边界

只有以下两个操作可以清除人工禁用：

1. 该账号的“恢复账号及全部模型”；
2. “一键启用所有账号”。

以下操作不得解除人工禁用：

- 冷却自然到期；
- 成功响应或健康检查成功；
- 单模型“恢复”；
- “一键重置所有账号 429 状态”；
- browser context 重建、WebSocket 重连或进程重启。

### 5.4 持久化

`disabled`、`disabled_at` 和 `disabled_reason` 应写入 `scheduler-state.json`，确保服务重启后仍然生效。

建议将 scheduler state schema 从 version 4 升级到 version 5，加载旧版状态时为缺失字段设置默认值：

```js
account.disabled ??= false;
account.disabled_at ??= null;
account.disabled_reason ??= null;
```

如果不升级 schema，也必须在 load 过程做同样的字段归一化，但显式升级更利于追踪数据格式。

## 6. 管理 API 与页面

### 6.1 API

建议新增：

```http
POST /api/scheduler/disable
Content-Type: application/json

{
  "account_id": 0
}
```

成功响应：

```json
{
  "success": true,
  "changed": true,
  "account_id": 0,
  "disabled": true
}
```

要求：

- 仅管理员可调用，复用现有 `isAuthenticated` 中间件；
- `account_id` 必须是当前存在的账号；
- 操作幂等，重复禁用返回 `changed=false`；
- 记录管理日志，但不输出 Cookie 或其他认证内容；
- 禁用允许在有 inflight 时执行，语义是“停止新请求，现有请求继续”。

现有恢复 API 的行为调整：

- `POST /api/scheduler/reset` 且未传 `model`：清除该账号的 `disabled` 并恢复全部模型；
- `POST /api/scheduler/reset` 且传入 `model`：只恢复该 slot，不清除 `disabled`；
- `POST /api/scheduler/reset-all`：清除所有当前有效轮换账号的 `disabled`；
- `POST /api/scheduler/reset-rate-limits`：不清除 `disabled`。

### 6.2 管理页面

在账号摘要行的“恢复账号及全部模型”旁增加“禁用账号”按钮。

建议交互：

- 点击后确认：“禁用后将不再向该账号分配新请求；已在执行的请求不会被中断。是否继续？”；
- 账号已禁用时按钮禁用或隐藏；
- 禁用操作不因 `account.inflight > 0` 而禁用；
- 恢复操作是否允许在 inflight 时执行可沿用现有策略，但不应影响禁用按钮；
- 账号摘要显示 `DISABLED`，不要将其显示为 `UNHEALTHY`；
- 模型 slot 在账号禁用时可显示 `ACCOUNT_DISABLED`，或在账号标题上明确说明整体禁用；
- 中英文 locale 同步增加按钮、确认、成功、无变化及失败文案。

## 7. Context 调度改造

### 7.1 预热过滤

`BrowserManager._poolCandidates()` 目前主要依据 auth rotation、READY 数量和 unavailable retryAt 构建普通预热候选。改造后必须排除人工禁用账号，否则它们虽不会获得请求，仍会占用 context 名额。

建议由 scheduler 暴露无副作用方法：

```js
isAccountManuallyDisabled(authIndex);
```

BrowserManager 不应自行解析 scheduler 持久化对象。

对于所有模型都冷却的账号，首版不建议直接永久排除预热，因为调度器不一定知道将来请求的全部模型。可在淘汰评分中降低其保留优先级。

### 7.2 记录 context 使用时间

在 context state 或与 account 对应的调度状态中记录：

```js
last_request_at;
created_at;
```

`last_request_at` 在真正向该 context 转发请求时更新，而不是只在 context 创建或 Launch 检测时更新。

### 7.3 淘汰优先级

仅对没有 inflight 且没有活跃 MessageQueue 的 context 进行淘汰。从最应被淘汰到最应保留的建议顺序为：

1. 人工禁用账号的 context；
2. 登录失效、账号不健康、auth 过期或已移出 rotation 的 context；
3. 所有已知 slot 都在长冷却或不支持状态的 context；
4. 没有对应排队需求的 context；
5. `last_request_at` 最早的 context（真正 LRU）；
6. `created_at` 和 account index 作为稳定的平局器。

建议将评分封装成纯函数，便于单元测试和管理快照展示：

```js
rankContextForEviction(authIndex, now);
```

不建议将单个不透明的加权总分作为首版实现。按元组逐项比较更容易解释与测试，例如：

```js
[disabledRank, unhealthyRank, unusableSlotsRank, queuedDemandRank, lastRequestAt, createdAt, authIndex];
```

### 7.4 繁忙 context 的 draining

当池已满且无空闲 context 时：

- 不抢占、不关闭正在输出的 context；
- 从可排空账号中选择保留优先级最低者作为 draining 目标；
- 人工禁用的繁忙 context 必须优先 draining；
- 停止向 draining 账号发放新租约；
- 最后一个租约和 MessageQueue 释放后再关闭 context；
- 关闭完成后立即 pump context demand。

现有仅按最小 inflight 选择 `drainingAccount` 的策略可作为后置平局条件，不再是唯一条件。

## 8. 状态和可观测性

账号快照建议新增：

```json
{
  "disabled": true,
  "disabled_at": 1780000000000,
  "disabled_reason": "manual"
}
```

模型 slot 建议新增：

```json
{
  "last_error_kind": "risk_controlled",
  "risk_control_failures": 2
}
```

context 快照可新增：

```json
{
  "created_at": 1780000000000,
  "last_request_at": 1780000123000,
  "draining": false,
  "eviction_priority": "healthy_idle_lru"
}
```

建议日志明确记录：

- 403 的账号、模型、连续次数、冷却截止时间；
- 人工禁用和恢复动作；
- context 淘汰目标及选择原因；
- 因池满而等待 draining 的 demand；
- 被禁用账号的 context 何时完成关闭。

## 9. 竞态与安全要求

- 账号选择和 inflight 预留仍保持同步完成，不在两者之间加 `await`；
- 禁用与租约同时发生时，已经预留的租约允许完成，之后不再发放新租约；
- 关闭 context 前同时检查 scheduler inflight 和 ConnectionRegistry 的活跃 MessageQueue；
- context 初始化过程中收到禁用操作时，初始化结束后不得进入 READY 预热池，应立即关闭；
- 恢复账号不强制同步初始化 context，只需清除状态、触发 `drain()` 和 context pool pump；
- API 输入必须验证 account ID，不允许通过人工禁用操作修改 auth 文件。

## 10. 测试计划

### 10.1 403 冷却

- 403 被分类为 `risk_controlled`；
- 首次 403 默认冷却约 600 秒；
- 连续 403 按 10 分钟、30 分钟、1 小时、3 小时退避；
- 冷却不超过 `RISK_CONTROL_MAX_COOLDOWN`；
- 403 不设置 `unsupported`、`rate_limited` 或 `account.healthy=false`；
- 5xx 仍按 `TEMP_ERROR_COOLDOWN` 退避；
- 5xx 失败不改变 403 连续次数；
- 冷却到期后可执行一次真实 probe；
- probe 再次 403 时进入下一退避档位；
- 真实成功或手动恢复清零 403 计数。

### 10.2 人工禁用

- 禁用后该账号不再被 `eligibleAccounts()` 返回；
- 禁用后排队请求可切换到其他账号；
- 有 inflight 时可禁用，已有请求不被中断；
- 冷却到期、成功响应、单模型恢复和 429 重置不解除禁用；
- “恢复账号及全部模型”可解除单账号禁用；
- “一键启用所有账号”可解除所有有效账号禁用；
- 状态在重启后仍然保留；
- 重复禁用 API 保持幂等。

### 10.3 Context 调度

- 普通预热和显式 demand 都不初始化已禁用账号；
- 禁用账号的空闲 context 优先被淘汰；
- 繁忙 context 不被直接关闭；
- 禁用账号的繁忙 context 在请求和队列释放后关闭；
- 没有高优先级异常时，真正的 LRU context 被淘汰；
- 有对应排队 demand 的 context 比无 demand context 更优先保留；
- 满池 draining 后能继续 pump 目标 context，不会丢失 demand；
- 禁用与 context 初始化并发时不会留下无效 READY context。

### 10.4 API 和 UI

- 未登录请求无法禁用账号；
- 非法、缺失或已移除的 account ID 返回 400；
- 按钮状态、确认文案和成功提示正确；
- 禁用后页面显示 `DISABLED`；
- 单账号恢复和一键启用后页面及时刷新；
- 中英文 locale 键完整，构建和 lint 通过。

## 11. 建议实施顺序

1. 增加 403 独立配置、状态字段和退避单元测试。
2. 增加账号人工禁用状态、持久化迁移和调度过滤。
3. 增加禁用 API，并调整单账号恢复和批量恢复语义。
4. 增加管理页按钮、状态展示和中英文文案。
5. 让 context demand、预热、初始化收尾逻辑排除已禁用账号。
6. 增加 context 使用时间，实现可解释的淘汰排序。
7. 完成并发、持久化、重启和管理界面回归测试。

## 12. 验收标准

改造完成后应满足：

1. 默认情况下，403 账号 × 模型至少 10 分钟内不会重新进入候选池。
2. 持续 403 会逐步延长冷却，而不影响其他账号、模型或普通 5xx 的冷却。
3. 管理员可以在账号有在途请求时禁用它，新请求立即不再选中该账号，原请求不被中断。
4. 禁用状态只能由“恢复账号及全部模型”或“一键启用所有账号”恢复，并且重启后不丢失。
5. 已禁用账号不会被后台预热，其空闲 context 会被优先释放。
6. context 池满时不会关闭正在服务请求的 context，空闲 context 按明确的状态和 LRU 规则淘汰。
7. 日志和管理快照可以解释账号为何不可用、context 为何被淘汰以及何时将再次 probe。
